# PR #11 人工测试指南

## 1. 测试目标

本指南验收 PR #11 的四条主链路：

1. steveX 从 Mineflayer 命令系统切换到 Fabric Mod WebSocket API。
2. Agent Connect/Disconnect 与 `/api/mod/*` 使用同一条 Mod 连接。
3. Web 面板实时显示玩家状态；Mod API 查询器选方法看 step JSON 写法并助写，Mod Batch 负责顺序执行。
4. 采集端通过 `vision/snapshot` 写入 NBT，记忆端读取这些文件恢复记忆世界。

## 2. 环境准备

要求：

- Windows PowerShell
- JDK 21+（已验证 JDK 24）
- Node.js 18+
- 首次构建时可访问 Gradle、Fabric 和 Minecraft 依赖源

在仓库根目录执行：

```powershell
npm run bootstrap
npm audit
```

通过标准：`bootstrap` 成功，`npm audit` 输出 `found 0 vulnerabilities`。

可选地先验证两个 Mod 能否构建：

```powershell
cd vendor\stevex-template-1.21.11
.\gradlew.bat build

cd ..\stevex-test-template-1.21.11
.\gradlew.bat build
```

通过标准：两次均输出 `BUILD SUCCESSFUL`。可忽略 Gradle 10 兼容性提示、开发客户端 Realms 401 和 JDK 24 的 LWJGL native-access 警告。

## 3. 启动采集端与 steveX

打开终端 A：

```powershell
npm run mc:capture
```

首次启动可能需要数分钟。Minecraft 主菜单加载完成后，Mod 会监听 `127.0.0.1:25550`；但 `player`、`f3`、`vision/*` 等方法在进入世界前应返回 `player not connected`。

创建或进入一个单人测试世界，再打开终端 B：

```powershell
npm start
```

浏览器访问 `http://localhost:8090`，在 Agents 页面点击 `steveX` 的 Connect。

通过标准：

- 页面显示 `WS: online`。
- Agent 显示 online。
- Mod 显示 `127.0.0.1:25550`。
- 约 3 秒内出现生命值和真实坐标。

## 4. API 冒烟测试

保持两个进程运行，并确保页面已经 Connect：

```powershell
node test_mod_api.js --stevex
```

通过标准：最终输出 `ALL PASS`。

额外验证连接生命周期：

1. 点击 Disconnect。
2. 调用任意 Mod 方法，应得到 HTTP 502 和 `Mod not connected`。
3. 再次点击 Connect。
4. 等待约 3 秒，生命值和坐标应恢复。

## 5. Mod API 查询器 + 单步 Batch 执行

面板已移除一次性 Send 直调：**Mod API 查询器**负责「选方法 → 看 step JSON 序列写法 → 填参助写」
（只读，**不执行**）；执行统一走 Mod Batch。单步执行 = 查询器「追加到 Mod Batch」后 Run 一行。

选中方法后，detail 顶部是**「语法框」**：第一行 = 该方法的分类 tag + 方法名 + **中文说明**（带参方法会在
说明里直接列出 `params` 可填键，无参方法注明「无参数」），下方固定为 step JSON 写法提示（调用步 / 纯等待步）；
语法框之下才是可编辑 step 模板与参数提示行。

操作步骤：

1. 在卡片 `Mod API 查询器` 的搜索框输入 `player`（名字/中文功能都可过滤），选中 `player`。
2. 「语法框」第一行应显示 `感知/查询 · player · 玩家状态：…，无参数`；语法框下是可编辑 step 模板
   `{"method":"player","params":{}}`，参数提示行显示「无参数」。
3. 点「追加到 Mod Batch」→ 同卡 Mod Batch 文本框末尾出现该行；点 Run，结果区输出
   `player` 结果并以 `— batch done —` 收尾。
4. 搜索框输入 `chat` 重新过滤、选 `chat/send`：「语法框」第一行中文说明应带
   「…params 填 { text }：内容…」的枚举；step 模板预填 `{"method":"chat/send","params":{"text":"hello"}}`，
   参数提示行列出 `text  string`；改值后再「追加到 Mod Batch」。
5. （目检多参方法的 zh 枚举与模板预填）选 `container/slot`：中文说明应为
   「点击容器格；params 填 { slot, button?, clickType? }：…」；step 模板预填
   `{"method":"container/slot","params":{"slot":1,"button":0,"clickType":0}}`，参数区列出 slot/button/clickType 三行。
6. （目检必填标注）选 `vision/entity`：中文说明应含「params 填 { uuid(必填), force? }」，参数区 `uuid` 行标「必填」。

无参方法单步验证（预期结果同旧表，均作为一行 Batch 执行）：

| step JSON | 预期结果 |
|---|---|
| `{"method":"status","params":{}}` | `ok`，包含 `busy` 和 `error` |
| `{"method":"player","params":{}}` | 返回 `vitals` 和 `flags` |
| `{"method":"f3","params":{}}` | 返回三维坐标和维度 |
| `{"method":"inventory","params":{}}` | 返回 `slots` 数组 |
| `{"method":"settings/get","params":{}}` | 返回渲染距离、模拟距离和 FOV |

带参方法抽样（模板已按示例值预填，改后 Run）：

| step JSON | 预期结果 |
|---|---|
| `{"method":"camera/turn","params":{"dx":90,"dy":0}}` | 视角右转 |
| `{"method":"key/hotbar","params":{"slot":3}}` | 选中第 4 格热键栏 |
| `{"method":"chat/send","params":{"text":"hello"}}` | 聊天区出现 hello |

复制按钮：点「复制」→ 剪贴板拿到同一行 step JSON（按钮瞬时变「已复制!」）。

错误恢复测试（HTTP 层，REST 单次直调仍在）：`curl -X POST …/api/mod/player -d '{}'` 成功后，
先 `curl -X POST …/api/mod/not-exist -d '{}'`（应 502 + unknown method），再成功调用 `player`，
等待下一次状态刷新：Agent 的 Mod error 应恢复为空，不应永久保留旧错误。

## 6. Batch Runner

Batch 现由 8090 服务端统一执行（`POST /api/mod/batch`，设计见 `docs/批量时序API设计方案.md`），
不再使用 `delay:` 文本前缀：每行一个 step JSON，调用步可带 `waitMs`（执行前先等），纯等待步只要 `waitMs`。

### 顺序与延时

输入：

```text
{"method":"status","params":{}}
{"waitMs":300,"method":"player","params":{}}
```

通过标准：按顺序显示两条成功结果，最后显示 `— batch done —`；Run 恢复可用，Stop 隐藏。

### 即时停止

输入：

```text
{"method":"status","params":{}}
{"waitMs":5000}
{"method":"player","params":{}}
```

点击 Run 后，在等待阶段点击 Stop。

通过标准：无需等满 5 秒，立即显示 `— batch stopped —`，等待步与 `player` 显示 `skipped`，
第三条 `player` 不执行；Run 恢复可用。

### 持续按键清理

输入（序列结束时前进键仍按住）：

```text
{"method":"key/up","params":{"pressed":true}}
{"waitMs":500}
```

通过标准：Batch 结束或中途停止时输出 `released key/up`，玩家不会持续移动（服务端兜底补发松开）。
正常脚本仍建议显式成对写：

```text
{"method":"key/up","params":{"pressed":true}}
{"waitMs":500}
{"method":"key/up","params":{"pressed":false}}
```

### 并发拒绝

一个 Batch 正在运行时再点另一个卡的 Run。

通过标准：第二个显示 `batch failed to start: a batch is already running`；第一个不受影响。

## 7. 视觉与记忆端

记忆端需要采集端先生成数据。不要只进入世界后就立即判断记忆端路径错误。

调用完整视觉测试：

```powershell
node test_mod_api.js --stevex --all
```

或在 Web 面板调用 `vision/snapshot`，Params 使用 `{}`。首次视觉调用可能耗时较长。

确认目录中至少出现以下文件：

```text
vendor/stevex-template-1.21.11/run/stevex/vision/block_entities.nbt
vendor/stevex-template-1.21.11/run/stevex/vision/terrain.nbt
vendor/stevex-template-1.21.11/run/stevex/vision/entities.nbt
```

然后打开终端 C：

```powershell
npm run mc:memory
```

通过标准：

- 记忆端自动创建或进入 `MemoryWorld`。
- 日志不再持续显示 `Source file missing`。
- 日志显示读取到采集端 NBT，世界中出现对应地形/实体。
- 采集端再次执行 `vision/snapshot` 后，记忆端按文件 mtime 自动更新。

如果两个 vendor 目录被改名或不再同级，需要编辑：

```text
vendor/stevex-test-template-1.21.11/run/config/stevex-test/memory.json
```

显式填写 `sourceFile`、`terrainFile`、`entityFile` 和 `memoryCellsFile`。

## 8. 配置页面

在全新 clone 或不存在 `configs/environments/app.json` 时打开 Configs：

1. 页面应正常显示空覆盖配置，不应返回 500。
2. 保存后应自动创建 `configs/environments/` 和 `app.json`。
3. 点击 Reload Config 后，Agent 列表和 Mod 地址应更新。

不要把含 API Key 的环境配置提交到 Git。

## 9. 结束测试

在三个启动终端中分别按 `Ctrl+C`。如果 PowerShell 询问 `Terminate batch job (Y/N)?`，输入 `Y`。

确认端口已释放：

```powershell
Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue |
  Where-Object { $_.LocalPort -in 8090,25550 }
```

无输出表示 steveX 和采集端 Mod 已关闭。
