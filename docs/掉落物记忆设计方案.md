# 掉落物记忆设计方案（v2.34）

> 状态：**已实施（采集端 + 记忆端代码落地，双端 compileJava --offline 通过，2026-09-06；runtime 启动验证待做）**。
>
> 用户需求：视觉链路目前**看不到掉落物**——采集端只把 `minecraft:item`（ItemEntity，地上掉落物）当普通
> 实体轻量快照（有位置、无内容），记忆端据此重建出**空物品实体**，而 vanilla `ItemEntityRenderer`
> 对空物品整体不提交渲染 → 记忆世界里地面物品不可见。需求：让记忆世界（与 agent 数据面）能看到
> 掉落物**及其内容**（是哪个物品、堆叠几个、带什么外观数据）。

## 1. 背景与问题（现状核查，均已落代码）

1. **采集端已经"看得见掉落物、只是不认得"**：
   - [LevelRendererMixin.java:88-140](vendor/stevex-template-1.21.11/src/main/java/name/modid/mixin/LevelRendererMixin.java#L88-L140) 复刻 vanilla 裁剪谓词后对**全部被渲染实体**做快照，无类型排除——掉落物在可见列表里（`typeId="minecraft:item"`）；
   - 可见性判定：[ObjectResolver §5.3](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ObjectResolver.java#L323)（不透明物品写 main 深度）+ [工序 D §5.3.1（v2.25）](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ObjectResolver.java#L392)（Fabulous 下半透明物品模型）——两类掉落物都能报可见；
   - 但 [VisionEntityStore.sync](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionEntityStore.java#L127-L137) 只落轻量字段：`id/uuid/type/pos/motion/rot/onGround/health`，**无 ItemStack**。
2. **物品内容采集端拿得到**：1.21.11 `ItemEntity` 的物品栈放在**同步实体数据** `DATA_ITEM`
   （`EntityDataSerializers.ITEM_STACK`）——客户端副本真实持有 `id/count/components`，`getItem()` 即可读
   （decompiled 核实；按惯例最终以 compile 为准）。
3. **记忆端重建后不可见**：[EntityRestorer.spawn](vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/EntityRestorer.java#L300-L322) 用 `EntityType.ITEM.create(level, LOAD)`（默认空栈）→
   [ItemEntityRenderer.java:44](decompiled_src_vf/client/net/minecraft/client/renderer/entity/ItemEntityRenderer.java#L44)
   `if (!state.item.isEmpty())` **空栈整体不提交**（模型、影子都跳过）→ 地面那格存在一个看不见的空实体。
4. **拾取是"玩家驱动"的（重要）**：`Player.aiStep` 每 tick 扫描身边 `AABB.inflate(1,0.5,1)` 内实体并 `entity.playerTouch(player)`
   ——**不需要掉落物自己 tick**。记忆端 `type.create` 出来的 ItemEntity 默认 `pickupDelay=0`（[ItemEntity.java:334](decompiled_src_vf/client/net/minecraft/world/entity/item/ItemEntity.java#L334) `playerTouch` 判 `pickupDelay==0` 即入包）——
   因此若只加物品内容而不拦拾取，记忆玩家**走上去就会把记忆里的掉落物捡走**（且因 v2.13 mtime 门控，文件不变时不会被立即回卷，要到下次采集才"复现"，产生闪烁）。
5. **物品序列化范式现成（v2.28 容器同款）**：`ItemStack.CODEC` + `NbtOps`，产出 `{id, count?, components?}`——
   采集侧 [ContainerMemoryTracker.encodeItem](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ContainerMemoryTracker.java#L356)（`registryAccess().createSerializationContext(NbtOps.INSTANCE)`）、
   记忆侧 [ContainerMemoryApplier.parseItem](vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/ContainerMemoryApplier.java#L385)（`registries.createSerializationContext(...)` 解析）对称。本方案原样复用。

## 2. 设计目标与范围

**目标**：① 记忆世界复现 agent 看到的掉落物（内容保真、可见、静止、只读）；② agent 数据面（snapshot JSON）
能看到"地上是什么"。

**范围**：仅 `minecraft:item`（ItemEntity）掉落物。

**明确不在本轮范围**（同属"可见物品"但机制不同，需另一主题设计）：
- `minecraft:item_frame` / `glow_item_frame` / 盔甲架手持/装备、`display` 实体——携带物品/装备的展示实体（重建亦为空，需按类型读各自持有物）；
- 玩家/生物的装备栏外观（视觉是"穿着"而非独立实体）；
- 经验球 `minecraft:experience_orb`：渲染为纯贴图、**不依赖 ItemStack**，现链路 type 重建即可见，无需处理（对照旁证）。

## 3. 要采集的信息（核心清单）

对每个**被判可见**的掉落物（`typeId=="minecraft:item"`，经 §5.3 或工序 D），在其实体条目里采集：

| # | 字段 | 类型 | 内容 | 用途 | 来源 |
|---|---|---|---|---|---|
| 1 | `id` | UUID | 实体 uuid（键） | 冻结/去重/删除 | 既有 |
| 2 | `type` | string | `minecraft:item` | 判别 | 既有 |
| 3 | `pos` | double[3] | 掉落物精确坐标（含悬浮高度） | 放置位置 | 既有（§5.3 partialTick 插值） |
| 4 | `rotation` | float[2] | yaw/pitch | 静止朝向 | 既有 |
| 5 | `onGround` | bool | 是否着地 | 语义参考（重建恒冻结） | 既有 |
| 6 | `motion` | double[3] | 帧间速度 | **只存档、重建归零**（冻结） | 既有 |
| 7 | `health` | float | 非 LivingEntity 记 0 | 占位（物品不受生命影响） | 既有 |
| **8** | **`item`（新增）** | CompoundTag | **掉落物完整物品栈**，`ItemStack.CODEC` 编码 | 记忆端重建内容 + 渲染模型 | **本方案** |

**字段 8 `item` 的结构与细节**：

- 序列化 = `ItemStack.CODEC` + `NbtOps` → `{ "id": <物品注册 id>, "count": <int，==1 时省略>, "components": <data components，仅当非默认> }`（与 v2.28/29 容器、末影箱条目同一编码，两端解析对称）。
- 内含物：**完整 `components`，不做外观字段白名单**（推荐，理由见 §6 决策点 A）：
  - 决定模型/质地的 `item_model`、自定义模型、`damage` 损坏度、皮革/旗帜颜色、**药水/喷溅/滞留的类型与颜色**、烟花、地图、附魔（glint 光效层虽无深度但吸附于本体、随本体进 world 渲染）等；
  - 白名单方案被否：1.21.11 物品外观由 data components **数据驱动**（`item_model` 可指向任意模型、纹理可带任意 tag），外观字段无法靠静态白名单穷举——漏一个组件就渲染错，宁全量保真。
- **空栈不采**：`stack.isEmpty()` → 无 `item` 键（条目照常进轻量快照，记忆端按 §5 规则跳过不生成）。
- **采集时机**：在 `extractVisibleEntities` @TAIL **快照帧**内、对幸存 ItemEntity 当场 `getItem()` 编码落进快照——
  此时读到的就是"本帧被渲染的那个栈"，杜绝 ObjectResolver 延后 1~2 帧解析时栈被合并/拾取换掉的竞态；
  编码需 `registryAccess()`（`Minecraft.level`），该点在渲染线程可用。
- **采集成本**：仅当 `captureRequested`（现有门控）时对掉落物逐条编码一次，掉落物稀疏（通常数十），逐条几字段，量级可忽略。
- **不采集**（并说明为什么）：
  - `age` / 剩余存活：记忆世界时间冻结 + `setUnlimitedLifetime`，无意义；
  - `pickupDelay`：记忆端**固定置无穷**（见 §4 只读），不采；
  - `thrower` / `owner` / `target`（拾取归属/磁吸目标）：记忆世界只读参照，无归属语义；
  - 物品 glint / 半透明掉落物的 item_entity 目标深度：视觉判定已在 §5.3.1 覆盖，不额外读目标；
  - 实体**非** `minecraft:item` 一律不带 `item` 键。

**agent 数据面（建议一并做）**：`snapshot` 响应 `entities[]` 对带 `item` 的条目补
`"item": {"id": <物品 id>, "count": N}`（组件/详情仍走 Tier-2 `vision/entity` 按 uuid 查，保持快照轻量）。
——让"我们"（agent/大脑）在帧快照里直接知道地上是"什么物品、几个"。

## 4. 记忆端应用与冻结

1. **解析**：`EntityRestorer.parseBucket` 对实体条目读可选 `item`（CompoundTag）；仅当 `type=="minecraft:item"` 时用
   `ItemStack.CODEC` + `NbtOps` 解码（`ServerLevel.registryAccess()`，与容器同款）。解码空/失败/未知物品 id → `skip` 该条
   + 每类一次 WARN（同 v2.31 biomes 的注册表共享约定：记忆端须与采集端同物品注册表，mod 物品缺装/版本漂移即优雅跳过）。
2. **spawn**：
   - `type=="minecraft:item"` 且无 `item` 或解码为空 → **跳过，不再生成空实体**（顺带移除现行"隐形空实体"废条目）；
   - 有栈 → `type.create(...)` 后 `setItem(stack)`（重建为真实物品实体），其余照旧：`snapTo`、冻结、`addFreshEntity`。
3. **冻结扩展**（只读语义）：
   - 保留：`setNoGravity` / `setInvulnerable` / `setDeltaMovement(ZERO)` / `setUnlimitedLifetime` / FROZEN 停 tick；
   - **新增**：`setPickUpDelay(32767)`（无穷拾取延迟）——因拾取由**玩家** `aiStep` 扫描驱动、不依赖掉落物 tick，
     必须显式置无穷否则 `pickupDelay=0` 的复原物会被走近的记忆玩家立刻捡走；置无穷后 `playerTouch` 判 `==0` 恒假 → 纯可见。
4. **删除/减量通道不变**：掉落物被反向通道证明消失时，`discard` 照常清理（既有逻辑），无新耦合。

## 5. 文件格式与兼容

- `entities.nbt`：每个实体条目新增**可选** `item` 键（CompoundTag），其余键不动；`WorldsFile` 分桶结构（`currentDimension`/`worlds`）不动。**文件格式 version 不变**。
- 前向兼容（老读方读新文件）：旧解析器 `getCompoundOrEmpty` 未知键忽略 → 安全。
- 后向兼容（新读方读旧文件）：无 `item` 的 `minecraft:item` 条目 → 按 §4 跳过（不生成空实体）；旧存档无需迁移，现有隐形空实体在下轮 sync 自然不再重建。
- 新增编码字段仅影响 entity 条目内部，与 `memory_cells.bin` version=2 无关。

## 6. 决策定案（用户已审阅定夺）

| 决策 | 内容 | 定案 |
|---|---|---|
| **A：components 采集粒度** | 全量 `ItemStack.CODEC` vs 外观字段白名单 | **全量**——1.21.11 物品外观由 data components 数据驱动，白名单会漏组件渲染错；偶有仅行为性组件入库无越权（掉落物物品栈本就整体被展示，见 §7） |
| **B：拾取语义** | 只读参照 vs 可拾取 | **只读参照**——`setPickUpDelay(32767)` 无穷延迟 + FROZEN 停 tick，`playerTouch` 恒不触发；与 v2.28/29 容器只读参照一致；不产生"捡走→下轮采集复现"闪烁 |
| **C：agent 数据面** | snapshot `entities[]` 补 item | **补 `item:{id,count}`**——id/count 从已编码 tag 读出（CODEC 键 `id`/`count`，count==1 时省略按 1 读）；组件详情仍走 Tier-2 `vision/entity` |
| **D：范围** | 展示实体（item_frame/盔甲架/display） | **本轮只做 `minecraft:item` 掉落物**；展示实体非掉落物（MC 语义上为放置/装饰/数据驱动陈列物），机制各自不同（携带者专属展示参数），后续另案 |

## 7. 正确性论证

- **内容即展示、无越权**：掉落物渲染的内容**就是**其物品栈（模型/颜色/堆叠），采集它 = 采集 agent 看到的像素，
  不触碰任何"交互后才可见"的内部——与 §5.2.1 观察边界自洽（对比：容器内部须交互才可见故 v2.28 走独立交互通道；掉落物无此问题）。
- **拾取被掐死**：`pickupDelay` 无穷 + FROZEN 停 tick → 玩家驱动的 `playerTouch` 恒不触发 → 记忆掉落物纯装饰、不闪烁回卷。
- **渲染保真**：重建实体携带原 `id/count/components` → 客户端 ItemEntityRenderer 照常按模型/颜色/堆叠摊铺渲染，与采集瞬间所见一致。
- **时间冻结正交**：只改 spawn 时的物品内容与拾取延迟，不新增任何 tick / Mixin / 通道；对 v2.21 冻结、v2.23 减量、v2.32 分桶零影响。
- **竞态消除**：栈在快照帧编码，解析侧只读快照 tag → 无跨帧/合并竞态。
- **注册表失败优雅**：记忆端解码失败仅跳过该条，不崩、不刷屏（WARN once）。

## 8. 已知限制

- **动画相位不还原**：记忆世界时间冻结，掉落物以 `age=0` 静止；渲染 bob/spin 相位与采集瞬间存在亚像素~0.1 格的视觉偏差
  （`bobOffs` 是 `final`、随生成本身随机，无法也不值得还原）——位置/高度精确，视觉姿态静止但完整。
- **既有采集盲区照旧**：大堆物品 Z 向摊铺 ~3 格超出盒、亚像素掉落物（占屏 <1px）仍漏（§10 已知限制，非本版范围）。
- **客户端栈语义**：采集侧 ItemEntity 栈是客户端同步副本（可能滞后服务端真实状态瞬时值）；本项目采集定义即"视觉所见"，一致。

## 9. 验证步骤（实施后，游戏内）

1. 两端 `./gradlew compileJava --offline` 通过。✅（2026-09-06 已通过；步骤 2–8 为游戏内 runtime，待启动验证）
2. **不透明掉落物**：真实世界地面放 1 颗钻石 / 一组泥土 → agent 采集 → 记忆世界同点应见钻石/泥土（含堆叠摊铺），形态与采集一致、静止。
3. **半透明掉落物**（Fabulous）：玻璃瓶 / 药水 / 附魔物品 → 记忆世界可见（验证 §5.3.1 已有 + 新 item 保真的合成效果）。
4. **内容保真**：皮革染色甲 / 自定义模型 / 药水颜色 / 附魔 glint → 记忆世界渲染一致。
5. **只读语义**：记忆玩家走近/穿过掉落物 → 不拾取、不消失；确认无闪烁。
6. **删除回归**：真实世界把掉落物捡走/让其消失 → 反向通道删除记忆掉落物（既有通道回归）。
7. **兼容**：旧 entities.nbt（无 item）加载不崩、不生成空实体；无新 WARN。
8. **agent 数据面**：snapshot `entities[]` 的掉落物带 `item:{id,count}`；组件经 Tier-2 可取。
