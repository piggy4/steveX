# 展示实体内容记忆设计方案（v2.35）

> 状态：**方案已定案且代码已落地（2026-09-06，决策见 §12；双端 compileJava 通过，未提交，待实测验证 §10）**。
>
> 用户需求：视觉链路目前对 `item_frame` / 盔甲架 / `display` 等**展示/装饰实体**只能记录"裸物理状态"
> （有位子、有朝向），记不住它们的**内容**——框里的物品、盔甲架的装备与姿态、`display` 的 item/方块/文本
> 与变换。需求：让记忆世界（以及 agent 数据面）能按所见还原这些实体的内容。

## 1. 背景与问题（现状核查）

1. **采集端"看得见、不认得内容"**：
   - [LevelRendererMixin.java:113-147](vendor/stevex-template-1.21.11/src/main/java/name/modid/mixin/LevelRendererMixin.java#L113-L147)
     对**全部被渲染实体**做轻量快照，无类型排除 → `minecraft:item_frame` / `minecraft:armor_stand` /
     `minecraft:item_display` 等都在可见列表里；
   - 但 [VisionEntityStore.sync](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionEntityStore.java#L127-L141)
     只落轻量字段：`id/type/pos/motion/rotation/onGround/health`（+ v2.34 仅 `minecraft:item` 掉落物带
     `item` 栈）。**框内物品 / 装备 / 姿态 / display payload 无一字段记录**——这是设计注释明说的取舍
     （[VisionEntityStore.java:22-25](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionEntityStore.java#L22-L25)：
     "只存轻量物理状态，不存每实体全量 NBT…避免 GC 风暴"）。
2. **记忆端复原成"空壳默认实例"**：[EntityRestorer.spawn](vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/EntityRestorer.java#L305-L338)
   用 `type.create(level, LOAD)` 生成**默认态**再套 pos/rot（仅 LivingEntity 设血量、仅 ItemEntity 套物品栈），
   **从不给任意类型应用 NBT**。于是：
   - 物品展示框 → 空白框 + 默认 `Facing`（缺省 DOWN）、无锚定方块；
   - 盔甲架 → 素体默认姿态，无装备无手臂无底座设置；
   - `item_display`/`block_display`/`text_display` → 空内容、恒等变换；
   - `mannequin`（1.21.11 玩家模型人偶）→ 无皮肤无姿态。
3. **内容数据采集端本可拿到**：客户端副本对这类实体持有完整状态（框的 `DATA_ITEM`、盔甲架
   装备/Pose、display 的 payload），`saveWithoutId` 即可整体读出——Tier-2 端点
   [VisionApi `vision/entity`](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionApi.java#L192-L243)
   已验证可对**当前加载**实体产出"完整可装载 NBT"。但它是 live 查询：一次一个 uuid、实体须仍在加载中、
   结果只回给调用方，**不进 entities.nbt、不落入记忆世界**。
4. **v2.34 掉落物是先例**：`minecraft:item` 原本也只有裸物理 → 加 `item` 载荷字段后记忆端能还原出物品。
   本方案把同一思路推广到展示实体的**整份内容**（见 §3 为何这次用整份 NBT 而非单字段）。

## 2. 目标与范围

**目标**：① 记忆世界把 agent 看到的展示/装饰实体**连同内容**（框里物品、盔甲架装备姿态、display
item/方块/文本、变换）按所见还原，仍是静止只读参照；② 内容变化能被增量同步（无需整表重建）；
③ agent 数据面（snapshot JSON）能低成本看到这些实体的内容概貌（决策 2）。

**范围**：采集侧对以下**展示/装饰实体类型**补内容载荷（**默认 allowlist**，可经采集端配置增删，§6.1）：
`minecraft:item_frame`、`minecraft:glow_item_frame`、`minecraft:armor_stand`、`minecraft:mannequin`、
`minecraft:item_display`、`minecraft:block_display`、`minecraft:text_display`、`minecraft:painting`（已定案纳入）。

**明确不在本轮范围**：
- 普通生物/玩家手持或装备的外观（是"穿着/持在身上的物品"，视觉采集走整实体外观的另一个主题）；
- `minecraft:interaction`（无可视内容；**已定案不纳入**）；
- 掉落物（v2.34 已做）。

## 3. 方案核心（机制定案：可装载全量 NBT 载荷，opaque）

**一句话**：采集端对可见的 allowlist 实体，复用现成的整实体序列化
（`id` + `saveWithoutId`，即 [VisionCollector.collectEntityNbt](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionCollector.java#L79-L115)
 同款输出），作为该实体在 entities.nbt 里多一个 `nbt` 键；记忆端若条目带 `nbt`，直接用 **vanilla 装载路径**
 由 NBT 建出配置完整的实体，其余字段仍照旧从轻量快照驱动。

### 3.1 为何是"整份 NBT"，而非逐类型建模

展示实体的内容字段名/编解码随版本演进而异（1.21.11 已迁到 `ValueOutput`/codec 体系，且新出现 `mannequin`）。
逐字段白名单意味着：
- 每个类型都要在采集端写"读哪些键"、在记忆端写"套哪些键"，两端 × N 类型，且**漏一个键就错一种外观**；
- 下次 MC 加新展示实体/改键名，整表失效。

整份载荷则相反：键名与结构对**我们的代码完全 opaque**——采集端"原样存"、记忆端"原样交回 vanilla 装载"，
正确性由 vanilla 自身的 save/load 对称保证，天然覆盖未来新类型，只需在 allowlist 加一行。

**为什么成本可控**：序列化只发生在——实体可见、且命中 allowlist、且本帧确有采集请求时（非每帧全量），
与 v2.34 为掉落物每帧编码物品栈同一量级；展示实体 NBT 普遍很小（框 = 一个物品栈 + 几个标量）。
"避免 GC 风暴"的原顾虑针对的是**每 tick 对全部实体**全量序列化，本方案不触碰。

### 3.2 载荷与现有轻量字段的关系

一份载荷 = 一份**可独立装载的完整实体存档**，等价于分块存档里的单实体条目：

```
"nbt": { "id": "minecraft:item_frame", ...entity.saveWithoutId() 输出 }
```

（1.21.11 核实：[Entity.saveWithoutId](decompiled_src_vf/client/net/minecraft/world/entity/Entity.java#L1977)
 已写 `Pos/Motion/Rotation/UUID/OnGround/Invulnerable/NoGravity/CustomName/data` 等全部基类字段，只缺
 `id`——采集端补 `id` 即得标准实体存档格式，vanilla 装载器可直接消费。）

轻量字段（`pos/motion/rotation/onGround/health/type`）**保留照常写**，职责分工：
- 记忆端的放置/移动/删除沿用现有轻量物理驱动（纯累积、几何删除、mtime 门控全部不变）；
- `nbt` 只补"内容/状态"，二者解耦。

### 3.3 两端责任不对称（刻意）

- **采集端**：用 allowlist 限定"哪些类型值得付出序列化成本"（成本控制方，且名单进配置可调，§6.1）；
- **记忆端**：**不做 allowlist**——条目只要带 `nbt` 键就走整份装载路径（无该键则退回现在的默认态路径，
  兼容旧文件）。这样将来扩大 allowlist / 出现新展示实体，记忆端零改动自动支持。

## 4. 需要记录的数据（核心清单）

> 载荷对机制是 opaque（§3.1），下面按"这些展示实体**应该被记住的外观/内容**"列出语义数据，并给出
> 1.21.11 已核实的 NBT 键名作参考。键名只影响本清单的可读性，不影响机制正确性（读回全交给 vanilla）。

### 4.0 每份载荷都自动携带的基类字段（Entity.saveWithoutId，已核实）

`Pos`、`Motion`、`Rotation`、`fall_distance`、`Fire`、`Air`、`OnGround`、`Invulnerable`、`PortalCooldown`、
`UUID`、`CustomName`、`CustomNameVisible`、`Silent`、`NoGravity`、`Glowing`、`TicksFrozen`、`HasVisualFire`、
`Tags`、`data`(自定义数据)、`Passengers`(若载有乘客)。
（记忆端 freeze 会重写 `Invulnerable/NoGravity/速度`，基类字段与冻结互不冲突。）

## 5. 文件格式与兼容

entities.nbt 的实体条目新增可选键 `nbt`（载荷），其余不变：

```jsonc
"<uuid>": {
  "id": 42, "type": "minecraft:item_frame",
  "pos": [x, y, z], "motion": […], "rotation": [yaw, pitch],
  "onGround": 1b, "health": 20.0f,
  "nbt": { "id": "minecraft:item_frame", "Facing": 3b, "Item": {…}, … }   // 仅 allowlist 可见实体，可选
}
```

**向后兼容**：旧文件条目无 `nbt` → 记忆端走现有默认态路径，行为与现状逐字节一致；
实体一旦在新采集帧被看到且命中 allowlist，下一轮 sync 会带上 `nbt` → 内容自然"补全"（§7.4）。

## 6. 采集端改动

### 6.1 allowlist：进采集端配置（决策 3）

名单不硬编码在代码里，放本地配置文件 **`config/stevex/vision.json`**（与记忆端 memory.json 同款风格，
与现有 `config/stevex/client_defaults.applied` 同目录），键 `decorativeEntityTypes`：

```jsonc
{
  "decorativeEntityTypes": [
    "minecraft:item_frame", "minecraft:glow_item_frame", "minecraft:armor_stand",
    "minecraft:mannequin", "minecraft:item_display", "minecraft:block_display",
    "minecraft:text_display", "minecraft:painting"
  ]
}
```

- 读取器 `vision/DecorativeConfig.java`：文件缺失 → 用上面这份默认清单；存在 → 解析后生效（非法/空 → 告警 + 默认）。
- **mtime 门控热重载**：每轮采集开始时 stat 一次该文件，mtime 变了才重读（仿记忆端 §7.4 模式，成本≈0）——
  这样改 JSON 即改名单，不用重编译、重启即可对下一帧生效。
- 名单只影响"采集端为哪些类型付出序列化成本"。记忆端仍无名单（§3.3），即使采集端名单与记忆世界预期不符，
  也只是"某些展示物不补内容"，不会错配。

### 6.2 抽取整实体序列化助手

把 [collectEntityNbt](vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionCollector.java#L79-L115)
 里"按 uuid 找实体 → `saveWithoutId`"的尾部抽成
 `static CompoundTag serializeEntityFull(Entity entity, HolderLookup.Provider registries, Logger)`：
- 现 collectEntityNbt：按 uuid 找实体后调它（TTL 缓存语义不变）；
- mixin：手里已有实体引用，直接调它，免去二次线性查找。

### 6.3 载荷随帧编码

[LevelRendererMixin.onExtractVisibleEntitiesDone](vendor/stevex-template-1.21.11/src/main/java/name/modid/mixin/LevelRendererMixin.java#L94-L152)
 建 `EntitySnapshotData` 时：实体命中 allowlist → `payload = serializeEntityFull(entity, …)`（失败 → null，跳过
 载荷但不丢该实体——退回轻量路径）。字段透传到：
- `DepthCapture.EntitySnapshotData`（加 `CompoundTag payload`，`null`=非展示/失败）；
- `VisionCollector.EntityLightSnapshot`（加同名 `payload`）；
- `ObjectResolver.addEntity` 一路透传（与 v2.34 `item` 同款穿针引线）。
- `VisionEntityStore.sync`：`payload != null` 时写 `nbt` 键（文件通道）。

### 6.4 数据面薄摘要（决策 2：渠道 B）

snapshot JSON 的 `entities[]` 对命中 allowlist、且带内容的实体额外暴露一个薄 `content` 对象，
**不落 entities.nbt**（文件通道只要整份 `nbt`）。摘要由 `vision/DecorativeSummary.java` 在**采集帧内、
实体引用在握时**从实体 API 直读构建（版本稳定、避免后置 CODEC 解码），产物是一个小 `CompoundTag`，
随 `EntityLightSnapshot` 透传到 VisionApi，用现有 `nbtToJson` 转 JSON。**这是采集端唯一一处按类型解释的地方**。

| 类型 | content 结构（JSON） | 取值 |
|---|---|---|
| item_frame / glow_item_frame | `"content": {"item": {"id","count"}}` | 框内物品；空框省略 `item` |
| armor_stand | `"content": {"equipment": {"<slot>": {"id","count"}, …}}` | 仅非空槽（mainhand/offhand/head/chest/legs/feet） |
| mannequin | `"content": {"profile": "<名字>", …}` | 皮肤名；若其持/穿槽可用则与盔甲架同法（实施核验） |
| item_display | `"content": {"item": {"id","count"}, "mode": "<ItemDisplayContext>"}` | 展示物 + 展示姿势 |
| block_display | `"content": {"blockId": "<方块 id>"}` | 展示的方块 |
| text_display | `"content": {"text": "<纯文本>"}` | `Component.getString()` 去样式文本 |
| painting | `"content": {"art": "<画作 id>"}` | 画作（实施核验具体读法） |

示例（item_frame，挂钻石剑）：

```jsonc
{ "uuid": "…", "type": "minecraft:item_frame", "pos": […], …,
  "content": { "item": { "id": "minecraft:diamond_sword", "count": 1 } } }
```

代价：采集帧内对可见 allowlist 实体多做一次很小的一次性读取（一次快照通常个位数这类实体）。
这样 agent 一次 `vision/snapshot` 就能看到"哪个展示位上是把钻石剑"，要细节（附魔、components、姿态全套）
再走 Tier-2 `vision/entity?uuid=`。

## 7. 记忆端改动（EntityRestorer）

### 7.1 读取

`parseBucket`：新可选键 `KEY_NBT = "nbt"`（`entry.contains(KEY_NBT) ? entry.getCompoundOrEmpty(KEY_NBT) : null`）
 → `EntitySnapshot` 记录加 `CompoundTag nbt` 字段，并纳入 `fingerprint()`。

### 7.2 放置（spawn）：条目带 nbt → 整份装载

```java
Entity entity = null;
if (es.nbt() != null) {
    try (var reporter = new ProblemReporter.ScopedCollector("…", LOGGER)) {
        ValueInput in = TagValueInput.create(reporter, level.registryAccess(), es.nbt());
        entity = EntityType.create(in, level, EntitySpawnReason.LOAD).orElse(null);
    }
}
if (entity == null) { …现有 type.create + snapTo 路径（载荷缺失/装载失败的回退）… }
entity.setUUID(uuid);                       // 与快照键对齐（载荷 UUID 同源，双保险）
freeze(entity);                              // NoGravity/Invulnerable/零速/NoAI/FROZEN，与现状一致
level.addFreshEntity(entity);
```

关键点：
- **不 snapTo**：位置/朝向由载荷内置 `Pos/Rotation` 给出（锚定/挂墙实体取整与朝向天然正确，避开现在
  `type.create + snapTo` 对挂壁实体的空壳/错向问题）；
- 装载失败的兜底 = 现有路径（退化成今天的样子，不丢实体、不崩）；
- 装载走 vanilla 装载入口 `EntityType.create(ValueInput, level, reason)` + `TagValueInput`（1.21.11 已核实）。

### 7.3 移动/内容变更（move / sync）

为每个已放置实体记"上次应用过的载荷" `appliedPayloadByDim: 维度 → uuid → CompoundTag`（onServerStart 清空）。
sync 循环里对已存在实体：
- 新载荷 ≠ 上次应用载荷（`Objects.equals`，树比较）→ **整实体重建**：`discard` 旧的 + 用 §7.2 从新载荷
  重生（同 uuid）——内容变了就换一份，不做逐字段 apply（避免重写 vanilla 字段逻辑）；
- 载荷相等但轻量 pos 变了 → 走现有 `teleportTo`（实体真的被挪动了）；
- 其余 → 不动。

**为什么整表粒度不用改**：现有"内容指纹变了才 sync"的桶级门控（`appliedFingerprintByDim`）已含 payload
（EntitySnapshot.fingerprint/toString 会带 `nbt`）——内容变化天然触发 sync，只差对**已存在** uuid 判"该重建"
 这一处（§7.3 新增）。

### 7.4 旧文件"空壳变有内容"的过渡

旧快照里某框是默认态空壳（appliedPayload=null）；新采集帧里它被看到 → 文件条目带 `nbt` →
桶指纹变 → sync → §7.3 判定 new≠applied(null) → 重建为带内容的框。无需 resetOnLaunch。

## 8. 正确性 / 成本论证

1. **内容正确性 = vanilla 自身 round-trip**：采集侧 `saveWithoutId`（+`id`）→ 记忆侧 `EntityType.create`
   装载，正是分块存档"存/读实体"的同一条对称路径；键名/编解码任何变化都由 vanilla 兜底，我们的代码零解释。
2. **采集成本**：载荷 + 薄摘要只在"可见 × allowlist × 有采集请求"时计算一次/实体/帧（mixin 内已持有引用，
   无二次查找；可见性去重由现有 seen 集保证）。展示实体 NBT 通常 ≤ 数百 B–2 KB；采集本就是 agent 主动
   低频触发（snapshot/resolve 驱动），且限定 allowlist → 总量有界，不触碰"每 tick 全量"。
3. **确定性/去抖**：`saveWithoutId` 输出对同一状态确定（键序固定、无时间戳/tick 计数入档——display 的
   `start_interpolation` 等运行时计数不入档，已核实），内容未变 → 载荷字节不变 → 桶指纹不变 → 不 sync、不重建。
4. **与删除语义正交**：DeletionApplier/纯累积语义只消费轻量物理与几何，载荷只是把"内容"带进已放置实体，
   不改变放置/删除时机。§7.3 重建也走现有 discard + addFreshEntity，不额外引入删除。

## 9. 已知限制

1. **只在"再被看到"时刷新内容**：现实里框里的物品被换了，但记忆端没再采集到它 → 记忆保留上次可见内容
   （与纯累积语义一致，是"记忆"而非"实时镜像"的既定边界）。JSON 薄摘要同理只代表"采集到的那一刻"。
2. **静态装饰的移除仍受几何删除约束**：挂在墙上的框/画占据格含墙块（非"已证空"）→ 现实移除后记忆端
   ghost 会留下（现有通用限制，非本轮引入；§2 说过的"记忆中最后一个可见位子"直觉成立）。
3. **冻结 = 时间静止**：display 的变换插值动画、框内物品自动旋转等播放类表现不随时间走（静态参照物）。
4. **不可见即不采集**：`Invisible/Marker` 盔甲架在真实世界渲染被 cull → 一般不会入快照（更不会带 payload），
   与"只有被看到的内容才进记忆"一致。
5. **装载失败会静默退回默认态**（§7.2）：例如条目引用了真实世界才有的注册表 id 而在记忆端缺失时，退化为
   今天的空壳——不崩、可自愈（下帧再采到即重建）。
