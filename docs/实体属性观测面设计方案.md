## 1. 问题：生物与玩家在两侧都是空白

v2.40 收紧了观察边界（`vision/entity` 改读落盘 store、掉落物 `item` 补 `enchanted`）之后，剩下的是**反向的缺口**：

| 对象 | `snapshot.entities[]` | 记忆世界复原结果 |
|---|---|---|
| 僵尸 / 村民 / 铁傀儡… | 8 个物理态字段（id/uuid/type/pos/rotation/motion/onGround/health） | `type.create(level, LOAD)` 的**默认空白实体** |
| 另一个玩家 | 同上 | **建不出来**（`EntityType.PLAYER` = `createNothing`，见 §7.1） |

而现实中肉眼可见的东西一样都没有：**僵尸身上那套钻石甲、手里那把附魔剑、名字牌、幼年体型、药水粒子、姿态、着火**——全都不可得。

`f3` 能读到一部分，但它受**触及距离 3 格**限制（`GameRenderer.pick` → `LocalPlayer.raycastHitResult` → `entityInteractionRange`），只能贴脸查，且不落盘、没进 `snapshot`。**所以它不能作为 agent 的批量感知手段。**

本方案补上这 7 个属性，并同时决定它们的**落盘与复原**。

---

## 2. 原则：一份来源，两个消费者，两种厚度

沿用 v2.34/v2.35 已验证的形态，并把它明确成通则：

```
活体实体（采集帧，渲染线程）
      │
      ├─► 复原口径（全量）──► entities.nbt 的 living 键 ──► 记忆侧 EntityRestorer 复原
      │
      └─► 可见口径（薄）  ──► snapshot JSON 的实体级键   ──► agent 感知
```

**读取面 = 落盘数据的可见子集。** 这条对偶解释了全部既有现状：

| 对象 | 落盘（复原口径） | 读取面（可见口径） |
|---|---|---|
| 掉落物 | `KEY_ITEM` 整份 `ItemStack.CODEC` tag | `item: {id, count, enchanted?}`（判据 A） |
| 展示实体 | `KEY_NBT` 整份可装载 payload | `content` 薄摘要 |
| **生物/玩家（本方案）** | **`KEY_LIVING` 全量** | **7 个薄字段** |

**两侧厚度不同的理由是不同的问题，不是妥协：**
- 读取面要**薄** —— 观察边界：agent 只能"看到"；
- 落盘要**全量** —— 复原保真：少一个组件就复原出错误的外观（"没附魔的同款甲"= 镜像里的**假事实**）。

而落盘厚一点**不构成越界**，因为已立规则：**落盘保真 ≠ 读取面可读，边界只在读取面执行，store 永远不是读取面。**

## 3. 读取面：7 个属性的定义

全部仅对 `LivingEntity` 生效（`ArmorStand` 也是 `LivingEntity`，见 §8.2）。平铺为实体级键。

| JSON 键 | 形状 | 出现条件 | 判据（javadoc 须写明） |
|---|---|---|---|
| `equipment` | `{ "<slot>": {id, count?, enchanted?} }` | 该槽非空才出现；整组为空 ⇒ **无该键** | 槽 = `EquipmentSlot.VALUES` 全 8 个（`mainhand`/`offhand`/`feet`/`legs`/`chest`/`head`/`body`/`saddle`），键名取 `slot.getName()`；`enchanted` = `stack.isEnchanted()`（判据 A） |
| `name` | String | 仅 **`entity.shouldShowName()`** | `Entity.shouldShowName()` = `isCustomNameVisible()`；`Player` 覆写为恒 `true`。**这正是名字牌的渲染判据**（`EntityRenderer.shouldShowName`），所以它字面上就是"肉眼看不看得见" |
| `effects` | `["minecraft:speed", …]` | 非空才出现 | 来自 **集成服务器**（v2.42，§12）；只给**种类**不给持续/等级；**过滤 `isVisible()`**（没有粒子的效果看不见）。连真实服务器时**恒缺席**——那意味着"未知"，由顶层 `effectsSource` 区分 |
| `baby` | `true` | 仅 `isBaby()` 为真 | `LivingEntity.isBaby()`（基类恒 `false`；`AgeableMob`/`Zombie`/`Piglin`/`Zoglin`/`Frog` 等覆写）。"属性存在" = 该接口对所有 `LivingEntity` 可读 |
| `maxHealth` | float | 恒有（`LivingEntity`） | `getMaxHealth()`。与既有 `health` 配套，agent 才能算"残血比例" |
| `pose` | String | **恒写** | `entity.getPose().getSerializedName()`（枚举 18 值）。已拍板恒写：与 `baby`/`onFire` 的"缺省即常态"相反——`pose` 有 18 个值，"缺省"反而是少数，恒写让 agent 无需知道缺省值是什么 |
| `onFire` | `true` | 仅真时 | **`entity.displayFireAnimation()`** = `isOnFire() && !isSpectator()` —— 火焰渲染用的就是它 |

**既有字段不变**：`health` 仍是当前生命值（超观测例外，见 §8.4）。

### 3.1 与 `f3` 的关系（已拍板：不改 `f3`）

| | `f3` | 本方案 |
|---|---|---|
| `name` | `getName()` **恒给** | 仅 `shouldShowName()` —— 比 `f3` **更严**（没插名字牌的生物，游戏里确实看不到名字，`f3` 那侧是超观测） |
| `equipment` | `{slot: {id, enchanted}}`，`enchanted` 恒在的 boolean，**无 `count`** | `{slot: {id, count?, enchanted?}}`，`count` 仅 >1、`enchanted` 仅 true（与 `content.equipment` 一致） |

⇒ **两套形状并存**是已拍板的取舍；本文档记为**已知不一致**（§9.2），不在本方案内统一。

### 3.2 实施中发现：`effects` 在客户端**根本没有数据源**（待重新拍板）

§3 表原写「`getActiveEffects()` 不过滤 `isVisible()`」。实施时核实**同步链路**，结论是该调用在观测端（客户端）对**除本地玩家以外的任何实体**都返回**空集**：

| 事实 | 证据 |
|---|---|
| 效果**不会**随实体进入视野而同步 | `ServerEntity.sendPairingData`（玩家开始追踪实体时下发）只发 add-entity / entity-data / attributes / **equipment** / passengers / leash，**无 effect**（`ServerEntity.java:272~315`） |
| 效果**不会**随变化同步给旁观者 | 全源码只有 3 处发 `ClientboundUpdateMobEffectPacket`：`ServerPlayer:1643,1655`（**本机玩家自己**）、`LivingEntity:1069`（**仅乘客**——`sendEffectToPassengers`）、`PlayerList:461`（`startRiding` 时给乘客）。**没有任何一处发给"追踪该实体的其它客户端"** |
| 客户端唯一的其它来源也没有 | 客户端 `activeEffects` 的写入只有 `handleUpdateMobEffect`（上面那个包）与 `readAdditionalSaveData`（网络实体不走 NBT 加载）⇒ 旁观者侧恒为空 |
| vanilla 实际同步的是**粒子**而非效果 | `LivingEntity.updateSynchronizedMobEffectParticles()`（`:883`）把 `activeEffects.values().filter(isVisible)` **map 成 `ParticleOptions`**（丢掉 id/等级/时长）后写进 SynchedEntityData 的 `DATA_EFFECT_PARTICLES`；客户端仅凭它**喷粒子**（`:852-860`），不重建效果对象 |

**两个推论：**

1. **这不是边界问题，是链路上根本没有。** 与 §8.3 的「生物背包 / 交易表 / 玩家背包」同类：客户端**没有数据源**，写多少代码都读不出来。既有的 `f3` 也一样——`F3Api:199-201` 的 `target.entity.effects` 对**远程实体恒为空列表**（只是没人注意到）。所以「与 `f3` 一致」这条理由本身不成立。
2. **vanilla 的同步格式本身就是"边界合规"的**：它只把「能看到几团什么颜色的粒子」发出去，**刻意不发**「是什么效果」——这正是观察边界要的形状。反过来说，「效果**种类**」既不在链路上、也不符合「看到」级。

**若要保留这个属性**，唯一可行的客户端数据源是 SynchedEntityData 的 `DATA_EFFECT_PARTICLES`（`private`，需新加 `@Accessor` mixin），但它只能给出**粒子颜色**（`ParticleOptions`），**无法反推效果 id** ⇒ 满足不了"药水效果**种类**"这个原始需求。

**已拍板（2026-09-19）：保留全部实现（读取面键 / 落盘键 / 复原路径都在），只把「获取」那一段置空**——采集端 `LivingSummary.collectEffects(LivingEntity)` 是唯一的取数点，当前恒返回 `List.of()`，源头解决时只改这一个方法。理由：调用 `getActiveEffects()` 只会读出一个恒空的集合，看起来"实现了"却永远不生效，后续维护者会误以为这条路是通的。

**当前实际效果（必须如实记录）**：`effects` 键在 `snapshot.entities[]` 里**不会出现**，`living.effects` **不会写盘**，记忆侧 `applyLiving` 因此每次都执行 `removeAllEffects()`（对新建实体是空操作）。"缺省即常态"这个通则在这里暂时**不成立**——缺省意味着"未知"而非"无效果"，待源头解决后一并恢复。§8.1/§8.4 里"不过滤 `isVisible()`"那条拍板随之**悬空**（链路给的本来就是过滤后的粒子）。

**其余 6 个属性的链路均已核实可用**（供对照）：`equipment` ← `ClientboundSetEquipmentPacket`（配对时全量 + `detectEquipmentUpdates` 变化时）；`name` ← `DATA_CUSTOM_NAME`/`DATA_CUSTOM_NAME_VISIBLE`；`baby` ← `DATA_BABY_ID`；`maxHealth` ← `ClientboundUpdateAttributesPacket`；`pose` ← `DATA_POSE`；`onFire` ← 共享标志位 0。**全是 SynchedEntityData 或配对包**，与 `effects` 的区别就在于此。

**后续（2026-09-19，见 §12）**：上面 101 行那句「唯一可行的**客户端**数据源」在**协议层**仍然成立——链路上确实没有。但还有一条不走协议的路：单机 / 自己是局域网主机时，**服务端权威数据就在同一个 JVM 里**（集成服务器）。**已拍板并实施**，方案见 **§12（v2.42）**。本节记录的是"v2.41 为什么当时置空"，不再代表最终状态；上面那段的"当前实际效果"同样只描述 v2.41 当时。

## 4. 落盘：`entities.nbt` 新增 `living` 键

每个实体条目新增**一个**复合键（与 `nbt`/`item` 同构，不散成 7 个键）：

```nbt
"<uuid>": {
  ...既有 8 字段...,
  "living": {
    "equipment": { "mainhand": {…ItemStack.CODEC…}, "head": {…} },   // 仅非空槽
    "customName": {…ComponentSerialization…},                         // 仅 hasCustomName() 时
    "customNameVisible": 1b,
    "effects": [ {…MobEffectInstance.CODEC…}, … ],                    // 仅非空时
    "baby": 1b,                                                        // 仅 true 时
    "pose": "crouching",                                               // 仅非 standing 时
    "onFire": 1b                                                       // 仅 true 时
  }
}
```

**键的存在性 = "是不是活体"（实施时的补正）。** 子键遵循"缺省即常态"只写非缺省值，但 `living` 键本身对每个 `LivingEntity` **恒写**（空时为 `{}`，不是省键）。理由是**区分"属性从有变无"与"本来就没有"**：若空即省键，那么"药水效果过期 / 装备被拿走 / 火灭了"（tag 变空）在文件里与"这个生物本来就什么都没有"长得完全一样，记忆侧无从区分 ⇒ 此前应用过的属性会永远留在镜像里，成为**假事实**。多花的是一个空 compound（约 4~8 字节/实体/帧），换来的是"缺省值"这件事本身可判定。

### 4.1 厚度取舍

| 子键 | 厚度 | 为什么 |
|---|---|---|
| `equipment` | **整份 `ItemStack.CODEC` tag**（与 `KEY_ITEM` 同路径） | 落薄摘要 ⇒ 复原出"同款但无附魔"的甲：外观少光效，且镜像里写下"这僵尸拿着把普通钻石剑"这个**假事实** |
| `customName` | **Component tag**（不是纯文本） | 名字的颜色/格式也是可见的；纯文本会丢掉它们。**注意不是 `getName()`** —— 对没自定义名的生物，`getName()` 返回类型描述（"Zombie"），落它会让复原体凭空长出名字牌 |
| `customNameVisible` | bool | 与上者配对，决定名字牌是否渲染 |
| `effects` | **完整 `MobEffectInstance` tag** | 复原需要 id + 等级 + 时长 + 隐藏标志 |
| `baby` | bool | **碰撞盒尺寸**——不仅外观，还经 `MemoryCellReporter` 的实体 AABB 占用格进入 `memory_cells.bin` 反向通道 |
| `pose` | String | 姿态影响渲染 |
| `onFire` | bool | 火焰外观 |

**不落盘**：`maxHealth`（重建实体时属性表自动给出，无复原价值）、读取面的 `name`（落盘用 `customName` 口径，见上）。

**应用侧配套：全量对齐语义。** `applyLiving` 是"把实体置成 tag 描述的样子"，故每个子键**缺席即回到缺省**（姿态回 `standing`、火灭、名字清空、效果清空、无记录的槽位清空）。若只在有值时设置，"火灭了"这个事实就永远传不过来。这条与上面"键恒写"是同一枚硬币的两面。

### 4.2 编码成本（唯一需要实测的风险）

`LevelRendererMixin` 的编码是**每帧**执行的（不是只在 `vision/snapshot` 请求时），见 §9.5。缓解：**只编码非空槽**（绝大多数生物只有 1~2 槽非空）。若 `ItemStack.CODEC` 编码成为瓶颈，再加"按内容缓存上次编码结果"。

## 5. 记忆侧复原

### 5.1 前提：冻结实体不 tick

`EntityRestorer.freeze()` 经 `FROZEN` 集合在 **`ServerLevelMixin.tickNonPassenger` 分发层取消 tick**（§7.9 陷阱②）。因此：

- 药水效果**不倒计时** → 落盘全量效果后一次应用即永久保持，无需管过期；
- `remainingFireTicks` **不递减** → 着火状态不会自己熄灭；
- 姿态不会被 vanilla 逻辑改回去。

**这是"落盘全量 + 一次应用"能成立的前提。** 若哪天冻结语义改成"仍 tick"，本节全部结论需重审。

### 5.2 应用点

| 时机 | 做什么 |
|---|---|
| 新建 / 重建（`construct()` 内，紧跟 `setHealth`） | `applyLiving(entity, living, registryAccess)` 全量应用 |
| 已存在实体（`sync()` 的 `move` 分支） | `livingChanged(es, appliedLiving)`（即 `!Objects.equals(es.living(), appliedLiving)`）→ **就地重应用**（不重建实体）。装备换一次只走 setter，不 discard+recreate |
| payload 变化 | 保持既有的整份重建语义不变 |

「恒写 `living` 键」在这里兑现：属性**从有变无**时，新 `living` 是空 compound（≠ 旧记录）⇒ 同样触发重应用 ⇒ 全量对齐把旧属性清掉。若空即省键，这条路径根本不会触发。

`EntitySnapshot` 新增一个 `CompoundTag living` 字段后，`EntityData.fingerprint()`（= records 的 `toString()`）**自动**把它纳入内容指纹 ⇒ 文件里 living 变了必然触发一次 `sync()`，不会漏。但**不要**把它并进 `payloadChanged`——那会让姿态/着火这类快变状态触发整份重建。

### 5.3 逐字段应用方式

| 子键 | 复原调用 | 备注 |
|---|---|---|
| `equipment` | `livingEntity.setItemSlot(EquipmentSlot.byName(slot), stack)` | `EquipmentSlot.byName(String)` 存在；栈用 `parseItemStack`（现成，同 `KEY_ITEM`） |
| `customName` / `customNameVisible` | Component codec 解码 → `setCustomName(...)` + `setCustomNameVisible(...)` | 解码用 `registries.createSerializationContext(NbtOps.INSTANCE)`，与 `DecorativeSummary` 同款 |
| `effects` | `MobEffectInstance.CODEC.listOf()` 解码 → 逐个 `addEffect(instance)` | 与 vanilla `active_effects` 存档格式一致 |
| `baby` | **instanceof 阶梯**：`AgeableMob` / `Zombie` / `Piglin` / `Zoglin` / `Frog` / `Sniffer` → `setBaby(b)`；`ArmorStand` → `setSmall(b)`；其余跳过（debug 日志一次） | ⚠️ **`Mob.setBaby` 是空实现**（`Mob.java:1297-1298`），**不能用**它兜底——它会让"以为设上了"的静默失败 |
| `pose` | `StringRepresentable.fromEnum(Pose::values).byName(s)` → `entity.setPose(pose)` | 解析失败 → 跳过 |
| `onFire` | `entity.setSharedFlagOnFire(true)` | 直接设 synched 标志（`Entity.java:555`），不依赖 tick 递减 |

## 6. 透传链

新增**两个** `CompoundTag` 字段，与既有 `payload`/`content` 完全同构（因为它们就是同一件事的第三、第四份）：

| 字段 | 口径 | 消费者 |
|---|---|---|
| `living` | 复原（全量 tag） | `VisionEntityStore.sync` → `entities.nbt` |
| `livingView` | 可见（薄摘要） | `VisionApi.snapshot` → JSON 实体级键 |

沿五层各加这两个字段（照抄 `content` 的搬运路径）：

```
LevelRendererMixin（编码，渲染线程）
  → DepthCapture.EntitySnapshotData（+2）
  → ObjectResolver.addEntity（透传）
  → VisionCollector.EntityLightSnapshot（+2）
  → { VisionEntityStore.sync（写 living）, VisionApi.snapshot（展平 livingView） }
```

**为什么是两个字段而不是"一个全量 tag + 读取时投影"**：沿用 `payload`/`content` 的双口径先例；投影在编码端一次完成，避免在 API 层再写一遍解码逻辑。薄口径的实现建议抽成一个 `LivingSummary` 工具类（与 `DecorativeSummary` 对称），`enchanted` 复用 `DecorativeSummary.isEnchanted`。

## 9. 已知取舍与风险

### 9.1 玩家：落盘了也复原不了
`EntityType.PLAYER` = `createNothing`（工厂返回 null）+ `noSave`，因此记忆世界**永远建不出玩家实体**，玩家的 `living` 是**死数据**。仍照常落盘，理由是**保持两个读取面一致**（`vision/entity` 读的就是 store 条目）。

### 9.2 `equipment` 形状与 `f3` 不一致（已拍板不改）
见 §3.1。两套形状并存，记为已知不一致。

### 9.3 堆叠数是一处既有松动
手持物/掉落物的**堆叠数**在游戏里不可辨（渲染成单个模型、不显示数字）。`count` 是 v2.34 已拍板的松动，本方案为一致性沿用。若将来收紧，应两处一起去掉。

### 9.4 瞬态状态在记忆世界里"永久保持"
因为冻结不 tick（§5.1），落盘的 `onFire`/`pose` 会一直保持，与现实中"8 秒后熄灭"不同。**这不是错误**：记忆世界是**快照式镜像**，下一次采集（火已灭）会整体覆写该维桶并触发重应用，自动修正。

### 9.5 每帧编码成本
见 §4.2。这是本方案唯一需要实测的风险点。

## 12. v2.42：药水效果数据源（集成服务器路线）

> §3.2 判定 `effects` 在客户端没有数据源，于是置空占位。本节补上数据源。
> **结论：走"集成服务器"路线——单机 / 自己是局域网主机时，服务端权威数据就在同一个 JVM 里。**

### 12.1 数据源

单机存档（以及"对局域网开放"且自己是房主）时，客户端进程里**同时**跑着一个集成服务器：

```java
mc.hasSingleplayerServer()   // true
mc.getSingleplayerServer()   // → ServerLevel.getEntity(uuid) → 权威实体，getActiveEffects() 是真全量
```

连真实服务器时 `getSingleplayerServer()` 返回 null，客户端手上的效果数据仍然是 §3.2 那个空集。

### 12.2 为什么必须"采样"而不能直接读（证据）

`LivingEntity.getActiveEffects()` **返回的是活视图，不是拷贝**：

```java
// LivingEntity.java:972-974
public Collection<MobEffectInstance> getActiveEffects() {
   return this.activeEffects.values();      // ← values() 视图，背后是同一个 HashMap
}
```

采集跑在**渲染线程**，集成服务器跑在自己的 **tick 线程**。服务端 `addEffect`/`removeEffect` 改的正是那个 map ⇒ 渲染线程直接迭代 = `ConcurrentModificationException` 或撕裂读。**必须跨线程交付，不能跨线程查询。**

> 注：`F3Api:56` 已经在用 `getSingleplayerServer()`，但它只取统计量（`gatherChunkSourceStats()`），**没有遍历任何可变集合**，所以它没踩这个坑。这不能当作"直读没问题"的先例。

### 12.3 交付管线：每 tick 采样 → 不可变信箱 → 渲染线程读

```
服务端 tick 线程                          │  渲染线程（采集帧）
─────────────────────────────────────────┼──────────────────────────────
ServerTickEvents.END_SERVER_TICK          │  LevelRendererMixin
  └ 遍历 server.getAllLevels()            │    └ LivingSummary.collectEffects(living)
      └ level.getAllEntities()            │        └ EffectSampler.sample(living.getUUID())
          └ instanceof LivingEntity       │                 ← 只读不可变数据，零竞态
             且 getActiveEffects() 非空    │
             → 深拷贝成不可变样本           │
  一次性 publish 整份新 map（volatile）     │
```

- **密钥 = 实体 UUID**（全局唯一，无需维度键）。
- **只发布有效果的实体**：绝大多数实体没有效果，空实体不占条目 ⇒ 常规每 tick 分配接近零。
- **深拷贝是硬要求**，且不能用 `new MobEffectInstance(copy)`：
  ```java
  // MobEffectInstance.java:88-91    拷贝构造只搬 effect 引用 + 5 个标量
  public MobEffectInstance(final MobEffectInstance copy) {
     this.effect = copy.effect;
     this.setDetailsFrom(copy);        // ← setDetailsFrom 只写 duration/amplifier/ambient/visible/showIcon
  }                                    //   (:121-127) —— hiddenEffect 被整个漏掉，仍是活引用
  ```
  ⇒ 样本用**自定义不可变 record**（`EffectSampler.EffectSample`），采集帧再重建 `MobEffectInstance` 交给 `MobEffectInstance.CODEC` 编码。
- **实施补正：`hiddenEffect` 刻意不带**（原设计写的是"递归带上 hiddenEffect 链"，**做不到**）：该字段是 `private` 且**没有 getter**（`MobEffectInstance.java:45`），读不出来。丢弃它在**本系统里无后果**——它只是 vanilla 的"同种效果被更强的顶替时把旧的存起来、等新的到期再恢复"记账（`:140-142` / `:256-266`），而记忆侧实体一律**冻结不 tick**（§5.1）⇒ 持续时间不倒计时 ⇒ 永远走不到那一步。**有据的取舍，不是遗漏。**
- **生命周期**：`ServerLifecycleEvents.SERVER_STOPPED` → 清空信箱并标记不可用。**必须有**，否则"玩完单机 → 退出 → 连服务器"会继续读到上一个世界的陈旧数据。
