## 一、目标功能

> 每条目标按 **目标 / 为什么 / 设计约束 / 验收标准 / 待定** 记录。
> 编号 `G1`、`G2`…… 与 §二的决策编号 `D1`、`D2`…… 平行，互相引用。

### G1. 执行观察窗口

**目标**

一个独立的 GUI 窗口，以树的形式实时呈现**当前全局反射树**与**当前任务树**的执行情况。

- 树的呈现顺序：**从上到下**，根在顶端，子节点缩进排列。
- **每个节点的 children 可折叠 / 展开。**

**为什么**

行为树由大模型生成（惰性展开），出问题时无法靠读代码定位——必须能看见"它当时在想什么"。具体要能回答三类问题：

1. 树跑到了哪个节点？为什么走这条分支而不是那条？
2. 快树为什么**没有**抢占？或者抢占了，但为什么没解决？
3. 快树**命中了哪个 arm**、返回了什么，从而触发了升级？

**设计约束**

*数据来源*

- **C1. 执行器必须暴露内省接口。** 这是本目标对系统的硬性要求，当前节点设计里没有。执行器要能在任意时刻以 O(活跃节点数) 的成本导出状态快照。快照分两层：

  | 层 | 内容 | 更新时机 |
  |---|---|---|
  | **静态结构** | `id` / `type` / `name` / `cmd` / children 结构 | 树生成、或展开替换子树时推一次 |
  | **动态状态** | 返回码 / 是否活跃 / 游标位置 / 重试计数 / 冷却剩余 | 变化时推增量 |

  分层的意义：结构只在展开时变，状态每 tick 都变。**只推状态增量（`{id, status}`），不要每 tick 推整棵树**——tick 可能 20Hz，树可能上百节点。

- **C2. 变化时推送，不用轮询。** 另加低频心跳（约 1s）兜底，防止丢包导致面板展示过期状态。
- **C3. 内省不得拖慢 tick。** 读快照必须是廉价读取，不能在 tick 线程上加锁或做同步序列化。

*呈现*

- **C4. 默认只展开活跃路径。** 一棵上百节点的树全展开无法阅读。默认展开「根 → 当前 `RUNNING` 叶子」这条路径，其余折叠。
- **C5. 折叠状态要跨状态更新保留。** 依赖 §8.3 的稳定 `id`。子树被展开替换时，未受影响节点的折叠状态不应重置——否则每次展开用户的视图都被冲掉。
- **C6. 升级信号需要独立的视觉标识。** 触发升级的不是某个返回码，而是「**命中真实 arm + 返回 `FAILURE`**」（D2 / D10）。面板必须把这两件事并排显示出来——只显示返回码的话，"无反射适用"（`otherwise` + 成功）和"有反射但解决不了"（真实 arm + `FAILURE`）看起来会一模一样。

*缺口*

- **C7. 抢占是"过程"，树只能显示"状态"。** 抢占、恢复、展开这三个关键事件在树上看不出来。需要一条**事件流**与树并列，至少记录：
  - 快树在 t 时刻抢占，任务树被打断于路径 X
  - 情节结束后 D3 判为哪一档（无效化 / 位移 / 无影响），以及依据
  - 哪个 `PendingExpansion` 被触发，展开耗时多久

*实现位置*

- **C8. 做成 harness 的 client plugin**，注册进 slot 系统（`dsh-client-ui-slots`），面板放在右侧边栏（`dsh-client-ui-sidebar-right`）或 dock 区（`dsh-client-ui-dockkit`）。现有 `ui-trajectory` / `ui-plan` / `ui-goal` 是同类面板的先例，可直接参考。
  **不要另起一个应用**——harness 已有这套机制，自建会重复实现布局、主题、插件生命周期。

**验收标准**

- [ ] 单一窗口内同时可见两棵树：反射树在上（小、常驻），任务树在下（大、可滚动）
- [ ] 每个节点显示类型、name、当前返回码；`Action` 额外显示 `cmd`
- [ ] 节点返回码变化后，面板更新延迟 < 200ms
- [ ] 每个 composite 节点的 children 可折叠 / 展开，且折叠状态在状态更新时不丢失
- [ ] 当前活跃路径（根 → `RUNNING` 叶子）一眼可辨
- [ ] 被抢占后，事件流中能看到被打断的路径，以及 D3 判成了哪一档
- [ ] 面板开启时，tick 频率下降 < 5%

**待定**

- **G1-a. 受众。** 给**开发者调试**用（显示返回码、耗时、被抢占路径等全部细节），还是给**使用者**看（显示"正在挖金矿"这类人话）？当前按开发者调试设计——树是大模型生成的，这个窗口的主要用途是调试生成的树。
- **G1-b. 时间维度。** 只显示当前状态，还是需要一条可回放的时间线？当前只做当前状态，C7 的事件流是折中方案。

## 二、决策记录：行为树双层执行模型

> 本节记录"快树 / 慢树"双层执行模型的决策。讨论于 2026-10-04。
> **已定** = 双方明确认可，可直接实施；**待定** = 尚未收敛，不要当成定论。

### 2.1 模型概述

每个行为由两层组成：

- **快树**：应对突发状态（野外遭遇怪物等），执行过程**不调用大模型**，大模型只在离线优化时介入。
- **慢树**：处理复杂任务，需要长思考与详细规划，由大模型驱动。

执行模型：周期性进入快树判断触发条件；条件成立则执行快树、中止慢树；快树情节结束后，判断慢树任务是否受影响，决定重规划还是继续。

### 2.2 已定决策

#### D1. 快树全局唯一，不按任务拆分

只有两棵树，不是"每个任务各配一对"：

- **全局反射树**（常驻，与任务无关）：自保、脱困、避怪、溺水、着火、卡住
- **当前任务树**（同时只有一棵活着）

任务**特有**的中止条件（如"背包满则中止采集"、"工具耐久 < 10 则中止"）属于任务树自己的分支，不属于全局反射树。

**理由**：任务无关的反射若按任务各写一份，"躲苦力怕"会被写 N 遍然后各自漂移，改一处漏 N-1 处。全局快树也不能知道所有任务的节点类型——那正是这条决策要避开耦合。

#### D2. 快树不产生新任务

加任务 = 重规划，是慢树的职责。快树只发一个信号：「我不认识这个局面」，由慢树决定加什么任务。

**理由**：快树若自己能加任务，它就从"预编译反射"退化成一个没有大模型、没有全局视野的 planner。

#### D3. 受影响判据分三档，只有一档需要大模型

快树情节结束后对慢树任务的判断：

| 情形 | 例子 | 处理 | 代价 |
|---|---|---|---|
| **无效化** | 要去的树被烧了 / 记忆中的箱子是空的 | 重规划 | 要 LLM |
| **位移** | 任务还成立，但怪把 agent 追出 50 格 | 重入当前节点 | 纯条件重检 |
| **无影响** | 挖矿时顺手砍死路过的僵尸，人还在矿脉上 | 继续 | 纯条件重检 |

**先做廉价的前提重检，只有前提重检失败才升级到大模型重规划。** 若每次被抢占都走一次大模型往返，快树省下的时间会被交接全部吃掉。

**【2026-10-06 修正适用范围】** 这条原则**对 §7.5 仍然成立**（任务树根失败先走本地三步廉价试探），但**对"抢占-恢复"不成立**——那里原本的"廉价前提重检"是求值被中断段的**后置 `Condition`**，而后置与那个段**无关**（理由见 D9），本地判不对。抢占-恢复因此改为直接交大模型，代价是每次情节结束一次往返；这条的成立现在取决于"情节结束"是低频事件，需实测确认。

~~一个相关推论：快树的"我没覆盖这个局面"应当建模成**显式的第三种返回码** `UNCOVERED`……~~

> **该推论已否决（2026-10-05）**，见 D10。问题出在快树用错了节点类型，不在返回码上。现在全局只有三个返回码，见 [行为树节点设计方案.md](行为树节点设计方案.md) §1.2.1。

#### D4. 不设 per-node 的 halt 语义字段

**不**给每个节点加"被抢占时是可冻结还是必须终止并释放"的标注。中止 = 中止当前叶子并重启，不做通用冻结。

**理由**：通用字段让几百个节点为 5 个节点的特例背负担。绝大多数动作的"中止"就是"停"，重启代价可忽略（重新寻路 10–100ms，方块破坏进度重置无所谓）。

**残留风险**：撤掉字段后，"哪些是特例"变成隐式知识。需要有机制保证"新加了一个用消耗品的动作但忘了写中止逻辑"这件事**响亮地失败**，否则是静默烧物品。

**接口形态**：慢树按 Sequence 语义，同时只有一个叶子处于 RUNNING，所以"中止当前所有原子动作"实际永远是"中止一个"——接口可收成 `abortCurrentLeaf()`。

#### D5. 回退只针对少数原子行为，`container/close` 作为主中止路径

不是所有原子动作都能回退。三种命运：

- **可回滚**：容器拖拽到一半 → 物品放回去、界面关掉
- **只能终止**：正在吃食物 → 停下来，那份食物没了
- **无法撤销**：村民交易已成交 → 只能接受

回退的推导依赖一个自反性质：**"拿起来"和"放回去"是同一个原语**。点击格子 A 拿起、点击格子 B 放下，若在两者之间被打断，读取第一个动作即可推出回退（再点 A 放回）。在此之前或之后中断则无需回退。

但该二分只对**单步**操作成立：一次搬 5 个物品（5 组拿放对）中途被打断，已搬过去 1~4 个，这是真实的部分进度，"回退"是撤销 N 步。多步场景由下面的主路径覆盖。

**主路径定为 `container/close`**（一次调用、总成功、产出慢树可观察的状态），逐项回退降级为"物品贵重且局势不急"时的优化。

**理由**：逐项回退是 N 次服务端往返，而一次往返可能就是几十到几百毫秒。苦力怕引信只有 1.5 秒——**回退本身可能比威胁还慢**。`container/close` 是一次调用，顺带解掉这个延迟问题。

#### D6. 中断后有一个自动判断步骤，与恢复合并

**中断流程的后半段是「自动判断 + 恢复」，判断是恢复的一部分，不是一个独立阶段。**

快树情节结束后，执行器不直接把控制权交回慢树，而是先自动收集一组事实，再据此恢复。

判断读三样东西：

1. **被打断的路径**（从根到叶的 `id` 链，见 [行为树节点设计方案.md](行为树节点设计方案.md) §6.5）
2. **中断前后世界的差异**——位置、背包、容器是否还开着、附近有没有新出现的掉落物 / 实体
3. **被打断的最小任务的前置 `Condition`**——它就是这个段的入场券

**【2026-10-06 修正】** 这三样事实现在是**交给大模型**的证据，不再是执行器本地推出结论的依据：D3 的三档结论（无效化 / 位移 / 无影响）由大模型产出，理由见 D9。

**为什么放在这里，而不是让中止动作往回报告**：原 D6 要求 `container/close` 回报 carried 的去向，但**关闭时客户端读不到服务端把 carried 放哪了**——客户端只是把 menu 换掉，从不处理 carried 的归置（见 §2.3①②）。与其让每个中止动作都负责往回报告，不如**中断后统一看一眼世界的现状**。

carried 掉在地上这件事，在这个视角下就是"附近多了一个掉落物实体"——**看得见**。所以不需要任何命令提供回执。

**好处**：

- 不依赖任何单个命令的回执，因此不受"命令是同步还是异步"的影响
- 对**所有**中断原因通用，不只是容器操作。着火、溺水、被怪打断，判断的是同一组事实

**已知的脆弱点**：掉落物存在有时限（约 5 分钟），且可能被别的实体捡走。所以自动判断有时效窗口，不能拖太久。

**待定**：判断读多少东西（完整 world-diff 的代价可能不小）、哪些变化算"显著"、以及代价超出预算时降级到什么。

#### D7. 慢树的输出形态：惰性展开（原 T2 前半，2026-10-04 定案）

大模型**不生成整棵树**，只展开**单个节点**——树是逐层长出来的，每次只回答"这个占位节点里应该是什么"。

展开流程（本决策的操作形态）：

1. 生成一份**目录式大纲**（只有层级与目标，没有具体动作）
2. 取出第一个未落实的节点，判断它是否还需要细分
3. 需要 → 为它生成一份子大纲，回到第 2 步
4. 不需要 → 为它写具体的命令段，该节点定型
5. 一个小任务完成后，再写下一个，依次类推

`PendingExpansion` 节点是这个流程在树上的表示（见 [行为树节点设计方案.md](行为树节点设计方案.md) §4.3）：它是"这里需要一棵子树，但我还不知道长什么样"的占位。

**理由**：整树生成要求大模型一次性产出上百个节点，提示词预算没有上界，且中间任何一处错都要整棵重来。惰性展开把单次生成的规模压到一个节点。

**已否决**：由大模型检索"能力胶囊"组装整棵高层树——见 §2.4。

#### D8. 最小任务子树的判据：读取点 = 分支点 = 边界（原 T2 后半，2026-10-04 定案）

**判据：一个子树是最小任务，当它内部不存在「读取世界状态」的操作。**

由此自然得到它无内部分支——这不是另一条要求，而是同一个事实的另一面。

**理由**：两次读取之间，执行器没有任何新信息。此时的分支只能凭空猜。分支必须发生在一个读取**之后**，由读到的东西决定走哪条路。

**推论（三者是同一个东西）**：

> **读取点 = 分支点 = 最小任务的边界。**

**形态**：一个最小任务夹在**两次观察之间**，头尾两次观察都**不属于**它——它们是 M 在父序列里的前后两个兄弟。（边界**可以缺失**：M 的前一个兄弟可能是另一个最小任务，M 也可能是父序列的最后一个孩子。见 D9。）

```
观察（M 的前置边界：M 的入场券）
  ↓
命令 命令 命令 …        ← M：无读取、无分支、确定性
  ↓
观察（下一个段的前置边界，不是 M 的毕业证）
```

**注意尾部的观察不是 M 的"后置断言"（2026-10-06 修正）。** 它被写出来是为了**下一个**段能跑，它描述的世界状态与 M 是否做成**没有必然关系**——同一棵树里，它可以是"背包还有空间""天还亮着"这类与 M 无关的条件。拿它判断"M 做完了吗"会**静默跳过未完成的段**，见 D9。

落到具体例子上：`[等待+开箱] → get → [两次点击] → get → [点按钮] → get → …`——**每一个 `get` 都是一次读取，也就是一个断点**，整段据此切成若干最小任务。

**边界粒度由大模型在展开时决定**，不是固定值：

- 读得太密 → 树退化成"读一次、点一下"的密集往返，每个往返几十到几百毫秒
- 读得太疏 → 一个节点里塞了太多无法验证的步骤，失败了也不知道错在哪一步

**已否决的判据**（记录以免重复论证）：**按命令数判定**——"这个节点能用注册表里的一条命令直接实现，就是最小任务"。太细：一段十几个命令的容器交互会被切成十几个节点外加一堆 `waitMs` 节点，树变成"带结构的扁平脚本"，深度增加了但语义没增加。**单条命令是最小任务的特例，不是它的定义。**

**相关**：命令段内部的时序由显式 `waitMs` 承担，见 [行为树节点设计方案.md](行为树节点设计方案.md) §9.3。

#### D9. 中断后的恢复：回溯到前置边界，交大模型判断（2026-10-06 改，原"三步判定"）

这是 D6 那个自动判断的**具体过程**，也是快树交还控制权的方式。

**记录什么**：中断时只记录一样——**被打断的最小任务的位置**（从根到它的 `id` 链）。前置边界就是 M 在父序列里的前一个兄弟，树里可查，不必记。

**不记**段内已执行到哪条命令（D4：不冻结）。

**恢复不是"从被打断的叶子继续"，而是回到边界重新判断。** 因为中止流程本身改了世界（[行为树节点设计方案.md](行为树节点设计方案.md) §6.3 第 3 步关了容器），段内已执行的命令有多少还成立，无从得知。

```
被打断在最小任务 M 的中途
   ↓
回溯到 M 的入口（游标归零到 M，§6.5.1）
   ↓
交大模型，附三样证据：
   · M 的定义（goal / inputs / outputs / 段内命令）
   · 前置 Condition 的求值结果
   · 中断前后世界的差异
   ↓
继续跑 M ／ 修补 M 或其后的计划 ／ 重规划
```

**原设计的第①步已废弃**：它求值 M 的**后置 `Condition`**，`SUCCESS` 就认为"段其实已做完"。这一步不成立——**`Condition` 的求值永远是对的，问题在于它描述的对象与 M 无关。**

| | 前置 Condition | 后置 Condition |
|---|---|---|
| 与 M 的关系 | M 的**必要条件**：不成立则 M 一定跑不动 | **既非必要也非充分** |
| 对"M 做完了吗"的信息量 | 能**否定** M | **零信息** |

**根因：写 `Condition` 的人是为它后面的东西写的。** 它是下一个兄弟的入场券，不是前一个兄弟的毕业证。上面 D8 那条修正——尾部观察不是 M 的"后置断言"——说的就是这件事。

```
Sequence "夜间作业"
  ├─ Condition "是白天"
  ├─ Sequence "露天挖矿"          ← M
  ├─ Condition "天还亮着"         ← 为下一步"继续露天作业"写的
  └─ …
```

中断后求值「天还亮着」→ `SUCCESS` → 旧① 判「露天挖矿已完成」→ **静默跳过**。天是否还亮，跟挖了几个矿毫无关系。

还有三条构造上的理由，让①连猜都猜不准：**M 是父序列的最后一个孩子**时后置根本不存在；**M 的父是 `Match` 的 arm 或 `Repeat` 的 body** 时"兄弟"不是序列步骤；**M 的左兄弟是另一个最小任务**时前置也不存在（此时没有便宜预筛，直接交大模型——方向保守，无害）。

**砍掉①的代价很小**：它原来的收益是"省掉一次没用的重跑"——纯优化，不是正确性检查。真正的代价只在含 `consumes` / `irreversible` 的段上（重跑一次 = 多消耗一次）。

**前置也不当门控，当证据**：前置不成立时答案未必是"重规划整棵树"，可能是"容器被中止流程关了，重开一下"。硬门控会把小补丁升级成整树重规划。反正这次大模型一定要被叫，把前置的求值结果作为输入交出去，成本一样，信息更多。

**原重试上限（上限 1）消失**：它是防「重跑 → 后置不成立 → 再重跑」的环。没有后置就没有环——重跑挂在树自己的返回码上，`FAILURE` 上传，接 §7.5。

**成本**：每次抢占恢复一次大模型往返，慢树停顿秒级。这不违反 D3——D3 的前提是"这个判断本地做得对"，而"被中断的段做到哪了"本地做不对，从来不在 D3 的适用范围内。成立的前提是**"情节结束"是低频事件**（只发生在命中真实 arm 且返回 `SUCCESS` 时），**这个频率需要实测确认**；其间快树照常每 tick 跑。

**「前置成立」不等于「重跑安全」**（这条与本次改动无关，仍然成立）：前置只说明**进入时**的假设成立，不说明段内每条命令的假设成立——段内没有读取（D8），那些假设**从未被验证过**。举例：最小任务是 `[slot2 拿起, slot0 放下]`，中断在中间。中止流程 close 时，服务端把 carried 还给背包或掉在地上（§2.3①）。slot 2 于是从「有铁锭」变成「空」。**若前置写的是「界面已开」，它会通过**，然后重跑去点空槽。

**已知的洞（待定，与本次改动无关）**：**重跑可能返回 `SUCCESS` 而什么也没做成。**

```
M = [slot2 拿起, slot0 放下]
中断在中间 → 中止流程 close 把 carried 还给背包 → slot2 变空
重跑：点空槽 → doClick 守卫 → SUCCESS（空操作）；点 slot0 → 同为空操作
M 返回 SUCCESS，一个铁锭都没搬。
```

原"静态防线：段内幂等"（标记复用 §6.4 已有的 `consumes` / `irreversible`）只保证**重跑不会把事情搞坏**，不保证**重跑能把事情做成**。容器点击大多幂等，恰恰因此看不出这个洞；旧①本来也堵不住它——它只在后置恰好相关时撞上。

**待定**：

- 幂等要求是**静态校验**（写树时非幂等就报错）还是**运行时告警**
- 交给大模型的世界证据里，"中断前后差异"的窗口**从中断那一刻才开始**，看不见 M 已经做到哪。要让它判断"M 是否已达成"，需另给一份**进入 M 之前的快照**（至少覆盖 M 的 `inputs` / `outputs` 涉及的部分）。加不加，等价于"接不接受偶尔白跑一次 M"。
- 恢复请求在飞行中时又被抢占：丢弃旧请求还是排队

（原待定项"前后两个 `Condition` 由执行器自动生成还是大模型写出"随第①步一起消失。）

#### D10. 快树是互斥分类，不是优先级选择（2026-10-05 定案）

**快树的根必须是 `Match`（互斥分类），不能是 `Selector`（优先级 / 备选方案）。**

起因是打算否决第四个返回码 `UNCOVERED` 时，推了一遍快树：

```
Selector (reactive) "反射根"
  ├─ Sequence "溺水自保"      ← 触发条件：在水下且氧气低
  ├─ Sequence "着火自保"      ← 触发条件：正在燃烧
  └─ Sequence "近战自保"      ← 触发条件：5 格内有敌对生物
```

| 情形 | 过程 | 根返回 |
|---|---|---|
| 无威胁 | 三个触发条件全假 | `FAILURE` |
| **有怪，但既没退路也没武器** | 触发条件为真，"手段"层全失败 | `FAILURE` |

**`Selector` 的语义就是"一个不行试下一个"，它天生不保留"哪个不行"。** 而快树没有大模型可用，压掉了就再也分不出来——于是"不抢占 → agent 继续挖矿 → 被僵尸打死"这件事变得不可分辨。

`UNCOVERED` 当初被发明出来，只是为了把这条被 `Selector` 丢掉的信息捞回来。

**换节点类型之后，问题在结构层面消失。** 改用 `Match`（互斥分类，`when` 显式给出适用条件，`otherwise` 必填保证穷尽）后，"触发条件为真但没解决"由**命中分支 + `FAILURE`** 唯一确定，不需要任何额外返回码。

于是：

- **全局只有三个返回码**，所有节点的语义回到教科书，不再需要任何语义转换
- 新增一个 `Match` 节点（节点层设计见 [行为树节点设计方案.md](行为树节点设计方案.md) §3.3）
- 任务树的 `Selector` 保留——"有现成镐就用，没有就现做一把"确实是优先级，不是分类

**已否决的备选方案**（记录以免重复论证）：保留 `UNCOVERED`，但降级成"只作用于快树的结构约定"（快树每个分支必须以 `Condition` 开头）。它能跑，但那是在**给一个错误的结构打补丁**——既然每个分支都要检查触发条件，它本来就该是 `Match`。

#### D11. 循环节点保留，且必须支持条件终止（2026-10-05 定案）

**`Repeat` 保留，但从装饰器升为独立的循环类别，且必须支持两种终止条件：`n`（计数）与 `until`（条件）。**

起因是"挖 64 个圆石"：把"找一个圆石并挖掉"展开 64 遍既臃肿又容易出错，需要循环。

但**只有计数循环是不够的**——"挖了 64 次"和"拿到 64 个"是两个不同的命题：

- 某次迭代空手而归（方块被水冲了 / 半路被抢占打断）→ 挥了 64 次，只拿到 63 个
- 背包满时挖出来的东西**直接消失且不报错** → 数量对不上还查不出原因
- 连锁挖矿类的 mod 一次挖一串 → 早就够了还在挖

所以 `until` 是必需的：**每轮重读一次世界**，而不是把完成判据焊死在写树的时候。另外 `until` 模式必须带 `maxIterations`——条件可能永远不成立（周围没圆石，或者圆石在岩浆对面走不到）。

**连带补上一条机制**：循环每轮迭代开始，**必须把循环体的游标归零**。行为树里没有 `for` 计数器，"重新做一遍"的唯一表现形式就是"游标归零"。少了它，迭代 2 会直接拿到迭代 1 遗留的游标位置，整个 `Sequence` 瞬间"成功"，循环空转 64 次然后报告"挖完了"（节点层见 [行为树节点设计方案.md](行为树节点设计方案.md) §3.5 / §6.5.1）。

**对 D7 的意义**：循环是惰性展开的放大器。没有它，LLM 要么展开 64 棵几乎一样的子树（64 次往返，且每棵会长得略有不同——第 37 棵忘了检查背包满不满就出错），要么根本表达不了"重复"。有它，往返从 66 次降到 2 次，出错面从 64 处收敛到 1 处。

**已否决的备选方案**（记录以免重复论证）：用 `Repeat(-1) { Sequence[ Inverter(until), 循环体 ] }` 凑出条件循环。**这个写法是坏的**——迭代 1 里 `Inverter` 成功，`Sequence` 的游标就移过去了，迭代 2 直接跳过它，条件**再也不会被检查**，变成死循环。这恰好说明 `until` 必须是节点级字段，不能写成循环体的第一个孩子。

**暂缓**：`ForEach`（遍历黑板上的一个列表，如"把这箱子里的东西挨个搬过去"）——终止条件既不是计数也不是世界谓词，是另一类循环，第一版用不上。

#### D12. 一棵慢树 = 一个任务，不是一次对话（2026-10-05 定案）

**慢树的创建单位是「任务」，不是「对话」。**

节点层的条文已经指向这一点，只是原先没有集中写出来：

- [行为树节点设计方案.md](行为树节点设计方案.md) §7.1：任务树数量「**0 或 1**」——同时只有一棵活着
- §7.5：「**任务树根**返回 `FAILURE` 之后」——树有明确的根，根会终结
- §5.1：「**每个任务树实例一个黑板**……任务树被替换（重规划）时清空」——顺带回答了"任务之间什么保留"：**黑板清空，世界状态靠命令重查**（§5.2）

**为什么不是"对话"**：本项目的目标是让 agent **不断**完成任务、从经验中迭代升级——这是**自主运行**，没有对话。对话是人机交互的包装，不是执行边界。而且"对话"**没有可判定的完成**：§7.5 的触发条件是"任务树根返回 `FAILURE`"，若根是"这个对话要办的事"，它什么时候算完根本说不清。说不清的东西当不了根。

**任务粒度的判据（唯一一条）：**

> **根 goal 达成后，可以停下来做别的事而不损失 → 一个任务。**

| 说法 | 判定 | 理由 |
|---|---|---|
| 挖 64 个圆石 | ✅ 一个任务 | 完成条件明确（`count >= 64`） |
| 造一把铁镐 | ✅ 一个任务 | 内含多个子目标，但**共享同一段连续状态**（位置、背包、连续时间），中间不需要重新决策 |
| 先挖矿，然后烧铁，再做把镐 | ❌ **三个任务** | 每件有独立的完成条件，各自有独立的根与反思样本 |
| 生存下去 | ❌ 不是任务 | 永不完成 → 那是**快树的职责**（D1） |

**反面判据（更实用）**：如果"这棵树的根 `FAILURE` 是什么意思"说不清，粒度就太大了。

**粒度不能往大了放，三个理由**：

1. §7.5 需要一个可判定的根——根模糊，廉价试探与升级都无从触发
2. **T4 的反思单元是"任务"**（"本次任务的完整路径"）——树越大，这条路径里混的东西越多，反思样本越糊，学到的就是混在一起的因果
3. 树的展开成本与崩溃损失——一棵跨几小时的树，D7 要把它整棵展开，中途崩溃全丢

第 2 条最关键：**反思模块的质量直接取决于"任务"这个边界划得干不干净。**

**由此暴露的缺口：§7.1 的「0」从来没被设计过。**

没有任务时 agent 在干什么？而 D2 明确说了**快树不产生新任务**——那任务从哪来？

两个选项其实是在回答同一个问题：**下一个任务由谁决定**。

| 选项 | 任务的**接续**在哪 | 后果 |
|---|---|---|
| 每任务一棵树（**本决策**） | 在**树外** | 需要一个**任务来源**（见下） |
| 每对话一棵树（已否决） | 在树内（任务是兄弟节点，用 `Sequence`/`Selector` 串） | 不需要外部来源，但树会长大、根 `FAILURE` 语义变糊，且 §7.5 / §5.1 / T4 都要重新定义 |

**任务来源**（本条决策的必然配套，形态待定）：

- 当前阶段：**人下指令**（最简单，先跑起来）
- 后续：一个「**任务选择器**」——从需求（饥饿、没工具、背包满）或目标库里挑下一个 goal，派发给慢树

**任务粒度 ⇒ 任务必须串行（2026-10-05 补充，推论）**

上面的粒度判据是**按目标状态切**，不是按动作切。这一条加上 §7.1 的「0 或 1」，直接推出：

> **同一时刻只有一件事在被推进——任务必须串行。**

**为什么"按目标状态切"能把等待吸进任务内部。** 以「烧 8 个铁锭」为例，正确的边界是 **8 个铁锭进背包**（与表格第 2 行"造一把铁镐"同理），而不是"放下原料就算完成"。三个零件都已具备：本条的判据定边界、`Repeat` 的 `until` 承担终止条件（D11）、`waitMs` 承担等待（[行为树节点设计方案.md](行为树节点设计方案.md) §9.3）。

```
Repeat until: count(铁锭) >= 8
  ├─ Sequence: 放原料进熔炉
  ├─ waitMs: 10000
  └─ Sequence: 从熔炉取出
```

任务终结的那一刻目标已经达成，**不留下跨任务的未收尾状态**。

**反面**：若把边界划在动作上（"放下原料"即 `SUCCESS`），任务会在世界进程还在跑的时候就结束，而有价值的目标尚未达成——那是**任务设计错误**，不是设计空洞，**不构成一类新的记忆需求**。

**唯一的例外开关是"并行"。** 想同时烧铁与挖煤，只有三条路：

| 做法 | 后果 |
|---|---|
| 等铁烧完再去挖煤 | 串行，即本推论 |
| 把两件事塞进一个任务 | 违反上面的粒度判据（各有独立完成条件） |
| 挂起烧铁任务，回头再取 | **需要挂起 / 恢复机制，且需要 §7.1 允许同时存在多棵树** |

所以"跨任务残留"不是任务切法的产物，是**并行**的产物。

**让步后剩下的三类残渣，各有归属，都不需要新的记忆类别**：

| 残渣 | 归属 |
|---|---|
| 世界副作用（挖的洞、随手插的火把） | 记忆世界镜像（已有的感知产物） |
| 任务未达标就终结（熔炉被拆、原料还在里面） | §6.3 / §7.5 的清理问题——与"mid-`Sequence` `Condition` 的副作用清理"是同一个洞，不是记忆问题 |
| 被放弃的整棵树 | 只在支持并行时才存在 |

**待定**：任务选择器的形态；空闲态（"0"）是否要有一套自己的行为（如"原地等待"/"整理背包"）；**是否接受任务串行**——不接受就要改 §7.1 的「0 或 1」并另行设计任务挂起机制，那是执行模型的改动，比加一类记忆大得多。

### 2.3 已核对的实现约束（反编译源码）

以下事实已对照 `decompiled_src_vf/` 核对，是设计的前提，不要再凭印象推断：

**① cursor 上的物品不会凭空消失，但背包满会掉在地上。**

调用链：`ContainerApi.closeContainer()` → `mc.player.closeContainer()`

- 客户端 `LocalPlayer.closeContainer()`（`client/net/minecraft/client/player/LocalPlayer.java:327`）：发 `ServerboundContainerClosePacket`，然后 `clientSideCloseContainer()`。其中 `Player.closeContainer()`（`client/net/minecraft/world/entity/player/Player.java:434`）只有 `this.containerMenu = this.inventoryMenu;`——**客户端完全不处理 carried**，旧 menu 对象连同其 carried 一起被替换。
- 服务端 `ServerPlayer.doCloseContainer()`（`client/net/minecraft/server/level/ServerPlayer.java:1403`）调 `containerMenu.removed(this)`，落在 `AbstractContainerMenu.removed()`（`client/net/minecraft/world/inventory/AbstractContainerMenu.java:588`），仅在 `player instanceof ServerPlayer` 时：
  ```java
  ItemStack carried = this.getCarried();
  if (!carried.isEmpty()) {
      dropOrPlaceInInventory(player, carried);
      this.setCarried(ItemStack.EMPTY);
  }
  ```
- `dropOrPlaceInInventory`（同文件 `:598`）：正常走 `getInventory().placeItemBackInInventory(carried)`；**背包满时退化成 `player.drop(stack, false)`，物品掉在地上**。

**这条要特别注意**：触发"拖到一半被打断"的场景，经常**就是**背包满（装不下了才会拖到一半卡住）。而逃跑中的 agent 不会回头捡。

**② `container/close` 是异步的，`{"status":"ok"}` 是"已排队"不是"已关闭"。**

`closeContainer()` 方法体是 `Minecraft.getInstance().execute(...)` 后立刻 `return Map.of("status","ok")`。而消息处理跑在 WebSocket I/O 线程（`AgentWebSocketServer.java:110` 的 `onMessage`），所以那个 lambda 是**投递到客户端线程排队**的。

后果：客户端关界面是立即的，服务端处理这个包要一次往返之后。**close 之后立刻读 `container/get` 不可信**——客户端 `carriedItem` 会显示为空（menu 对象已换），服务端那边可能还在安置物品。中断路径上若快树需要"界面确实关了"才能继续，这个异步返回值不够用，需要等一轮同步或轮询。

**相关的已知问题**：`ContainerMemoryTracker.commitFromClose()` 的守卫（`if (session == null || mc.screen != session.screen) return;`）应对的就是同一个根因——回调执行时 screen 可能已经变了。**该守卫尚未定案。**

### 2.4 已否定的做法

记录被讨论并否决的方案，避免重复论证：

- **每任务各配一棵快树** —— 见 D1。
- **第四个返回码 `UNCOVERED`** —— 见 D10。问题不在返回码，在快树用错了节点类型。
- **per-node 的 halt 语义字段** —— 见 D4。过度设计。
- **由大模型检索"能力胶囊"组装整棵高层行为树** —— 胶囊库会随进化无限增长，没有提示词预算的上界机制。替代形态见 D7。
- **拿 Git 作为运行时逻辑存储层** —— JSON 树的合并冲突极难处理，且对单 agent 的逻辑存储来说过重。**2026-10-05 补充**：否决的是"用 git 当运行时存储"，不是否决版本管理本身。本地版本保存已立（见 T4），仍用 append-only 日志 + 内容哈希，不引入 git；**跨 agent merge 传播继续推迟**。
- **命令层完成语义**（命令声明"我完成了"还是"我排队了"，由执行器自动插入等待）—— 49 条命令逐条声明观察条件，工程量与出错面都太大；**且即使观察条件立刻成立，仍然需要 `waitMs`**，因为 Minecraft 不允许同一时刻执行大量操作，两个操作之间必须有间隔。该方案省不掉 `waitMs`，只是叠加了一层复杂度。时序改由树里显式的 `waitMs` 承担，见 [行为树节点设计方案.md](行为树节点设计方案.md) §9.3。

### 2.5 待定项

**T1. 抢占条件与缓解手段成对设计（原则已认可，未形式化）**

「低血量」单独不是抢占条件，「低血量 AND 背包里有食物」才是。缓解手段不可用时根本不触发，持续态就不会饿死慢树。

未形式化的部分：这个"成对"是约定还是强制的结构性约束？谁来检查？

**T2.（已定，移入 §2.2 D7 / D8）** 慢树输出形态与最小任务判据。

**T3. 抢占的两条运行时兜底**

- **进入快树必须是情节（边沿触发）**：一旦进入，跑完整个快树情节才重新检查条件。否则吃掉食物的 1.6 秒里条件持续为真会反复重入，设计期做的一切都被抵消。检查可以高频（level-triggered），但**进入**必须是边沿触发。
- **缓解失败时的退避**：吃了食物但又被砍一刀、血量仍低，条件合理地为真、缓解手段也"有"，会立刻再触发。一轮两轮没问题，但"吃了 N 份还是回不来"会退化成高频重试。需要同一条抢占条件在情节结束后未解决时进入冷却。**这条设计期避免不掉**，因为缓解失败是运行时才知道的。

**T4. 版本保存系统的形态（2026-10-05 改写；原标题「Git 演进是否推迟」）**

**目标**：像 git 一样追踪快树与慢树的变化——历史、diff、回滚、可审阅。**已定的部分见下，细节待确认。**

**已定**

1. **要 git 的语义，不要 git 的实现。** 需要的是内容寻址、不可变历史、diff、回滚、可审阅；**不需要**工作树、索引、packfile、ref、merge 算法。对单 agent 的逻辑存储，一份 **append-only 的版本日志 + 内容哈希**就够了。
   —— 这与 §2.4「已否定的做法」里那条「拿 Git 作为运行时逻辑存储层」并不冲突：那条否决的是**用 git 当运行时存储**，不是否决版本管理本身。

2. **版本保存留下，跨 agent merge 继续推迟。** 原 T4 的疑虑——"这棵树跑成功了"在 Minecraft 里噪声极大（是实力还是运气？）——针对的是 **merge 传播**，与本地版本管理无关。未验证的逻辑进库再被**跨 agent 复用**会积累成半坏胶囊，这条判断不变。

3. **版本粒度 = 一批可审阅的改动。** 不是"一次反思一版"（自动新增 arm 会产生大量细碎版本，历史被淹没），也不是"一次人工审阅一版"（自动改动在审阅前不落盘，而它们可能本身就是功能性的）。**自动新增 arm 按批提交**（可回滚，但不单独成版）；**人工审阅的修改 / 删除单独成版**。

4. **快树与慢树存的东西不同**——"追踪慢树的变化"这句话必须先拆开：

   | | 快树 | 慢树 |
   |---|---|---|
   | 是什么 | 一份持续演进的**产物**（全局唯一，D1） | **每次任务重新生成**的树（D7） |
   | 存什么 | **版本链**（v1 → v2 → v3） | ① 任务内的**演化链**（展开 → 失败 → §7.5 重规划 → 展开）<br>② 跨任务的**实例集** |
   | 时间尺度 | 周 / 月 | 分钟 / 天 |
   | 供谁用 | 反思落盘、训练回归、回滚 | ① 反思的输入（"我原来那么想，改成了这样"）<br>② skill 库的原料 |

   关键差别：**慢树不是"一棵在变的树"，是"一堆各有来历的树"。** ①② 的存储与检索不同，不要用一个容器装。

5. **与"训练快树"共用同一套设施。** 训练 / 回归、反思、版本保存三者要的能力完全重合——**版本库 + 场景回放 + 结果对比**。不要各做一套。

6. **快树回滚发生在运行时。** 慢树回滚 = "下次任务用旧版"，没有时效性；快树的回滚触发条件多半就是**它刚刚把 agent 害死了**。所以需要：当前生效版本的**原子指针**；以及**回滚不得在情节执行中途切换**（快树是边沿触发的，见 T3），必须等当前情节结束。

**交叉引用**

- **T9**：T9 的「对同一棵树的并行反思写操作必须串行化」直接挂到版本库上——串行提交本来就是版本库该管的事。两者是一套设施的两个用法。
- **[行为树节点设计方案.md](行为树节点设计方案.md) §8.3**：版本控制要能算 diff，就要求 **`id` 跨版本稳定**——反思改树时，未受影响的节点必须沿用原 `id`，不得重新生成。这条已加进 §8.3。
- **T10**：事实库的"版本"是**游戏版本**，不是内容版本，两者不要混用同一套机制。

**待确认**

- 存储形态（append-only 日志 / SQLite / 文件 + 哈希）
- JSON 树的 diff 怎么呈现给人看
- "一批可审阅的改动"里，"一批"由什么界定（时间窗？事件数？）
- 审阅的界面与流程
- 快树回滚由谁触发（人？反思模块自动？）

**T5. 分层的依据：延迟预算 vs 复杂度**

当前描述的分界是「复杂任务 → 慢树 / 突发状态 → 快树」。**我主张改为按「在局势不可逆之前还剩多少时间」分层**，理由：

- **战斗**很复杂（走位、格挡、退到掩体后）但毫秒级，按复杂度分法会被错放进慢树，等于送死。
- **"记忆中的那个箱子是空的"** 极简单，但快树里没有规则覆盖它，按复杂度分法会被错放进快树，快树只能沉默。

复杂度决定"这棵树写起来多难"，延迟预算决定"它必须放在哪一层"，两者无关。

**此项未正式确认。**

**T6. 紧急旁路**

`container/close` 虽快，仍是异步且需要一轮往返。若威胁距离小于某阈值，是否需要一个"丢弃型中止"（直接断开、接受容器状态残留）的旁路？阈值未定。

**T7. 抢占检查的读取代价**

"慢树执行与快树判断并行"意味着条件节点要高频读取世界状态。必须是读**本地缓存快照**，不能每次问服务端。steveX 现有的视觉 / 实体 / 容器几套 API 需要先提供廉价的"当前帧"读取口。

**T8. 预展开的深度（D7 的补充，未确认）**

D7 的流程是"到达时才展开"。问题：每个 `PendingExpansion` 到达时都要等一次大模型往返，**agent 在每个任务边界会卡几秒**。

我建议：**预展开下一个兄弟节点，只预展开一层**。到达时子树已经在手上，且第二层仍是占位（不预展开，避免整树生成的成本重新出现）。

未定：是否采纳；以及预展开期间的失败处理（预展开的子树到达时前提已不成立怎么办）。

**T9. 反思模块（2026-10-05 讨论：边界已定，参数待定）**

**定位**：agent 不断完成任务、从经验中迭代升级——反思模块是这条闭环的执行者。

**两个触发点**

1. **一个可判定的结局**——**不限于成功**。包括：任务根 `SUCCESS` / 任务根 `FAILURE` 且 §7.5 的三步廉价试探已用尽 / 任务被放弃。
2. **抢占-恢复的边界**——快树情节结束、慢树恢复之时。

**反思对象的性质不同，产出物和门槛也不同**

| | 反思对象 | 产出 | 落盘门槛 |
|---|---|---|---|
| 慢树 | 本次任务的完整路径 | 知识库条目 / skill（可复用子树） | 自动 |
| 快树 | 本次命中的 arm + 返回码 | 候选 arm | **新增自动；修改 / 删除已有 arm 需审阅 + 可回滚** |

快树的门槛更高，因为快树出错的代价不对称——慢树规划错了顶多挖不到东西，快树改错了是 agent 被烧死、淹死、炸死。

**快树的反馈信号天然稀疏。** 绝大多数命中是 `SUCCESS`，信息量接近 0；真正有信息量的「命中真实 arm + `FAILURE`」最罕见。两条应对：

- **主动制造样本**：专门训练快树的相关内容（用命令构造场景——`/summon`、`/effect`、放水放岩浆），把每种 arm 逼出来。这解决**样本数量**和**初始质量**，但**不解决分布偏斜**（训练的分布 ≠ 运行时的分布）和**训练集外的局面**——后者正是反思模块存在的理由。**分工：训练给底座，反思补长尾。**
- **批量反思**：事件只记录不反思；攒到 N 个事件（或任务收尾 / 空闲）时成批喂给大模型。相似性由**窗口隐式定义**，不需要写相似度算法，也不会因"判定为不相似"而漏掉该合并的。

**三条件流控**：合并相似事件的反思 / 限制最大并行反思数量 / 按信息量从高到低排序。

**已定的架构约束**（会影响双树怎么实现，现在就得定）

1. **事件流一套，三个消费者**：可视化面板（§一 C1）、反思模块、快树回归测试（训练用）。
2. **原始日志全量落盘，压缩只发生在喂给大模型的那一刻。** 压缩规则以后可以改，历史还在；若压缩是对日志本身做的（有损写入），等压缩方法定了再回头看，早期日志已经丢了。
3. **对同一棵树的并行反思写操作必须串行化。** N 路反思各自产出对同一棵快树的修改，谁先落盘、要不要合并，是必须回答的。**这一条直接挂到 T4 的版本库上**——串行提交本来就是版本库该管的事。两者是一套设施的两个用法（见 T4）。
4. **快树条件的原语白名单。** 大模型写 arm 的 `when` 时只能从 [行为树节点设计方案.md](行为树节点设计方案.md) §9 命令注册表里挑现成的低成本条件，不能自由发明。§7.1 要求快树条件的代价"必须极低"，自由发明的条件（如"扫 5 格内所有实体"）会让快树慢到不能每 tick 跑。
5. **"记录所有内容"里的"所有"指所有*事件***，不含每 tick 的空闲状态——`otherwise` 每 tick 都命中（§7.2），否则日志 99% 是空气。

**待定**（依赖实测数据；双树跑起来才定得对）

- **信息量的具体度量。** 一个候选形式是「预测误差 × 罕见性」。注意**罕见的成功也是高信息量**——"原来这条 arm 在这种情况下也能用"能扩大 arm 覆盖面。若只按成功 / 失败二分排序，这类事件会被归进低信息量堆里丢掉。
- 迭代机制 / 淘汰机制 / 置信度机制
- **检索的探索配额。** 淘汰和置信度共有一个冷启动陷阱：按使用率或置信度排序会让弱条目永不被选中 → 永远没数据 → 永远被判为没用然后淘汰。**"没被用过"和"没用"是两回事**，需要显式的探索通道（例如每个任务留一个槽位随机试一条低使用条目）。
- 合并相似事件的判据、最大并行反思数、反思频率
- 日志压缩方法
- **`Match` 新增 arm 的插入位置规则。** 快树是 `Match`，第一个 `when` 为真的赢——新 arm 插在前面会抢走后面 arm 的命中，插在后面可能永远轮不到。节点文档现在只写了"从左往右"，没写顺序从哪来（手写时是人的直觉，大模型写就得有规则：紧迫度？特异性？）。

### 2.6 建议的实施顺序

1. **先定义中止语义**（D4 / D5 / D6），不依赖行为树引擎就能定。
2. **快树先用行为树重写**：行为数少（10–30），规模可控，完整验证中止与抢占。
3. **慢树先只做惰性展开**（D7），不做整树生成，不做胶囊检索。
4. **版本保存（T4）**：本地版本库与"训练 / 回归"共用一套设施，和反思模块（T9）同期做；**跨 agent merge 传播推迟**。
5. **反思模块（T9）最后做。** 它的参数（信息量度量、淘汰机制、置信度、反思频率、压缩方法）全是实测依赖的，双树没跑起来之前定不了。唯一的例外是 T9 里那五条**架构约束**——它们影响双树怎么实现，要提前守住：事件流一套三消费者、全量落盘、写串行化、`when` 的原语白名单、事件记录不含空闲 tick。
