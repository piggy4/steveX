## 0. 一句话方案

**保留 §7.11/§7.12 的"整格 bbox 预判 + 逐像素射线越票"判据原样不改，只对每个"越票"像素追加一次
「射线 ∩ 被记住形状」的几何求交过滤**：射线只穿过格内**空余区**（活着时本就不被终止、无作证价值）
的票一律作废；只有确实穿过**被记住形状**的越票才构成"该格在现实中已消失"的证据。形状的"在/不在"
信号差只存在于几何区，过滤后即可安全判删非满形状方块。

**被记住形状 = 该方块在客户端烘焙模型里的实际渲染几何，表示为「quad 面清单 + sprite alpha 掩码表」**
（本次修订的核心；上一版是"轴对齐盒并集"）。由记忆侧在写 cells 时算出：

```
Minecraft.getInstance().getBlockRenderer().getBlockModel(state)   // BlockStateModel
  → model.collectParts(random, parts)                              // random.setSeed(state.getSeed(pos))
  → part.getQuads(null/each Direction) → List<BakedQuad>
  → 每条 quad 存：4 顶点（格内局部 [0,1]）+ 4 个 sprite 局部 UV + 自算法线 + spriteId
  → 每个用到的 sprite 存：mip 0 的逐 texel alpha 字节表（增量下发，§4.3）
```

采集侧求交 = **射线 ∩ 三角形 → 重心坐标插值 UV → 查该 sprite 的 alpha 表 → 按该方块渲染层的阈值判该
texel 是否被 discard**；未被 discard 的**正面**命中才计入几何证据，`t_shape_exit` 取这些命中里最大的 `t`
（§3.2）。

**为什么这样一步到位**：几何表示从"轴对齐盒"换成"quad + alpha 掩码"后，`G`（我们算出的几何）与 `R`
（真实会写深度的几何）**处处相等**——档 2（非轴对齐 quad）不再需要 fail-closed 排除（做三角形求交即可，
不需要 AABB 包住它），档 3（alpha 镂空）不再需要 fail-closed 排除（掩码精确给出哪些 texel 通过）。
上一版"三档构造、两档整体排除"的两条欠删族**同时消失**，而且**不是**靠"精确几何更难所以更危险"——
方向始终是 `G ⊆ R`（§3.4），掩码只是把 `G` 抬到 `= R`，比盒表示**更安全**（盒表示是它的子集）。

**为什么拾取盒被推翻（三次修订的核心，保留记录）**：拾取盒并非渲染足迹的子集，对 §2.1 的招牌交付物直接不成立——

| 方块 | 拾取盒 | 实际渲染 | 高估倍数 |
|---|---|---|---|
| 栅栏 | 横臂 **4 px 宽**、y 0–16（`FenceBlock:38` 传 `wallWidth=4.0F`） | **2 px 宽**、y 6–9 / 12–15 两道横杆 | 横向 **2×**，且 y 向覆盖渲染不占的 0–6、15–16 |
| 红石线 | **10 px** 十字（`RedStoneWireBlock:96-98`） | 约 **2 px** 细线 | 约 **5×** |
| 铁栏杆 | 2 px 十字（`IronBarsBlock:30`） | 约 2 px | ≈1×（此族恰好接近） |

方向约束（§3.4）要求几何**不超出**渲染足迹；拾取盒在横向上系统性高估 2~5 倍，会把"方块活着、
射线穿格内空余区"的像素误判为作证像素 → **误删活体**。注意 `FenceBlock` 自己就给出了反证：它给
`occlusionShapes` 用的是 `2.0F`（`FenceBlock:42`），即 MC 自己都不认为拾取盒的 4 px 是真实占位。

> **两次推翻的区别**：三次修订推翻的是**几何源**（拾取盒 → 烘焙模型）；四次修订推翻的是**几何表示**
> （轴对齐盒并集 → quad + alpha 掩码）。几何源自三次修订起就已是烘焙模型、未再变；四次修订只改"把
> 已拿到的 `BakedQuad` 编码成什么"——从"包住它的 AABB"换成"它就是它"，并用 alpha 掩码补上贴图这一维。

## 1. 背景与问题（现状核查，均已落代码）

### 1.1 判据为何钉死在"填满整格"

§7.11 判定谓词是 `isShapeFullBlock && canOcclude`（`isSolidOpaque`，
[BlockStateUtil.java:53](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/BlockStateUtil.java#L53)）。
限制项是**"形状是否填满整格"**，与透明度、写哪张场无关——因为逐块判定隐含的前提是：

> 某格若存在，任何从相机出发、穿过该格**几何所占据区域**的射线必被其近表面终止（深度 < 格远面 t_far）；
> 因此"存在某像素射线穿过该格整盒而深度 ≥ t_far − δ" ⟺ 该格不存在。（[DeletionJudge.java:13-16](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/DeletionJudge.java#L13-L16)）

对非满形状，该前提只在**几何区**成立。格内**空余区**是整格判据唯一的假证据来源（§7.13 根因）：

| 射线穿过的区域 | 活体时深度行为 | 整格判据（Z ≥ t_far−δ 越票） |
|---|---|---|
| 几何区 | 被近表面终止（近面 < t_far） | 不越票 ✓ 正确保活 |
| 空余区 | **不被终止**（直达背后/天空） | **越票** ✗ 与"已消失"外观无差别 |

把空余区越票全计入 → 一个**活着的玻璃板/栅栏**单快照就远超阈值像素越票 → 误删活体。故 v2.23/v2.36 把
判据钉在 `isShapeFullBlock`，非满形状一律不纳入 cells、不判、不删（欠删无害，接受）。

### 1.2 现状边界（要补齐的那块）

- **记忆侧 `MemoryCellReporter`** 只上报三段：main（实心不透明 + 冻结实体占用格 + 岩浆）、translucent
  （水 + 满格透明）；**非满形状不在任何段**（[MemoryCellReporter.java:167-191](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/MemoryCellReporter.java#L167-L191) 的 computeCells 分类丢弃分支）。
- **采集侧 `DeletionJudge`** 只按整格 bbox 判（main 场 `test` / translucent 场 `testTranslucent`），无几何概念。
- **记忆侧 `DeletionApplier`** 的内容守卫 `isDeletableContent` = 实心不透明 ∪ 流体 ∪ 满格透明；**非满形状被挡在可删集外**（[DeletionApplier.java:139-154](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/DeletionApplier.java#L139-L154)）。

于是：敲掉一个独立玻璃板/栅栏/铁栏杆/台阶 → 真实世界没了，记忆世界**永远残留**。§7.12 验证清单里
明确把它列为"回归不删"（[视觉api设计方案.md §7.12 已知边界](../视觉api设计方案.md#L1090)）。

### 1.3 实施此版时顺带修正的一个 v2.36 缺陷（含水非满块）

现状 computeCells 里 `isWaterFluid(state)` 只看 `state.getFluidState()`，**不看方块本体**——一个
**水logging 的栅栏/台阶/玻璃板**（方块本体 + 水同时占据该格）会被整格归入 translucent 水段。而 translucent
水段的语义是"该格=纯水，整格消失判据证明的是**水**消失"，判删后 `DeletionApplier` 会把**整个格置空**
（连同还活着的方块本体）→ **误删活方块**。本版把此类格改走几何段（见 §4.4），一并修正。

## 2. 设计目标与范围

### 2.1 纳入（本轮判删）

**纳入不再按方块族手列，改由谓词自动分类**（判定见 §4.1）。几何源换成烘焙模型后，"拾取盒 ≈ 渲染"
这条筛选依据消失，纳入范围由三条**可自动检验的判据**给出，判据场则随现实渲染层路由（§5.2）：

| 判据 | 处理 | 判据场 |
|---|---|---|
| 非满形状、`RenderShape.MODEL`、无 BE、模型 quad 数 > 0 | **纳入几何段**，按「quad 面清单 + sprite alpha 掩码」精确求交判 | 由渲染层定：`SOLID`/`CUTOUT` → main 场（任意图形配置）；`TRANSLUCENT` → Fabulous 走 translucent 场、Fancy/Fast 走 main 场、Fabulous 第二路缺 → 欠删 |
| 满格方块（`isShapeFullBlock`） | 仍走 §7.11/§7.12 现段，**不进几何段**（整格盒是它的退化情形：quad 恒相交、`t_shape_exit = t_far`，无收益） | 同现段 |
| 流体 | 走 §7.11/§7.12 现段，**不进几何段**（水不在方块模型系统内，见 §9「水的整格判据」待实测项） | 同现段 |

于是**栅栏、铁栏杆、门、活板门、台阶、楼梯、梯子、火把、拉杆、按钮、压力板、锁链、墙、铁轨系、
红石线/中继器/比较器、玻璃板（普通与染色）、十字植物/草/作物、睡莲、以及任何满足上述三条
判据的模组方块**，一律自动纳入，**不再需要按族预判**。★ 与三次修订相比，**粗体新增的族（十字植物/
草/作物/睡莲…）是本次几何表示更换的直接收益**：它们在盒表示下因非轴对齐（档 2）或 alpha 镂空
（档 3）被整类 fail-closed 排除，见 §3.4。

> **告示牌**（`oak_sign` / `oak_wall_sign` 及同类）**不在本版纳入范围**：它们是方块实体方块，
> 被上表第 1 条的 `hasBlockEntity()` 判据自动排除（§2.2 第 2/5 行）——牌面几何由 BE renderer 绘制、
> 不在方块模型系统内，且"完整删除"还须协同废止 BE 通道的记录（§13，v2.38）。

§10 第 3 条扫描从"确认哪些族可纳入"降级为"确认哪些方块 quad 数为 0 / 模型缺失"（即验证判据本身），
范围大幅收窄；档 2/档 3 的"分类清单"一项**整项删除**（已无此分类）。

> **承重前提（本表成立于此，此前从未被验证）**：把 SOLID/CUTOUT 路由到 main 场、把
> TRANSLUCENT 路由到 translucent/main 场（§5.2），隐含"该渲染层的表面确实写入其所路由的深度场"——CUTOUT
> alpha-test 表面须写 main 深度、且非满块须能被 raycast 进本帧可见集。现行 main 段只跑过满格实心
> （`isSolidOpaque`），**CUTOUT 入 main 场是从未验证过的新前提**。以 §10 第 2 条"场构成探针"为一票否决：
> 不过 → 本表相关类整体降级欠删，先修采集深度场构成。

### 2.2 明确排除 / 欠删（防误删）

## 3. 判定：两步法（几何过滤）

### 3.1 第一步：整格 bbox 预筛（对几何段格降级为粗筛）

对记忆格 C：8 角投影 → 屏幕 bbox → 逐像素「射线(camPos→p) ∩ 整格 AABB」slab 求交 + 读 C 现实所写场
（路由见 §5.2）→ 记录每像素的 `Z` 与该场。

- **无几何的格（现 main/translucent 段）**：仍在此步定案，判据 `Z ≥ t_far − δ` → **越票集 S**
  ——判定式、哨兵、δ、裁剪、相机在格内跳过、`currentTerrain` 跳过全部复用
  [DeletionJudge.java:138-200](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/DeletionJudge.java#L138-L200)，**零改动**；
- **带几何的格（几何段）**：本步只做**粗筛**（射线确实穿过整格 bbox、且该格不在可见集），
  **阈值判定下沉到第二步**——因为比较基准要换成形状自身的**真实命中出口**（§3.2 第 2b 条）。

### 3.2 第二步：对每张候选票追加「射线 ∩ 被记住形状」+ 换比较基准

用 C 的**被记住几何**（= 客户端烘焙模型的 quad 面清单 + sprite alpha 掩码，来源见 §4.2），对候选像素
p 做两件事：

**2a. 求交过滤**【原设计，本次由"射线 ∩ 盒"升级为"射线 ∩ 三角形 + 掩码"】

对 C 的每条 quad 做一次 **Möller–Trumbore 射线-三角形**求交（quad = 两个三角形 `(p0,p1,p2)`、
`(p0,p2,p3)`），命中得 `t` 与重心坐标 `(w0,w1,w2)`。一次命中记作**有效**需同时满足三条：

1. **正面**：`dot(n_q, rayDir) < 0`（`n_q` = 该 quad 随数据下发的法线，§3.4）。地形背面剔除是**开**的
   （`TERRAIN_SNIPPET` 无 `withCull(false)`，`RenderPipelines:30-40`），背面 quad 不产生任何绘制 ⇒ 不
   写深度 ⇒ 不能作证据；
2. **掩码通过**：用重心坐标插值 4 个顶点的 **sprite 局部 UV**，取该 texel 的 alpha，按 C 的渲染层阈值
   判定 `alpha ≥ 阈值`（阈值表见 §5.2）。terrain 的 `sampleNearest` 按屏幕 texel 尺寸吸附到 texel 中心
   （`terrain.fsh:16-35`），**与我们的"取整查表"模型一致**；
3. **在格内**：命中点落在该格 bbox 内（与第一步的截断口径一致）。

- **无任何有效命中**（该票只穿格内空余区、或只从背面擦过、或命中的 texel 全被 discard）→ **作废**。
  这类像素活着时本就不被终止、是整格判据唯一的假证据源；
- **有有效命中** → 进入 2b。

**2b. 比较基准由「整格远面」改为「形状出口」**【三次修订新增，本次口径微调】

对相交的票，判据用 `Z ≥ t_shape_exit + δ` 而非 `Z ≥ t_far − δ`：

- `t_shape_exit` = **通过 2a 三条的全部有效命中中最大的 `t`**（不再是"各盒 `slabInterval` 的 `tmax` 取最大"——掩码不过的 texel 不写深度，其 `t` 不能用来界定"被记住形状的最远边界"，否则会把活体表面划进形状之外）
  （[DeletionJudge.java](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/DeletionJudge.java)
  的 `slabInterval` 仍供**第一步整格粗筛**使用；几何段的 2a/2b 改用新增的**射线-三角形求交**，
  不再复用它）；
- **为什么必须换**：`Z` 是现实深度（到第一个可见表面的距离）。活体时
  `Z = t_surface ∈ [t_shape_enter, t_shape_exit]`，故 `Z < t_shape_exit + δ` **恒成立** → 活体**永不越票**。
  若仍用 `t_far − δ`，则当形状沿射线的厚度 < δ 时活体表面会落进 `[t_far − δ, t_far]` → 越票 → 第二步
  又判"相交" → **保留 → 误删活体**。而最薄的形状（红石线中心点 1/16 = 0.0625）与 δ = 0.05 只差
  **0.0125**（0.2 px）——余量薄到不能依赖。
  > ⚠️ **2026-09-11 实测推翻此处的几何估计**：那个 `1/16 = 0.0625` 是按**模型直觉/碰撞盒**估的，
  > 实测烘焙后的 `BakedQuad` 几何是 **1/64 = 0.015625**（红石粉全部 12 条 quad 都在格内 `y = 1/64`）。
  > 也就是说真实余量不是 `+0.0125` 而是 **`0.0156 − 0.05 = −0.0344`**（负值）。见下方 **2b-δ**。
- **副作用是正向的**：`t_shape_exit < t_far`，阈值更低 → 真消失的证据更容易成立，
  **同时更安全、又更灵敏**，不是保守化。
- **本次修订的额外收益**：盒表示的 `t_shape_exit` 是"盒的出口"，可能远在真实几何之外（斜视角下的
  旋转 quad 尤其），使活体表面**有可能**落进 `[t_shape_exit, t_shape_exit + δ)`；换成"通过掩码的
  真实命中"后，`t_shape_exit` 严格收紧到真实几何的边界 → 2b 的欠删窗口同步收窄。

**2b-δ. δ 必须是逐格量，不能是全局常量**【2026-09-11 五次修订新增】

2b 修好了"**活体不被误删**"这一侧（`Z ≤ t_shape_exit < t_shape_exit + δ` 恒成立）。但**同一批最薄形状的
另一侧——"真消失能否成立"——从未算过**，而两侧用的是同一个量：形状沿视线的几何尺度与 δ 比大小。

判据 `Z ≥ t_shape_exit + δ` 要成立，观察面必须落在形状之外**至少 δ**。而形状能提供的跳变上限就是它自己的
几何高度：设 `h_max` = 该格几何顶点在格局部坐标下的最大 `y`，某像素命中高度为 `h_hit ≤ h_max`，
则跳变 = `h_hit / |dy|`，`|dy| ≤ 1` ⇒ **上界恰为 `h_max`**。于是：

> **可达性必要条件：`δ < h_max`。**
> δ ≥ h_max 时判据**按构造不可满足**——该格无论是否真的消失都永不越票。

取 **`δ_cell = min(δ_global, κ · h_max)`，κ = 0.5**（保证最有利像素上的跳变仍是余量的 2 倍）：

| 形状（实测格局部 `h_max`） | `h_max` | `δ_cell` | 效果 |
|---|---|---|---|
| 草丛 / 藤 / 竹 / 灌木 / 蕨（立体，y 跨 0..1） | 1.000 | 0.05 | **与现状逐位相同，零回归** |
| 台阶 / 栅栏 / 墙 / 压力板（≥ 0.5） | ≥0.5 | 0.05 | 同上 |
| 地毯 / 铁轨类（1/16） | 0.0625 | 0.031 | 略放宽，仍 ≤ 半高 |
| **红石粉 / 落叶（1/64）** | **0.015625** | **0.0078125** | **从"按构造不可满足"变为可达（需 `abs(dy) ≤ 2`，即全角度成立）** |

阈值就落在 `h_max = δ_global = 0.05`：**比 1/16 薄的非满形状方块**（红石粉、落叶、苔藓地毯、花粉瓣…）
全部命中此病。实测口径下的失效-可达边界见 §3.3 末行。

> **一处口径选择（请审阅时定）**：本式对 `h_max > δ_global` 的形状也生效（如地毯：0.05 → 0.031），
> 即**对"原本已可删"的方块也放宽了一点**。理由是"每格都保住 2 倍余量"这条性质更整齐。
> 若偏好**对现有行为严格零改动**，改用分段式即可：
> `δ_cell = (h_max > δ_global) ? δ_global : κ·h_max`——此时只有 `h_max ≤ δ_global` 的一类被改动，
> 红石粉/落叶的效果完全相同，地毯维持 0.05。两者都不放宽任何**上界**（均 ≤ δ_global）。

`h_max` 由**已解析出的 quad 顶点**在采集侧就地算出（对 `v[1]/v[4]/v[7]/v[10]` 取 `max`），
**不写进文件、不动 v4 格式、不涉 epoch**——它是几何的纯函数，重复计算无副作用。

> **为什么取"每格"而不是"每像素"？** 逐像素用命中点自身高度 `h_hit` 看似更精确，但它是**反向**的：
> 草丛的射线在贴近地面处命中时 `h_hit` 很小，逐像素会让 δ 在那里**变小**——而那恰恰是最容易受
> 深度噪声影响、最需要余量的像素。取格内 `h_max` 是"按该格**最有利**的像素定余量"，对弱像素只会
> 更严 ⇒ 恒走欠删方向。

> **δ 调小要不要补一条抗噪下界？——要（2026-09-11 六次修订：原"不需要"的论证有漏洞）。**
> 原论证（"量化只会吞掉信号、不会凭空造出信号"）成立的前提是**比较两侧同为量化值**。但 2b 的比较是
> **量化观测 `Z` vs 解析阈值 `t_shape_exit + δ`**——阈值没有量化。于是残差 `e = Z − t_surface`
> （界为 `0.5·Δz(1ULP) = 5.96e-7·z²`）**可正可负**，正残差 `e ≥ δ` 即**误删活体**。
> 故 δ 必须有下界：**`δ_cell ≥ c · 1.192e-6 · z²`**（`c` 由 §10 第 17 条实测标定，先取 1）。
> 由此得到贴花类（`h_max = 1/64`）的**可行窗口**：`[c·1.192e-6·z², κ·h_max)` ——
> **在 `z ≈ 81.0 格`（c=1，保守）/ `114.5 格`（c=0.5，按残差半 ULP 界）/ `57.2 格`（c=2）闭合**
> （解 `c·1.192e-6·z² = κ·h_max = 0.5/64` ⟹ `z = 80.95/√c`；注意 `114.5` 这个数在 ε 侧也出现，
> 那是"`1/64 ÷ 1 ULP 量子`"的同一算式、问的是**另一个**问题——落格可观测性，勿混）；窗口闭合后该格在 2b 上两面都不可判，
> 必须**显式记为"不可判"并跳过**（欠删方向安全），**不是**硬用上界（那会退化成噪声驱动、误删活体）。
> 详见 §7 决策 Q。**不得**回退到全局 δ（那会让红石粉/落叶重新失效）。

> **一处待验证的工程假设**：`terrain.fsh:88-96` 的 discard 判据是 `color.a < ALPHA_CUTOUT`，而
> `color.a` 来自 `贴图采样 alpha × vertexColor.a`（`:91` 的雾混合写成 `vec4(1,1,1,color.a)`，不改变
> alpha 分量）。本设计假设 terrain 层 `vertexColor.a ≡ 1`，故判定量就是**贴图 alpha**。列入 §10 第 2 条
> 探针一并核对；若某些方块带逐顶点 alpha，则该类欠删（方向安全）。

越过计数仍 ≥ `removalPixelThreshold`（默认 2）才进 deletions。§3.5 的弦长 ε 规则继续用于消除
2a 阶段"擦过三角形边、命中弦长 ≈ 0"的贴边噪声票。

|---|---|---|---|

| 活体、射线过几何区、命中 texel **被 discard**（镂空处） | 无（不写深度） | （不进 2b） | ✓ 作废 |
| 活体、射线过空余区 | **无命中** → 作废 | （不进 2b） | ✓ 消除唯一假证据源 |

| 已消失、射线过空余区 | **无命中** → 作废 | （不进 2b） | ✓ 剔除无意义像素 |
| 已消失、射线过几何区、**但该格 `h_max ≤ δ`**（贴地平铺贴花：红石粉/落叶，`h_max = 1/64`） | **命中** | 背后就是**支撑块顶面**，跳变 `= h_max / abs(dy) ≤ h_max < δ` → **不越票** | ✗ **本次修订前的失效行**（判据按构造不可满足，永不删） |

> 第 2、3 行是本版（quad + 掩码）**新增**的正确性行：盒表示下它们都会被错算成"相交"（盒盖住了背面
> 与镂空处），只有在"恰好也满足 2b"时才侥幸不出错。掩码表示把它们**在构造上**归于"不写深度 ⇒
> 无证据"，与真实渲染逐条对齐。

**承重前提（仍未被验证）**：第 1、3 行隐含"**该格现实所写的那张深度场里，确实存在该方块表面的写入**"
（§5.2）——具体到 CUTOUT 非满块，即其 alpha-test 表面确实写 main 深度、且该格能进本帧可见集。该前提
**此前从未验证**（§7.11/§7.12 的 main 段只跑过满格实心）。若前提不成立，第 1 行退化为：读不到自身近面
→ `Z` = 背景 → 越票 → 2a 又相交 → **误删活体**。故 §10 第 2 条"场构成探针"列为**一票否决的 Phase-0**。

**关键推论**：前提成立时，活体穿过几何区的像素被 **2b** 的基准排除（`Z ≤ t_shape_exit`）；2a 只负责
剔除"只穿空余区"的票。也就是说 **2a 管"射线是否真穿过被记住的实体"，2b 管"深度是否显示那里真的空了"**，
两者缺一不可——**不能**只留相交谓词。**满格方块是本法退化情形**（形状 = 整格盒 → 2a 恒真、
`t_shape_exit = t_far` → 与现判据逐像素一致），可统一实现而非另开并行判据。

> **本节修正了上版的错误结论**：上版写"过滤器只需一个相交谓词——无需改预判参照距离（仍是整格远面 + δ）"，
> 并据此断言"活体过几何区的像素在第一步就被自身近面深度排除"。该断言**只在形状沿射线的厚度 ≥ δ 时成立**；
> 而最薄形状（红石线中心点 1/16 = 0.0625）与 δ = 0.05 只差 0.0125 → 活体表面可落入 `[t_far − δ, t_far]`
> → 越票 → 2a 相交 → 保留 → **误删活体**。2b 把基准换成形状自身出口，使该通道**在构造上关闭**。
>
> **2026-09-11 补记（同一处估计的第二次代价）**：上面那句"最薄形状 1/16 = 0.0625"是**估的，不是测的**，
> 实测是 **1/64 = 0.015625**。这个 4 倍误差当时只被用来论证"余量薄"（误删活体一侧），2b 顺手把它关死了；
> 但**同一个数在相反方向上的后果没人检查**——δ = 0.05 > h_max = 0.0156 意味着 2b 对红石粉类
> **按构造不可满足**，于是"活体不被误删"与"消失永不被识别"同时成立。新增的**末行**与 **§3.2 2b-δ**
> 即为此。教训与 §14.3(b) 同源：**凡承重的几何量必须取自烘焙后的真实顶点，不得用模型直觉估计。**

### 3.4 形状方向约束：`G ⊆ R`，且本表示使 `G = R`

设 `R` = 该方块真实"会写深度的像素"集合，`G` = 我们算出的几何。两个方向的需求是**互相冲突**的：

| 目标 | 需要的方向 | 违反的后果 |
|---|---|---|
| 不漏判真消失 | `G ⊇ R` | 漏掉证据 → 欠删 |
| **不误删活体** | **`G ⊆ R`** | 空区射线当证据 → **误删活体** |

冲突时以"不误删"为准 → **约束是 `G ⊆ R`**。理由：活体时若射线在 `G \ R` 上有**有效命中**（我们的几何
盖住了渲染并不占的地方——盒表示下是旋转 quad 的 AABB，掩码表示下是放行了被 discard 的 texel），该命中处
没有被绘制、没有深度写入 → `Z` = 背景 → 2b 判越票 → **保留 → 误删活体**。
`G ⊆ R` 时"2a 有有效命中"⇒"该处确实被绘制过"⇒ 活体必然 `Z ≤ t_shape_exit` ⇒ 保活。

> **本节保留两条历史撤回**：① "过估是安全的，我们只需要一个超集"——**错的**，它混淆了上表两行的方向需求，
> 超集满足的是"不漏判"、代价恰好落在"不误删"上；② "盒表示下的 `G ⊆ R` 已是能拿到的最好结果"——
> **四次修订后不再成立**：quad + alpha 掩码把 `G` 抬到 `= R`。两次撤回的方向一致：**`G ⊆ R` 是底线，
> `= R` 才是目标**，且达到 `= R` 的路径是"换一个更强的表示"，不是"把盒算得更紧"。

**`G` 的构造：quad + alpha 掩码**。每条 quad 贡献"该 quad 上掩码通过的那部分"；某格全部 quad 都不
可用（法线退化 / sprite alpha 表不可得）→ 该格不进几何段（欠删）：

| 表示要素 | 内容 | 为什么是 `R` 的一部分 |
|---|---|---|
| **quad 顶点** | `BakedQuad.position0..3`，格内局部 [0,1] | `BakedQuad` 的顶点就是提交给 GPU 的那份数据（变体选择 / `multipart` / `BlockElementRotation` / 烘焙期面剔除全部已应用）。**不做 AABB、不做任何近似**——这正是档 2 消失的原因：旋转 quad 照样做三角形求交 |
| **正面法线** | `n = normalize(cross(p1−p0, p2−p0))`，**随数据下发** | 地形背面剔除是开的（§3.2 第 1 条），背面 quad 不写深度 ⇒ 不属于 `R`。**不读 `BakedQuad.direction`**：`FaceBakery:90` 是 `Objects.requireNonNullElse(finalDirection, Direction.UP)`——`calculateFacing` 对**非轴对齐** quad 返回 `null`（`findClosestDirection` 要求 `product >= 0`，`FaceBakery:169`），于是旋转 quad 一律被静默标成 `UP`，**不可用**。自算法线两侧共用同一个数，不存在约定分歧 |
| **UV（sprite 局部）** | 4 顶点各一对 [0,1] 的 sprite 内坐标 | `FaceBakery:136` 存的是 **atlas 空间** UV（`UVPair.pack(icon.getU(u), icon.getV(v))`）；记忆侧用 `sprite.getU0()/getU1()/getV0()/getV1()` 换算回 sprite 局部再下发，采集侧无需任何 atlas 几何 |
| **sprite alpha 表** | mip 0 逐 texel 的 alpha 字节 | `terrain.fsh:94` 的 `if (color.a < ALPHA_CUTOUT) discard;` 是**逐 texel** 的 ⇒ 只有逐 texel 的掩码才是 `R`。**这是档 3 消失的原因**：不再需要"有一处透明就整条 quad 不参与"，而是精确到 texel |

> **法线符号约定**：`GeometryUtils.normal(p0,p1,p2)`（即 `cross(p1−p0, p2−p0)`）就是 vanilla 自己的
> `calculateFacing` 用的同一个量（`FaceBakery:153-157`），其右手定则方向即"该面朝外的方向"；渲染器的
> 正面定义与之一致。故 `dot(n, rayDir) < 0` ⇔ 相机看到的是该 quad 的正面。**两侧共用下发值**，采集侧
> 不重新推导，唯一需要保证的是记忆侧用 vanilla 的顶点顺序（直接取 `position0..3` 的原始顺序即可，
> `recalculateWinding` 已对非旋转 quad 归一化过缠绕，旋转 quad 的缠绕也来自同一 `FaceInfo` 构造）。
> 退化情形（顶点共线 → 叉积 ≈ 0 / 非有限）→ **该 quad 丢弃**（fail-closed）。

> **双面 quad 不需要特判**：十字植物/草/作物在模型里**每个元素同时声明了相反的两个面**
> （`models/block/cross.json`：同一元素带 `north` + `south`（或 `west` + `east`），UV 相同、各绕 Y 轴
> 45°、`"rescale": true`）→ 每个平面得到 **2 条法线相反**的 quad。于是任何穿过该平面的射线必然命中其中
> 一条的正面，**无需"忽略法线"这种会引入过估的偷懒做法**。

- **`G = R` 是同一状态下的等式；状态过期时由更强的闸门兜底**：记忆连接态过期（如邻居栅栏被拆 → 现实
  那格已断杆、被记 quad 仍是长杆 → 瞬时 `G ⊋ R`）时，误删被**可见集跳过**挡住——cells 格若本帧可见，
  judge 直接跳过、deletions 只在格不在可见集时产生
  （[DeletionJudge.java:138-200](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/DeletionJudge.java#L138-L200)，
  与 [ObjectResolver.java:158-162](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ObjectResolver.java#L158-L162)
  的可见格不判删同源）。立着的活栅栏本帧被看到 → 永不被判删。
- 残余风险收窄为**一个**小口：**(a)** 状态过期且**本帧不在可见集**（刚出视野/屏缘/极远）的格，其过期
  长杆几何的空余区恰有 ≥ 2 有效命中越票 → 误删（记入 §9 边界）。盒表示时代的另两个口
  （"同状态下拾取盒 ⊋ 渲染"、"档 2/档 3 整类"）**已分别由几何源更换与几何表示更换根除**。
- **缺面元素（原"待验证构造细节"）已由本表示自动解决**：若某模型元素故意省略了部分 `faces`（烘焙期面
  剔除），从缺面方向进入的射线**在该位置根本没有 quad** → 2a 无有效命中 → 作废。盒表示下这条射线会
  "穿过盒"而越票（渲染面上没有它的深度）→ 误删；quad 表示下它在构造上安全。§10 第 3 条原有的扫描项
  **降级为观测**（确认这些方块按预期欠删，而非验证正确性）。
- **掩码保真度的三个已知差距**（记入 §9，均为距离/资源侧效应，不改变 `G ⊆ R` 的方向保证）：
  ① **mip 级**：我们建模 mip 0，实际渲染在远处用 mip > 0；vanilla 有 alpha 感知的降采样
  （`SpriteContents.alphaCutoffBias` / `MipmapStrategy`）使差距收窄但不为零；
  ② **动画贴图**：`SpriteContents.isAnimated()` 的帧会改变 alpha；本版按**首帧**建表（或按当前帧，
  见 §4.2 第 4 步），帧不匹配时欠删/误差；
  ③ **资源包不一致**：见 §9。

### 3.5 斜掠/贴边（工程而非逻辑）

像素中心射线恰好擦过 quad 边/角的贴边越票（命中弦长 ≈ 0）要降权或作废：此类票在活体时本就不被终止
（像素中心落在渲染足迹之外）、是 1 像素级噪声。规则：**有效命中的弦长 < ε**（如 < 0.05 格，几个 δ）的
越票作废，配合既有 ≥2 多票阈值全消误删。轮廓/亚像素容差同 §7.12 已提及口径。

> 本表示下 ε 规则的适用面比盒表示**更窄**：掩码已经把"射线打在镂空 texel 上"的票在 2a 就作废了，ε
> 只剩"贴着一个**不透明** texel 的边缘擦过"这一种情形，噪声源比原来少一类。ε 的取值维持不变。
>
> **2026-09-11 补**：上面的"几个 δ"措辞在 δ 逐格化（§3.2 2b-δ）后**不再成立**——ε 与 δ 从此必须**解耦**
> （δ 会随格缩到 1/128，ε 若跟着缩就失去降噪意义）。实现已按**重心空间**取 `min(w0,w1,w2) < 1e-3`
> 作废**整个像素**，与 δ 无关，正是这个口径；§14.3(a) 记了它的落地理由。

### 4.2 形状来源与编码：记忆侧客户端烘焙模型 → quad + alpha 掩码

几何由**记忆侧**在写 cells 时计算，取**烘焙模型的 quad 面清单 + sprite alpha 掩码**（§3.4）。理由：

- **这是唯一等于渲染足迹的源**（§0）：`BakedQuad` 的顶点就是提交给 GPU 的顶点，变体选择 / `multipart`
  组合 / `BlockElementRotation` / UV / 烘焙期面剔除全部已应用。任何 `BlockBehaviour.*Shape` 都是玩法近似，
  没有一个等于渲染几何；拾取盒被 §0 证伪（栅栏 2×、红石线 5× 高估）；
- **记忆侧算而不是采集侧算**：几何源就是 `BlockState`，而 cells 本来就是记忆侧发的；采集侧手里只有
  `blockId` + 属性，须 `BlockStateUtil.fromSaved` 重建，而该重建**有回退**（未知方块 → AIR、非法属性
  跳过）——**重建出的几何一旦小于记忆侧真实方块的足迹，就是低估 → 越票 → 误删**。记忆侧用被判格自己的
  `BlockState`，**构造上不会低估**；
- **alpha 掩码也只能在记忆侧取**：真实 alpha 的公开入口不够用——`SpriteContents` 只暴露
  `isTransparent(frame, x, y)`（**只有 alpha == 0 这一个布尔**，`SpriteContents:202-211`），拿不到
  `ALPHA_CUTOUT` 需要的**连续 alpha**（阈值 0.5 / 0.1 / 0.01，见 §5.2）。须加一个 **MixIn accessor**
  读 `SpriteContents.originalImage`（`:46`，无 getter）——这是本版唯一新增的 MixIn，且只读不改；
- 采集侧继续只消费"quad + 掩码"做射线求交，**零模型代码、零注册表依赖**（理由与上版一致）。

```
// 记忆侧，首次遇到某 BlockState 时烘焙 + 缓存
BlockStateModel model = Minecraft.getInstance().getBlockRenderer().getBlockModel(state);  // BlockRenderDispatcher:96
RandomSource random = RandomSource.create();          // 或复用 BlockRenderDispatcher.singleThreadRandom
random.setSeed(state.getSeed(pos));                   // ← 必须：vanilla 自己就是这么取变体种子的
List<BlockModelPart> parts = new ArrayList<>();
model.collectParts(random, parts);                    // BlockStateModel:22
for (BlockModelPart part : parts) {
    for (Direction d : ALL_DIRECTIONS + {null}) {
        for (BakedQuad q : part.getQuads(d)) {        // BlockModelPart:11
            Vector3fc p0..p3 = q.position0..3;                        // ① 顶点：原始顺序，不做 AABB
            Vector3f n = cross(p1-p0, p2-p0).normalize();             // ② 法线：自算（不用 q.direction，§3.4）
            if (!n.isFinite() || length ≈ 0) continue;                //    退化 → 丢弃（fail-closed）
            for (i in 0..3) uv[i] = atlasUV_to_spriteLocal(q.packedUV(i), q.sprite());  // ③ UV 换到 sprite 局部
            spriteId = spriteTable.intern(q.sprite());                // ④ 装表（增量下发，§4.3）
            emit Quad(p0..p3, uv0..uv3, n, spriteId);
        }
    }
}
→ 顶点归一化到格内局部 [0,1]（超出格的部分：顶点保留原值，命中点用第一步的格 bbox 截断）
→ spriteTable 对每个新 intern 的 sprite 读 mip 0 的逐 texel alpha（MixIn 读 originalImage）
```

**四个新前提（必须实现，否则本版白做）**：

1. **种子用 `state.getSeed(pos)`，不是固定常量**。vanilla 自己就是 `setSeed(state.getSeed(pos))`
   （`BlockRenderDispatcher.renderBreakingTexture` 内，与 `collectParts` 同处一个调用序列）；
   位置相关的变体会因此选中与实景一致的模型。用固定种子（如 42）会让这类方块拿到**与实景不同的**
   模型 → 几何对不上；
2. **必须在客户端线程取模型 + 按 `BlockState` 缓存**。`getBlockModel` 依赖 `ModelManager`
   （`onResourceManagerReload` 填充），而 `MemoryCellReporter.tick(ServerLevel)` 跑在**服务器 tick**
   上；`collectParts` 与资源重载并发不安全。做法：首次遇到某 `BlockState` 时经
   `Minecraft.getInstance().execute(...)` 在客户端线程计算，写进并发缓存；之后命中缓存零开销。
   方块种类数是几十量级，缓存后成本可忽略。**注**：记忆侧本身就是客户端进程
   （`StevexTestClient implements ClientModInitializer`），模型系统可用；
3. **模型未就绪 → 跳过该格，绝不回退到拾取盒**。启动早期 / 资源重载窗口内 `getBlockModel` 会回落到
   missing model（quad 数 = 0）→ 走 §4.1 第 5 步自动排除（欠删，安全方向）。**回退到拾取盒等于把 §0 的
   误删通道原样放回来**，明确禁止。同理禁止"alpha 表不可得时按整面全通过处理"——那是 `G ⊋ R`；
4. **alpha 表按 `sprite` 缓存、随 sprite 表增量下发**（§4.3）。单张表的长度 = `width × height` 字节
   （普通 16×16 = 256 B，高清资源包更大 → 见 §4.3 的压缩选项）。**动画贴图**按当前帧建表
   （`SpriteContents.isAnimated()` / `getUniqueFrames()`），并在帧切换时使该 sprite 的表失效重发；
   若暂不实现帧切换，退化为"按首帧建表 + 该族欠删"（安全方向，记为 §9）。

成本 = 每 `BlockState` 一次烘焙遍历（按 `BlockState` 缓存后失效），加上每张 `sprite` 一次的 alpha 读数
（按 `sprite` 缓存后失效）；毫秒级。

### 4.3 cells 文件格式 v4（几何段：quad 面清单 + **增量式** sprite 表）

文件仍走原路径/原 magic，version 常量升 **4**；v1–v3 解析路径不动（旧文件 → 几何段恒空，行为等同 v2.36）。

**拆成两个文件**——quad 段引用 sprite，而 sprite 的 alpha 表体积大且**几乎不变**，混在一起会让每次
重写都重发整张表（每张 16×16 表 256 B × 数百张 ≈ 数十 KB/次）。因此：

- **`memory_sprites.bin`（新增，独立文件）**：sprite alpha 表的**全量快照**，只在**表内容变化时**重写
  （即"首次用到某张新 sprite"时，暖机后是每数百帧一次）；
- **`memory_cells.bin`**：几何段照旧随 cells 重写，但只引用 sprite 的**下标**（int），不带 alpha 字节。

#### 4.3.1 `memory_sprites.bin`

```
magic "SSPR"  version=1
long   epoch                 ← 记忆侧进程启动 / 资源重载时重新生成的随机 long
int    count
count 条，每条：
         ushort nameLen + UTF-8 sprite 名（如 "minecraft:block/oak_planks"，即 atlas 标识）
         ushort width；ushort height
         byte   flags        ← bit0 = OPAQUE（全表 alpha = 255，后面不跟字节）
                               bit1 = RLE（alphaBytes 是游程编码；否则为 width×height 原始字节）
                               bit2 = ANIMATED（只写当前帧，帧切换时靠 epoch 变更重发）
         alphaBytes          ← mip 0、逐 texel、行主序；Opaque 时为 0 字节
```

- **`epoch` 的语义**：sprite 的**身份**用 `name` 字符串（跨进程稳定，采集侧缓存因此**跨记忆侧重启存活**）；
  `epoch` 只用于**传输层一致性**——一个 cells 文件引用的下标，只保证对**同 epoch** 的 sprite 表有效。
- 写入次序硬约束：**先写 sprite 文件（新 epoch + 全量表）、再写 cells 文件**。反序会出现"cells 引用
  新 epoch 的下标、磁盘上却还是旧 epoch 的表"的窗口。
- **Opaque 标志是主力压缩**：栅栏/铁栏杆/墙/压力板/台阶这类"细盒子 + 不透明贴图"的本版主交付物
  全部命中 Opaque → **0 字节 alpha**；只有真正的镂空贴图（玻璃板、睡莲、十字植物）才付 256 B。

#### 4.3.2 `memory_cells.bin` v4 的几何段

```
[..]    long epoch                                   ← 新增：本文件引用的 sprite 表 epoch
        int  shapedCount                             ← 几何段
        shapedCount 条，每条：
          long BlockPos.asLong（该格）
          ushort blockIdLen + UTF-8 block 注册 id      （采集侧据此路由判据场 + 定 alpha 阈值，见 §5.2）
          byte quadCount
          quadCount × {
            4 × (3 × float)   顶点 p0..p3，格内局部 [0,1]，小端
            4 × (2 × float)   顶点 UV，**sprite 局部** [0,1]，小端（记忆侧已从 atlas UV 换算）
            3 × float         单位法线（自算，§3.4）
            int               spriteIndex（本 epoch 的 sprite 表下标）
          }
```

- **每条 quad 96 B**；一个栅栏格（柱 + 横杆 + 连接臂）约 10~20 条 → 每格约 1~2 KB；数百格 → 数百 KB。
  **量化打包（顶点 `short` 1/2048 格、UV `ushort`、法线 3×`byte`、spriteIndex `ushort`）可压到约 46 B/quad**，
  定为**实施期按实测文件体积决定的优化项**（§10 第 14 条），默认先上 float32 以保证正确性；
- **顶点不做 clamp**：超出格的部分保留原值，命中点由第一步的格 bbox 截断（与"只数整格内像素"的口径一致）。
  这一点与盒表示不同（盒表示对盒做了 clamp，因为盒参与比较基准），quad 表示下比较基准是命中 `t`，
  截断只需作用在"是否计入该格"上。

#### 4.3.3 采集侧的 sprite 表缓存（增量语义的落点）

采集侧持有 `Map<String, SpriteAlpha>`（**按 name，跨 epoch 存活**）+ `epoch` + `int[] indexToName`：

```
读 cells 文件：
  if (cellsEpoch != cachedEpoch) → 载入 memory_sprites.bin
       ├ 其 epoch == cellsEpoch → 重建 indexToName（本 epoch 首次，一次 I/O）
       └ 其 epoch != cellsEpoch → **fail-closed**：本轮几何段整体跳过（欠删），不猜、不缓存
  逐 quad 取 spriteIndex → indexToName → name → Map 命中（暖机后**零 I/O**）
       └ name 不在 Map → 该 **quad 不参与**（fail-closed，欠删），绝不当成全通过
```

- **增量的实际效果**：一张 sprite 的 256 B 只在其**首次被 intern 时**写一次；之后所有 cells 文件重写
  （每次方块增减都发生）都只带 4 B 的下标，采集侧也只在 epoch 变更时读一次 sprite 文件。这正是
  "增量式 sprite 表"的含义——**传输按需、缓存跨帧跨重启**；
- `memory_sprites.bin` 的原子写/mtime 门控/半截写防护与 cells 同套机制；epoch 不匹配时**只降级不误删**。

#### 4.3.4 其余约定（沿自 v3）

- **`blockId` 是承重字段，不是诊断字段**：判据场路由**和 alpha 阈值的确定**都必须在**采集侧**做
  （§5.2），因为 `ChunkSectionLayer` 的选择依赖**采集侧**的客户端设置（`cutoutLeaves`）。**不可**改成
  "记忆侧算好渲染层标签下发"——两个客户端的该设置可以不同，会让路由与"采集侧真实写的场"错配；
- 上报**无需携带 state 属性**：`getChunkRenderType` 内部按 **`Block`** 查表（`TYPE_BY_BLOCK`），
  唯一的 state 依赖是 `LeavesBlock` 看客户端的 `cutoutLeaves`、且树叶是满格不进几何段。故采集侧
  `Block.defaultBlockState()` 即可还原渲染层（§5.2）；
- 半截写防护/原子写/mtime 门控/内容指纹（现含 `Segments` 相等比较）需把几何段并入指纹集合与
  `writeAtomic` 布局；**sprite 段另立指纹**（它变化频率远低于 cells，两者分别门控，避免 sprite 变化
  连带触发不可必要的 cells 重写）；
- **`ShapedCell` 只含通过 §4.1 全部判据的格**——`hasBlockEntity()` / `RenderShape != MODEL` /
  模型 quad 数 = 0 / 全部 quad 法线退化 的格**根本不进文件**，故采集侧不需要任何额外的排除逻辑。

### 4.4 含水（waterlogged）非满块归属

次序化处理，修正 §1.3 缺陷：一个格 = 方块本体 +（可能）水。

- 本体是满格透明（玻璃块等可水logging 的极少）或纯水格 → 走 translucent 水段（整格 = 水的判据成立）；
- **本体是非满形状（栅栏/台阶/玻璃板…waterlogged）→ 只进几何段**（按本体 id 路由，§5.2）：
  - 水 drained、本体还在：几何段的"本体消失"判据不成立 → 保活 ✓（本体仍写它的层）；
  - 本体被打掉、水还在：本体的层上整格越票 + 射线命中本体 quad（掩码通过）→ 判本体消失，置空后水由正向增量在后续帧补回；
  - 本体与水的消失互为独立证据，不再互相误删。

### 4.5 兼容

- v4 新读方读 v1–v3：`shapedCount` 缺失 → 几何段空，行为等同 v2.36（无迁移负担）；**同时不看
  `memory_sprites.bin`**（旧文件不引用它）；
- **sprite 文件缺失 / epoch 不符**：几何段整体跳过 → 非满方块整体欠删（安全方向）。这与"旧版文件"
  是同一条降级路径，无需额外处理（§4.3.3）；
- 旧读方读 v4：版本不支持 → 解析失败、保留旧 mtime 只增不删（与 v2/v3 升级同语义，两端同仓同发）；
- **记忆侧已升 v4、采集侧未升（v3 窗口）**：几何段不存在 → 非满方块整体欠删（安全方向），但
  **waterlogged 非满块仍按 v2.36 分进 translucent 水段**，§1.3 的活本体误删缺陷在该窗口内照旧存在
  （既有行为，非本版引入；见 §9）。**运维结论：两端同批部署**；
- 记忆侧离线 → 无 cells → 无删除证据（优雅降级，同 §7.11）。

## 5. 采集侧：解析 → 判据场路由 → 判定 API

### 5.1 解析（MemoryCellsReader）

`CellsData` 增 `List<ShapedCell> shapedCells` + `long spriteEpoch`，并新增一份 **sprite 表缓存对象**
（§4.3.3）：

```java
record Quad(Vector3f[] vertices, float[] uv, Vector3f normal, int spriteIndex)   // §4.3.2
record ShapedCell(BlockPos pos, String blockId, Quad[] quads)
record SpriteAlpha(String name, int width, int height, byte[] alpha)            // 展开 RLE 后
final class SpriteTableCache { long epoch; String[] indexToName; Map<String, SpriteAlpha> byName; }
```

version ≤ 3 → `shapedCells` 空、`spriteEpoch` = 0，行为等同 v2.36。mtime 门控/半截写防护沿用；
sprite 文件独立门控（§4.3.4）。

### 5.2 判据场路由（与 §7.12 同一把尺，逐格在运行时决定）

几何段条目现实写哪张场，由**现实渲染层**定——沿用现成的 `isSemiTransparentLayer` 思想
（[ObjectResolver.java:592-603](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ObjectResolver.java#L592-L603)）。
几何段条目**无流体**，只查方块渲染层：

```java
Block b = BuiltInRegistries.BLOCK.getValue(Identifier.tryParse(blockId));
if (b == null) continue;   // ← fail-closed：采集侧无此方块（模组不一致）→ 该条欠删
ChunkSectionLayer layer = ItemBlockRenderTypes.getChunkRenderType(b.defaultBlockState());

switch (layer) {
  case SOLID           → alphaThr = 0f   （无 ALPHA_CUTOUT，掩码恒通过）
                         main 场判（任意图形配置，testShaped 的 main 变体）
  case CUTOUT          → alphaThr = 0.5f
                         main 场判（任意图形配置，testShaped 的 main 变体）
  case TRANSLUCENT     → alphaThr = 0.01f
                         Fabulous && hasTranslucentDepth && translucentEnabled → translucent 场判
                         !Fabulous                                              → main 场判（Fancy/Fast 写 main）
                         Fabulous && (无第二路 || !translucentEnabled)          → 该条欠删（空集）
  case TRIPWIRE        → 该条欠删（本版几何段不含绊线，§4.1 第 6 步已排除；兜底防御）
}
```

**★ 同一次路由顺带定出该条的 alpha 阈值**（本版新增，取值全部实测自 `RenderPipelines` / `terrain.fsh`）：
`ChunkSectionLayer.pipeline()` 决定 `ALPHA_CUTOUT` 宏是否存在及其值，`terrain.fsh:94` 的
`if (color.a < ALPHA_CUTOUT) discard;` 就是"该 texel 写不写深度"的判据。

| `ChunkSectionLayer` | 管线（`ChunkSectionLayer:8-11`） | `ALPHA_CUTOUT` | 掩码判定 |
|---|---|---|---|
| `SOLID` | `SOLID_TERRAIN`（`RenderPipelines:141`） | **无 define** | **全通过**（不 discard，任何 alpha 都写深度） |
| `CUTOUT` | `CUTOUT_TERRAIN`（`:148-150`） | **0.5** | `alpha ≥ 0.5` |
| `TRANSLUCENT` | `TRANSLUCENT_TERRAIN`（`:151-157`） | **0.01** | `alpha ≥ 0.01` |
| `TRIPWIRE` | `TRIPWIRE_TERRAIN`（`:165-171`） | **0.1** | 不适用（本版几何段不含绊线，§4.1 第 6 步） |

> **这纠正了上一版的说法**：上一版按"SpriteContents 里存的 0.1 阈值"讨论档 3，隐含"所有层共用一个阈值"
> 与"TRANSLUCENT 不做 alpha test"。**两句都错**——`TERRAIN_SNIPPET`（`RenderPipelines:35-40`）固定用
> `core/terrain`，其 `main()` 的 `#ifdef ALPHA_CUTOUT` 对 **CUTOUT 与 TRANSLUCENT 都生效**，只是阈值不同。
> 故 alpha 掩码对**所有**非 SOLID 层都必须生效，且阈值**逐层不同**——这正是"掩码按层阈值判定"而非
> "整面参与/不参与"的原因。
>
> **阈值随 `blockId` 的 `Block` 查表而来，故每格只有一个阈值**（一个 `BlockState` 整体落在一个
> `ChunkSectionLayer`），capture 侧按格解析一次即可，逐 texel 只做一次字节比较。

**两处相对上版的 API 更正（1.21.11 实测）**：

1. **`getChunkRenderType` 返回 `ChunkSectionLayer`，枚举只有 4 个值：`SOLID / CUTOUT / TRANSLUCENT /
   TRIPWIRE`**。上版写的 `CUTOUT_MIPPED` **在本版本不存在**（`CUTOUT_MIPPED` 是旧版 `RenderType` 时代的
   东西），照写会编译不过；
2. **签名是 `getChunkRenderType(BlockState)`，且内部按 `Block` 查表**（`TYPE_BY_BLOCK.get(state.getBlock())`，
   唯一例外是 `LeavesBlock` 看客户端 `cutoutLeaves` 设置）。所以几何段**只带 blockId 是够的**——
   `b.defaultBlockState()` 即可还原；树叶是满格、不进几何段，那个例外不出现。

**路由必须在采集侧做**（不能改成"记忆侧算好标签下发"）：`cutoutLeaves` 是**采集侧客户端的视频设置**，
而读的深度缓冲也是采集侧渲染出来的。两个客户端该设置不同时，记忆侧算的标签会与"采集侧真实写的场"错配
→ 路由到错误的场 → 假消失。§4.3 因此把 `blockId` 定为承重字段。

### 5.3 DeletionJudge 泛化

把 `judge` 的逐格/逐像素循环泛化：记忆格可带**可选几何**（null = 整格，现 full-block 行为；非空 =
**quad 面清单 + 该格的 alpha 阈值 + 该格的 sprite 表视图**）。越票判据不变，第二步对带几何的格追加
射线-三角形求交 + 掩码判定（§3.2）+ 弦长 ε 规则（§3.5）。对外暴露：

```
test(snap, unproj, mainCells, thr, terrain)                    // 不变：整格、main 场
testTranslucent(...)                                           // 不变：整格、translucent 场
testShaped(snap, unproj, shapedCells, field, thr, terrain,
           spriteTable, alphaThrPerCell)                      // 新增：quad + 掩码；field ∈ main/translucent
```

**本次新增的求交内核**（替代原"形状盒并集 + `slabInterval`"）：

```
for each 候选像素 p:
  ray = (camPos, normalize(unproj(p) - camPos))
  best = -inf; valid = false
  for each quad q in cell.quads:
     if (dot(q.normal, ray.dir) >= 0) continue              // 背面：剔除开，不写深度（§3.2 第 1 条）
     (t, w0, w1, w2) = MöllerTrumbore(ray, q.p0, q.p1, q.p2)   ∥ (q.p0, q.p2, q.p3)
     if (!hit) continue
     if (!inCellBox(hitPoint, cell)) continue               // 第 3 条：只数整格内
     alpha = spriteTable.sample(q.spriteIndex, interpolate(q.uv, w))   // 第 2 条：重心插值 → texel → 查表
     if (alpha < alphaThr) continue                          // discard：不写深度
     best = max(best, t); valid = true
  if (!valid) → 该票作废（§3.2 2a）
  else if (Z >= best + δ_cell) → 越票（§3.2 2b / 2b-δ）
```

> `δ_cell = min(δ_global, κ · h_max)`，`h_max = max{cell.quads 顶点的 y}`，`κ = 0.5`——**每格算一次**
> （不进像素循环）。取 `h_max` 的顶点通道为 `v[1]/v[4]/v[7]/v[10]`（§3.2 2b-δ）。

**比较基准按有无几何分两路**（§3.1/§3.2）：无几何的格仍用**整格远面 + δ**（`Z ≥ t_far − δ`，现行为不变）；
> 注：该路的格是**满格**（几何 = 整格盒 ⇒ `h_max = 1` ⇒ `δ_cell = δ_global`），故逐格化对它**恒等**，
> 无需也不应改动。
带几何的格改用**真实命中出口 + δ**（`Z ≥ t_shape_exit + δ`，`t_shape_exit` = 上式的 `best`）。translucent
场读 `translucentDepthAt`、main 场读 `depthAt`，哨兵语义（translucent `t==m` 编码"无半透明在前"）与
§7.12 完全一致。满格方块走同一泛化入口时几何退化（全部命中、`t_shape_exit = t_far`），单条代码路径。

在 §7.12 两段路由（[ObjectResolver.java:156-183](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/ObjectResolver.java#L156-L183)）
后追加几何段路由：`dimensionOk` 时按 §5.2 把 `shapedCells` 分成 main/translucent 两批，各调
`testShaped`，结果并入 `deletions`；Fabulous 降级批次直接空集。诊断日志沿用"main/translucent/geometry
各判删数"。

## 6. 记忆侧 DeletionApplier：语义转折（唯一"放宽"点）

判定已由采集侧几何过滤证明（deletions 只含通过过滤的位置），记忆侧**不重复判据、只执行**，但内容守卫
须从"整类拉黑"升级为"诚实几何判定"：

- 主循环守卫由 `isDeletableContent` 扩为 `isDeletableContent ∪ isShapedDeletableContent`（§4.1 同一谓词）：
  **当前该格内容属于 cells 会上报的可删类才置空**（含被几何过滤证明消失的非满方块），否则跳过、交放置/更新路径；
- 相机格快路径仍只删实心不透明（v2.22 语义，不变）；
- `currentTerrain` 跳过集、幂等、清 BE（`clearStale`）、限活动维均不变。删除非满格时 `clearStale` 自然清该格
  BE（本版几何段不含 BE 方块，故无 BE 清空路径新增）。

> **守卫的正确性依赖 §4.4 的分段次序，必须一并成立**。`isDeletableContent` 对**任何含流体的格**直接返回
> true（`BlockStateUtil:85-86` 的 `if (!fluid.isEmpty()) return true;` 短路）。因此"含水非满块不会被整格
> 误删"**不是**守卫本身保证的，而是靠 **§4.4「先形状后流体」**——waterlogged 栅栏只进几何段、不进
> translucent 水段，于是"水段格被证明消失"必然意味着那格**没有方块本体**，整格置空才成立。两处改动必须
> 同批落地：**只做 §4.4 不改守卫** → 守卫对几何段格过宽（但几何判据已证明本体消失，实际无害）；
> **只改守卫不做 §4.4** → v2.36 的活本体误删缺陷照旧对 waterlogged 格生效。§10 第 6 条为该项回归。

防误删的职责整体由几何过滤承担：只要 cells 只含可删类、judge 只对穿过被记住形状的越票计数，applier 按
同一谓词放行就是安全的（§8 论证）。

## 8. 正确性论证

论证结构：先证"活体不可能被判删"，再证"真消失仍能被判删"，最后列前提。

**① 活体不可能被判删（核心）**。设活体方块真实写深度的像素集为 `R`，我们算出的几何为 `G`，二者同状态。
活体在某像素被记为越票需同时满足 2a、2b：

- 2a 要求"存在 **有效命中**"。由 §3.4 的构造 `G = R`（并且 `G ⊆ R` 始终成立），该命中必然是**真实写入
  深度**的那一次绘制；
- 于是该像素的现实深度就是该几何的表面距离：`Z = t_surface = ` 某次真实命中的 `t`；
- 2b 要求 `Z ≥ t_shape_exit + δ`，而 `t_shape_exit = max{有效命中 t} ≥ t_surface`，故
  `Z ≤ t_shape_exit < t_shape_exit + δ` → **2b 恒不成立**。

两条不可能同时成立 ⇒ **活体零越票 ⇒ 不可能进 deletions**。注意这一步**只用到 `G ⊆ R` 与
`Z = t_surface ≤ t_shape_exit` 两个条件**，与形状厚薄、δ 取值、视角全部无关——这正是上版"第一步整格
远面排除"做不到的（那条依赖"形状厚度 ≥ δ"，是**有条件**的，§3.3 已记录修正）。

- **`G ⊆ R` 的保证**：§3.4 的表示**逐条对齐渲染管线**——顶点直接取 `BakedQuad`（不做任何近似）；
  背面由下发法线剔除（剔除开着，背面不写深度）；alpha 由逐 texel 掩码 + 该层阈值判定（与
  `terrain.fsh` 的 `discard` 同判据）。任何一环拿不准（法线退化 / alpha 表不可得 / epoch 不符）都
   **丢弃**而非放行 → `G` 只会更小，方向不被破坏。
- **前提 A（仍待验证）**：活体表面确实写入其所路由的那张深度场（§5.2），即 `Z = t_surface` 成立。
  若不成立（如 CUTOUT alpha-test 表面未写 main 深度）→ 读到的 `Z` 是背景 → 活体越票且 2a 有有效命中 →
  **误删活体**。§10 第 2 条"场构成探针"是**一票否决的 Phase-0**，先于一切功能回归。
- **前提 B**：状态未过期（`G` 与 `R` 同状态）。状态过期时由可见集闸门兜底（§3.4/§9）。

**② 真消失仍能被判删**。方块已消失时，其原本占的位置无表面写入 → 射线穿过的像素读到**背后的**深度
（`Z` = 背景距离，通常 ≫ `t_far` > `t_shape_exit`）→ 2b 成立；且该射线仍穿 `G`（`G` 是记忆中的形状）
→ 2a 成立 → 计一票。与 §7.11 相同：逐块判定天然覆盖"背后是天空 / 背后是不透明块 / 部分遮挡"三况，
只需 ≥ `removalPixelThreshold` 像素作证。

- **代价**：`t_shape_exit + δ` 比原来的 `t_far − δ` 更严，故"背后紧贴一个表面"（背面距离落在
  `[t_shape_exit, t_shape_exit + δ)`）时会欠删。这是**有意的**：宁欠勿过，且该窗口只有 δ 宽。
  > **2026-09-11 补**：这个"有意的欠删窗口"在 δ 逐格化后随格缩到 1/128（§3.2 2b-δ），正是为了让
  > **贴地平铺贴花**类（红石粉/落叶）那唯一一个"背后紧贴表面"的真实用例能落回可判范围——它此前
  > 100% 落在窗口内，即该窗口对本类方块是从 0 到 1 的全部，不是边缘代价。

**③ 三重约束与排水修正**。

- **applier 三保险**：删格受 (a) 采集侧几何过滤证明、(b) `currentTerrain` 跳过集、(c) 单一
  `isShapedDeletableContent` 谓词放行 三重约束。**注意 (c) 的正确性依赖 §4.4 的分段次序**
  （`isDeletableContent` 对含流体格无条件放行，§6 已记录该耦合）；
- **含水修正**：本体与水的消失各自独立判定，消除 §1.3 的活本体误删；
- **`INVISIBLE` 修补**：§4.1 第 2 步顺带修掉 v2.23/v2.36 "零足迹方块进 translucent 段被整格过投票"；
- **欠删方向**：法线退化 / alpha 表不可得 / epoch 不符 / 模型缺失的方块、远距、被挡、占屏不足、状态
  过期型，全部欠删（宁欠勿过），与 §7.11/§7.12 同哲学。**四次修订把"欠删族"从"按方块类别"缩到了
  "按运行时故障"**——斜薄板、作物、睡莲这些曾经的整类欠删**已转为可判**（告示牌不在此列：
  它属于 `hasBlockEntity()` 排除族，与几何表示无关，见 §2.2）。

**④ 本版**撤回**的旧论证**（两轮）：① 上版写"拾取盒 ⊆ 真实渲染足迹 → 活体几何区像素第一步被保活"。
前半句被 §0 证伪（栅栏 2×、红石线 5×），后半句是**有条件的**（依赖厚度 ≥ δ，§3.3）——重写为
`G ⊆ R` + 2b 基准；② 三次修订写"档 2/档 3 是几何源无法在不误删前提下表达的族，是有意付的代价"。
**四次修订证明那是表示能力不足，不是几何源的极限**：换成 quad + alpha 掩码后 `G = R`，两条族一并转为
可判（§3.4）。教训与 ① 相同——**"做不到"的结论要先问是"哪一层"做不到**。

## 9. 已知边界与限制

- 信号缺失族（绊线/绊线钩）**不进几何段**（见 §2.2，是**范围**而非缺漏，换任何几何源都救不了）——
  其删除能力 v2.37 七次修订起由**独立通道**（§15，真实世界状态直读）提供，不走几何判据。该通道的
  已知边界：候选集受 `removalMaxRayDist` 限制（半径外的镜像绊线不被校正，欠删）、区块未加载时**不裁决**
  （§15.4 P1）、裁决→执行之间有一个文件往返的时序窗（§15.6 第 8 行，与现有 deletions 同款）；
- **~~档 2/档 3 排除族整体欠删~~ → 已消除（四次修订）**：非轴对齐 quad（十字植物/草/作物/
  斜坡铁轨）与 alpha 镂空贴图（睡莲等）在四次修订后**精确可判**（§3.4）。
- **掩码保真度的三个已知差距**（不影响 `G ⊆ R` 的方向保证，只影响误判方向上的保守度）：
  ① **mip 级**：我们建模 mip 0，实际渲染在远处用 mip > 0。vanilla 的 alpha 感知降采样
  （`SpriteContents.alphaCutoffBias` / `MipmapStrategy`）缩小但不消除差距。**方向不确定**，但该差距
  只在"远的连 2 px 都占不到"时出现 → 被 `removalPixelThreshold` 与 96 m 上限自动摊薄；
  ② **动画贴图**：帧切换改变本应通过掩码的 texel。按首帧建表 → 该族欠删（安全）；按当前帧建表 →
  帧未同步的窗口内方向不确定（窗口 ≤ 一个 sprite 表的重发周期）；
  ③ **资源包不一致**：见下一条；
- **`vertexColor.a ≡ 1` 的假设**：掩码只建模贴图 alpha。若某些方块带逐顶点 alpha，则该类欠删（安全），
  §10 第 2 条探针核对；
- **红石线/铁栏杆/玻璃板/栅栏/墙/台阶/压力板等已从"欠删"转为"精确可判"**——换几何源的直接收益
  （原"待 §10 扫描复核拾取盒 ≈ 渲染"随几何源更换取消）；
- 非满形状 BE 方块整体移除仍欠删（本版排除，§2.2）；配套"完整删除"路径 = **v2.38 方案 B**，分析见 §13；
- **模型未就绪窗口**（启动早期 / 资源重载中）：`getBlockModel` 回落 missing model → quad 数 = 0 →
  §4.1 第 5 步排除（欠删）。**明确禁止回退到拾取盒**——那会把 §0 的误删通道放回来。记忆侧启动后
  首次触发上报即恢复正常，窗口是瞬时的；
- **资源包 / 模组不一致**：采集侧与记忆侧资源包不同时，同一 `BlockState` 的模型几何可以不同。
  四次修订把这一前提**加重了一档**：现在不一致的不只是 quad 顶点，**alpha 掩码也来自记忆侧的资源包**
  （§4.2 的 MixIn 读的是记忆侧进程内的 `SpriteContents`），而采集侧读的是**采集侧**深度场——两侧贴图
  不同 → 掩码判定的"通过/丢弃"与实景渲染的 `discard` 可以逐 texel 不同 → **方向不确定**。
  与 v2.23/v2.36 的差异是：那两版的几何源是**服务端 `getShape`**（不依赖资源，两侧天然一致），
  本版改吃**客户端资源**后**新增了"两侧资源包须一致"这一部署前提**，且是**强制**而非建议。不一致时
  几何与掩码双双错配、方向不确定 →
  需求侧约定：**两侧装同一资源包**，并在 §10 第 3 条扫描里打印记忆侧模型来源（vanilla / 资源包）
  以便发现错配；
- **水的整格判据未改（本版范围外，待实测）**：水不在方块模型系统内——`Blocks.WATER` 的
  `getRenderShape` 返回 `INVISIBLE`（`LiquidBlock`），渲染走 `LiquidBlockRenderer` 且
  `MAX_FLUID_HEIGHT = 0.8888889F`、还要对四邻插值出四个角高度。故 translucent 水段**沿用整格 bbox**，
  对水是**过估计**：水面以上 `1 − h` 的那条带内，射线不终止 → 越票。静止水 `h ≈ 0.889`（带 ≈ 11%），
  **流动水 `h` 可低到 ≈ 0.111（带 ≈ 89%）**，暴露大得多。**这条是 v2.36 的既有行为，非本版引入**，
  且大概率被 `currentTerrain` 可见集闸门挡住（活水本帧可见 → 跳过）。**本版明确不改**（§7 决策 J）：
  水判删既已由 v2.36 §7.12 交付，本版范围就限定在"非满形状方块"，不动水。是否引入 `FluidState` 作为
  第三几何源留作独立课题（§10 第 13 条仅作可选观测，非本版验收项）；
- 模型几何为空（quad 数 = 0、全部法线退化、或 sprite alpha 表不可得）的方块欠删；几何极小的作物类
  多因证据不足欠删（安全方向，不误删）；
- **MixIn 依赖**：本版新增唯一一个 MixIn（`SpriteContents.originalImage` accessor，§4.2）。若 MixIn 在
  某环境下未生效，**读 alpha 会失败** → 本设计让它 fail-closed（该 quad 不参与 → 欠删），而不是回退；
  这是本版**唯一一个"该存档/该加载器/该版本上可能整体空转"的依赖点**，列入 §10 第 1 条冒烟检查；
- **sprite 表失联**：`epoch` 不匹配（记忆侧重启/资源重载的瞬间，或两端升级不同步）→ 该轮几何段整体
  跳过（欠删，安全）。窗口 = 一个 cells 写周期，量级毫秒~秒；
- **细薄物（火把/按钮/红石中心点）另有基准变化带来的欠删**：2b 改用 `t_shape_exit + δ_cell` 后，背后紧贴
  表面的情形（背面距离落在 `[t_shape_exit, t_shape_exit + δ_cell)`）会欠删，窗口宽 δ_cell，有意保守。
  **其中"贴地平铺贴花"类（红石粉/落叶）是该窗口的全集而非边缘** ⇒ 已由决策 O 单独处理；火把/按钮是
  立体形状（`h_max = 1`）⇒ `δ_cell ≡ 0.05`，行为不变；
- 倾斜视角下极薄物体：真实形状 + 弦长 ε 规则仍可能贴边欠删（工程可控，靠验证清单覆盖）；
- 距离 > `removalMaxRayDist`=96 / 占屏 <2px：沿用整格判据固有边界（深度量化超 δ 可靠区 / 证据不足）；
- **细薄物远距欠删（§7 H 标定前默认成立）**：火把/按钮/红石中心点的相交证据像素随距离快速衰减，中远距常
  < 全局阈值 → 判得出、删不动（欠删，不误删）；按 §10 第 4 条标定决定是否放宽近距。
- **CUTOUT → main 前提未过时的整体降级**：若 §10 第 2 条探针显示 CUTOUT 不入 main 深度场，栅栏/铁栏杆/
  门/玻璃板类（本版主交付物）整体欠删，直至采集深度场构成修正；属"前提未证"而非设计失效。
- **状态过期型大盒残余（§3.4(b)）**：记忆连接态过期且该格本帧**不在可见集**（刚出视野/屏缘/极远）时，
  过期大盒的空区越票有可能不被可见集跳过 → 极少数误删；实践风险低，靠"可见集跳过 + 连通态刷新帧率"摊薄。
- 本判据只证明"整格 bbox 内无被记住几何"——不证明格内**新增**了更薄的其它内容（新增由正向增量在后续帧覆盖）；
- **升级窗口内的 waterlogged 格**：记忆侧已升 v4、采集侧仍是旧版时，v3 文件无几何段 → waterlogged
  非满块仍按 v2.36 分进 translucent 水段 → §1.3 的活本体误删缺陷在该窗口内**照旧存在**（属既有行为，
  非本版引入）。反方向（采集侧新、记忆侧旧）由 §4.5 的版本门控挡住 → 只增不删。窗口 = 两端升级之间，
  建议同批部署；
- **~~档 1 缺面元素的构造前提~~ → 已消除（四次修订）**：模型元素省略 `faces` 时该位置**没有 quad** →
  2a 无有效命中 → 作废，构造上安全（§3.4）。§10 第 3 条相应扫描降级为观测项；
- 旧 cells 文件/旧读方组合只增不删（与历次版本升级一致）。

      这是唯一一处对"原本已可删"的方块发生了 δ 变化的角落。
17. **★ 深度残差实测与 δ 噪声下界的标定（决策 Q 的承重输入，2026-09-11 新增；同日六次修订改写）**：
    - 对"**射线命中形状且该格判定为仍在**"的像素，统计残差 `e = Z − t_surface`（`t_surface` = 记忆几何
      在该像素上的解析交点距离）的**分布**。注意它**不必恒 ≤ 0**：`Z` 是**量化观测**、`t_surface` 是
      **解析量**，`e` 的对称界是 **0.5·Δz(1ULP) = 5.96e-7·z²**（正负皆可）；
      > 旧稿此处要求"恒 ≤ 0 且紧贴 0"——那是把 `Z` 与 `t_surface` 都当成了同源量化量。2b 的比较是
      > **量化观测 vs 解析阈值**，故**正残差必然存在**，且不需要它是"系统性偏差"。决策 P 的"不需要
      > 下界"结论由此被 **决策 Q** 取代（§3.2 2b-δ / §7 决策表 Q 行）。
    - **本条的实际产出 = 下界系数 `c` 的标定值**：按 `δ_cell ≥ c·1.192e-6·z²` 取
      `c = ceil(实测 |e| 上界 / (1.192e-6·z²))`，保守从 `c = 1` 起步；若实测 `|e|` 上界贴近 0.5 ULP
      则 `c` 可降到 0.5。同时记录**残差随 z 的实际增长斜率**，与 `视觉api设计方案.md` §4.2 的闭式
      `Δz(1ULP) = 2⁻²⁴·z²/n`（`= 1.192e-6·z²`，与远平面 f 无关）对照——旧稿的 `2^-20·z² = 9.54e-7·z²`
      **比真值小 1.25×**（只相当于 0.8 ULP），不可用；
    - **不得**回退到全局 δ（那会让本条第 16 项的用例重新失效）；
    - 该统计与本条同时给出 δ 的**真实安全下限**与深度侧误差量级，是 v2.39 统一口径的输入之一
      （另一份是 `视觉api设计方案.md` §4.2.1 的 ε 落格误差；两者同源于"最小几何厚度"这一量）。
18. **★ δ 可行窗口闭合时的"不可判"记账（决策 Q 的验收，2026-09-11 新增）**：
    - 构造一个 `z > 81 格`（c=1；若第 17 条把 `c` 标定到 0.5 则临界距离为 `114.5 格`）的睡莲/红石粉
      （站远处看一片红石线或落叶），**在其仍在时**做快照：
      应**不产生任何删除**（该格被记为"2b 不可判"），而不是因正残差越过 δ 而误删活体；

    - 若第 17 条实测 `|e|` 上界远小于 0.5 ULP（`c` 取小），窗口闭合半径随之后移，本条用例的临界距离

## 13. 附录：BE 载体方块完整删除 —— 失败模式分析与方案 B 立项（v2.38）

> 本附录回答审阅轮的两个问题：(1) 告示牌/旗帜/头颅/花盆/装饰陶罐/钟/讲台/箱子/床/潜影盒等
> **带方块实体（BE）的非满块**到底难在哪（§13.1–13.2）；(2) 是否需要把 NBT 内容与方块"绑定在同一
> 份记录里"才能完整删除（§13.3）→ 定案：**不合并文件，用"唯一删除原语"跨通道删除（方案 B，§13.4）**。
> 代码锚点均为现状实现（v2.36）。**完整展开的可实施设计见 docs/BE载体方块减量设计方案.md（v2.38，
> 设计待审阅、未实现），随本附录一并审阅。**

### 13.1 根因：这类格子是"方块 + BE 负载"两条通道的耦合

"完整删除一格"在本系统里 = 让该格可能同时躺着的<b>三份记录</b>一并、永久失效。而这三份记录分属
两个侧、三种落盘语义，删除能力各不相同：

| 通道 | 侧 | 记录内容 | 落盘方式 | 现状删除能力 |
|---|---|---|---|---|
| terrain（方块本体） | 采集写/记忆读 | block + state | **每帧整体覆写 = 本次可见集**（[VisionTerrainStore.java:117-143](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionTerrainStore.java#L117-L143)） | 有 deletions + 文件自然缺位 → 能删、且跨重启持久 |
| block_entities（BE 负载） | 采集写/记忆读 | block + state + **nbt**（告示牌文字/旗帜纹样/头颅皮肤…） | **增量累积，只增/改、永不删旧条目**（[VisionBlockEntityStore.java:130-164](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/VisionBlockEntityStore.java#L130-L164)） | 只有 `clearStale`（记忆侧**内存级瞬时**遗忘，[MemoryRestorer.java:120-123](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/MemoryRestorer.java#L120-L123)）→ **删不掉、不持久** |
| containers（L2 容器） | 采集写（交互）/记忆读 | 方块 + BE + **物品** | 交互提交 | 无删除概念；世界为空气时**自足回放**（[ContainerMemoryApplier.java:215-229](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/ContainerMemoryApplier.java#L215-L229)） |

地形通道删得干净，是因为它的**文件本身**反映"最后可见快照"——被删格在文件里天然缺位，重启后全量
重放也不会出现。BE 通道恰恰相反：文件**永不缺位**，且对空位握有回放权威——记忆侧复原对"世界为空气"
的记录**明确放行**（"BE 数据是自身方块的权威来源"，[MemoryRestorer.java:244-247](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/MemoryRestorer.java#L244-L247)）。
这就是对称性断裂：**删 BE 格 = 只删了世界里的方块本体，那条累积 BE 记录没人删得了**。

> 注：此洞对**一切带 BE 的方块**成立（含满格实心熔炉/木桶——它们是现行 cells 可删集），并非 BE 非满块
> 独有；只是满格 BE 数量少、且多被采集侧 STRIP 成元数据空壳（[BlockEntityFieldPolicy.java:76-111](../vendor/stevex-template-1.21.11/src/main/java/name/modid/vision/BlockEntityFieldPolicy.java#L76-L111)），
> 表象被掩盖。v2.38 的删除原语应挂到**现有 deletions 清单**上，天然一并覆盖。

### 13.2 三个具体失败模式

**F1 删不干净 → 复活/闪烁。** 告示牌例：墙上 `oak_wall_sign`、文字"入口"存于 BE 记录。现实中被敲掉 →
采集侧证方块消失 → deletions → 记忆世界置空（`deleteBlock` 只清世界内方块）。但 block_entities.nbt 里
"入口"还在；此后任何触发——同维别处一个 BE 被改（远处箱子被重观察）使文件 mtime 变化，或**服务器重启**
（applied 表清空 → 全量重放）——记忆侧重读时该格世界是空气 → 权威校验放行 → 牌与文字一起放回。下一帧
快照又证它消失又删：**重启后幽灵牌出现、直到 agent 移动触发新快照才再被删**，方块与 BE 两态永不收敛。

**F2 两个权威通道抢同一格。** 箱子：方块本体归视觉 L1（非满、BE、STRIP），内容归 L2 containers.nbt
（交互提交）。即便视觉判据正确证明"现实中箱子没了"并删格，容器通道下一轮 reconcile 看到世界为空气，
就**自足放置箱子方块 + 补挂 BE + 填满记录里的物品**（[ContainerMemoryApplier.java:215-229](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/ContainerMemoryApplier.java#L215-L229)）。
视觉减量与容器复原形成对删/对放的打架。完整删除箱子必须同时废止 containers.nbt 里该 pos 的记录。

**F3 格子语义 ≠ 方块语义，负载不可被几何证明。**
- 告示牌文字/旗帜纹样/头颅皮肤是**观察者可见**（采集 PASS），但对深度场/几何不可见——判据只能证明"牌面
  没了"，**证明不了文字该不该忘**。而删格是整格丢弃：判据一次瞬时假阳性（贴边噪声/占屏抖动）即连带销毁
  用户负载且无法恢复（BE 记录没了，正向通道连"正确内容"都找不回）。欠删至少只留可被下次观察修正的幽灵
  → 安全默认 = **宁留幽灵不删内容**；
- **多格/半格**：床占两格（head+foot，BE 挂 head），现实中半张床被敲 → 判据只证其中一格方块几何消失；
  按逐格置空删掉一格，剩半格既非法 state、又挂 head 的 BE——"床"整体无法用逐格删除表达。双格大箱同理；
- **方块几何 ≠ 该格的视觉形状**：花盆的**形状模型**只有陶盆本体，盆内的花是**方块实体渲染**（按槽位里的
  物品另行渲染），不进 `BlockStateModel` 的 quad 集合。即 §4.2 的几何源对这类格是**系统性低估**（漏掉
  内容部分），且这部分恰恰是"内容"——判据只能证明"盆没了"，证明不了"花该不该忘"。这类"方块+内容"格的
  视觉形状本就不是任何静态方块几何能描述的（严格说这是本方案对带 BE 格必须走 §13 删除原语、而不能只靠
  几何过滤独立的另一条理由）。

### 13.3 是否必须"绑定成一份记录"才能完整删除？—— 否

完整删除的必要条件不是"记录放哪"，而是三性：**原子性**（一次判删覆盖该格全部记录）、**持久性**（跨重启、
跨后续任意 NBT 重写不复活）、**覆盖面**（在 terrain / BE / containers 三通道都生效）。"绑定在一份文件里"
只是达成原子性的一种手段，且较重的实现。候选三条路径：

| | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A 合并文件** | block_entities 并进 terrain.nbt，每格一条 `{block,state,nbt}`，删格 = 删整条 | 原子性靠构造保证；两个 restorer 合一，权威矛盾根除；记忆侧 `StoredBlock` 本就带 nbt（[MemoryRestorer.java:402-406](../vendor/stevex-test-template-1.21.11/src/main/java/com/example/memworld/MemoryRestorer.java#L402-L406)），形状现成 | 大爆炸式重构：文件契约/两个 store/两个 restorer/指纹全动；terrain 稠密每帧覆写 vs BE 稀疏偶发，合并改变写入节奏与体积；**containers 本就是独立交互通道，合并也管不住它** |
| **B 唯一删除原语跨通道**（定案） | **不合并记录，合并"删除"**：现有 deletions 清单提升为唯一删除原语，采集侧在 snapshot 同 tick 把它喂给 BE/容器 store 做持久修剪后再落盘；记忆侧 `clearStale` 保留为即时遗忘 | 改动最小、贴合现有 deletions 通道；对满格熔炉等既有 BE 删除一并收口；三份记录一次失效并写进文件 → 重启不复活 | 要求各 store 提供按 pos 的持久 drop；BE 内容仍只能作为"方块消失的从属品"删除，无独立删除资格 |
| **C BE 存在性绑定 terrain** | BE 记录只在"该格 terrain 块当前存在且类型一致"时有效，sync 时孤儿即弃（不再"空气即放行"） | 规则单一，连 deletions 都不用扩 | 记录生命周期变"间接推导"，触发依赖 terrain 刷新；与现有"BE 记录可自足回放"设计哲学冲突，语义迁移大 |

**定案 = 方案 B**：原子性由"唯一删除原语"保证，而非物理合并；改动最小、贴合现有 deletions 通道；容器
通道本就独立于视觉文件，合并（A）也覆盖不到它，只有显式删除原语能同时命中三个存储。

### 13.4 方案 B 设计（v2.38 范围）

**原则：判据管"方块消失"，原语管"整格消失"。** 一个格子消失 = 判据证明其**方块本体**不再存在于现实
（v2.37 模型几何过滤即可做到，与是否带 BE 无关）+ 删除原语把该格在三个存储里的记录一并持久移除。
BE 负载与容器内容**永无独立删除资格**，只作为方块消失的从属品被清。

实现要点：
1. **扩展判据纳入 BE 格**：`isShapedDeletableContent` 放开 §4.1 第 4 步的 BE 排除（改由 §13 删除原语兜底），
   判据仍只对**方块本体**的几何消失作证——BE 格与普通非满格共用同一几何过滤，无新增判据逻辑；
2. **唯一删除原语 = 现有 deletions 清单**（采集侧 DeletionJudge 产出，已随 terrain.nbt 落盘）：同一 snapshot
   循环里，把 deletions 同批喂给采集侧各 store——`VisionBlockEntityStore` / 容器 store 实现
   `dropPos(dimension, pos)`（下次落盘前从累积表移除该 pos），BE store 在 `sync()` 落盘前应用，容器 store
   在下次 reconcile / 落盘前应用；删除的**持久性由这次修剪落盘承担**（记忆侧无法改采集文件）；
3. **记忆侧**：`DeletionApplier` 的 `clearStale` 保留（即时遗忘世界内 + applied 表）；容器通道 reconcile 对
   "已在 deletions / 世界为空气" 的格跳过放置（把"空气即自足回放"改为"空气且有删除记录 → 不回放"）；
4. **多格/半格语义另办**：床/双箱这类"逻辑物体跨格"不随上述逐格原语自动正确，须配套"格级删除 → 找逻辑
   物体 → 全量删"的归并规则（§13.2 F3），同为 v2.38 范围但独立实现；
5. **内容不可证明性**（§13.2 F3）不因本方案消失——它决定 BE 负载只能从属删除，永远不能反向单独"被证明
   消失"，此边界记为长期语义约束，不是缺漏。

记录清理矩阵（v2.38 生效后）：

| 判据证明 | 删除原语动作 | terrain | block_entities | containers |
|---|---|---|---|---|
| 普通非满块消失 | dropPos(pos) | 置空 | 本就无记录 | 无 |
| BE 非满块消失 | dropPos(pos) | 置空 | **移除 nbt 记录** | 若该格有容器 → 移除 |
| 满格 BE（熔炉等）消失 | dropPos(pos)（挂现有 deletions，随 v2.38 一并收口） | 置空 | 移除记录 | 若该格有容器 → 移除 |

### 14.4 五次修订记录（2026-09-11，红石粉消失无法识别）

**触发**：草丛消失判定在 j 修复后验证通过；随后发现**红石粉（`minecraft:redstone_wire`）无论怎么敲都不被判消失**。

**排查路径（可直接复用的三段切分）**：

| 段 | 判据 | 本轮实测 |
|---|---|---|
| 写方没上报？ | 几何段里有没有该 blockId | ✅ 4 格 `redstone_wire`、56 条 quad |
| 读方没读懂？ | epoch 是否一致、`shaped` 分母 | ✅ epoch 一致、`shaped=0/712 judged`（分母 712 > 0） |
| 判据不成立？ | `h_max` vs `δ`，及判据 2b 的可达性 | ❌ **断点在此** |

**根因**：全部 12 条 quad 都在格内 `y = 1/64 = 0.015625`（实测），而支撑块顶面就是格底 ⇒ 消失后观察面
只比形状远面后退 `1/64·(1/|dy|) ≤ 0.0156`，**恒小于 `δ = 0.05`** ⇒ 判据 2b **按构造不可满足**。
即 §3.2 2b 修好了"活体不被误删"，却让同一批最薄形状的"真消失"永不成立——**同一个数（形状沿视线的
几何尺度 vs δ）的两侧，只检查了一侧**。

**定案**（详见 §3.2 2b-δ / §7 决策 O、P）：

1. **δ 逐格化**：`δ_cell = min(δ_global, κ·h_max)`，`κ = 0.5`，`h_max` = 该格 quad 顶点在格局部的最大 y。
   采集侧就地算，**不动 v4 文件格式、不涉 epoch**。对 `h_max ≥ δ_global` 的形状（草丛/藤/台阶/栅栏…）
   **恒等于旧值 0.05 ⇒ 零回归**；只把 `h_max < δ_global` 的"贴地平铺贴花"类抬到可达。
2. **不补抗噪下界**（决策 P）：深度量化把两面映到同一深度值时观察差为 0 ⇒ 只会欠删，不会凭空造出
   假跳变；前提"反投影无系统偏差"列入 §10 第 17 条实测。
3. **ε 与 δ 解耦**（§3.5 补记）：ε 维持重心空间 `min(w0,w1,w2) < 1e-3`，不随 δ 缩放。

**教训（与 §14.3(b) 同源，且这是第二次）**：`1/16 = 0.0625` 这个"最薄形状"的数在 §3.2 里被**估计**了两次、
承重了两次。第一次它只被用来论证"余量薄"（安全方向，2b 顺手关死）；第二次它让 δ 的**可达性**从未被
检验。**凡承重的几何量必须取自烘焙后的真实顶点**，不得用模型直觉估计。离线工具现已直接打印这一列。

### 15.1 判据分裂：不是"判不出"，而是"判据的输入不存在"

§2.2 第 1 行的排除理由须复述精确：绊线在 **Fabulous** 下画进 weather 目标、**不写任何已读深度场**
（§10.8）⇒ 活体在 main/translucent 场上**不产生可读信号** ⇒ 深度判据下"消失了"与"活着"**不可区分**
⇒ 判消失必误删活体。

由此得到一个此前被"整族排除"掩盖的区分：

| 判据 | 逻辑形式 | 对信号缺失族 |
|---|---|---|
| 深度判据（§7.11 / §7.12 / §3.2） | **间接推断**："我不在有深度的表面上看到它 ⇒ 它可能没了" | 前提（存在深度信号）不成立 ⇒ **恒真**，不可用 |
| 状态直读（本通道） | **直接事实**："该格现在是不是绊线" | 与深度场无关，**可用** |

绊线**不是几何问题**（§2.2 已写"换任何几何源都救不了"），而是**判据的输入不存在**——而"该格现在有
没有绊线"这个事实，在真实世界侧**本来就是可直接读的**。于是本通道的全部内容就是：把这一族的删除判据
从"深度推断"换成"状态比对"。

它**不是**"给绊线开一个特例后门"，而是给**"判据的输入不存在"的整族**换一条判据；族的边界由单一谓词
`BlockStateUtil.isSignalLossBlock`（`BlockStateUtil.SIGNAL_LOSS_BLOCKS`）定义，扩展条件见 §15.5。

**为什么不走"另读 weather 深度场"**（§7.13 / §10.8 曾提的方向）：

| | 读 weather 深度场 | 状态直读（本通道） |
|---|---|---|
| 需要什么 | 第二路 PBO + 新反投影路径 + 混入雨雪须剔除 | 一次 `getBlockState` |
| 与图形配置 | **Fabulous 专属**（Fancy/Fast 无 weather 目标） | **无关**（顺带解掉"排除范围过宽"） |
| 与视锥 / 可见性 | 必须"看得见" | **无关**（§15.4 P2） |
| 与 §10.1"覆盖层不入深度语义" | 违背该原则 | 不涉及 |
| 误差来源 | 与深度判据同源（量化 / ε / δ） | **无量化误差** |
| 成本 | 每帧一路全屏回读 + 新路径 | 每格 O(1)，且该族极稀疏（本世界 **0** 格） |
| 方向安全性 | 新增一路"缺失即误删"的信号源 | 读不到 ⇒ 保留（§15.4 P1） |

### 15.2 方案：三段协议（复用现有两条文件通道）

**不新增文件、不新增方向**——两段走的就是既有的 `memory_cells.bin`（记忆→采集）与 `terrain.nbt`
（采集→记忆）：

```
① 记忆侧 → memory_cells.bin 新增「信号缺失段」
   上报：镜像中当前"在场"的信号缺失族格（存在 + 是什么方块，供诊断与族扩展）
   逐格： long BlockPos.asLong + ushort blockIdLen + UTF-8 blockId
   构造： computeCells 第 ① 步的同一趟遍历、同一距离球（removalMaxRayDist）、
          同一"只报已应用格"口径；在形状谓词**之外**并列一条：
            isSignalLossBlock(state.getBlock()) → 进 signalLoss 段
          （与几何段并列不冲突：isShapedDeletableContent 对信号缺失族恒 false，两段天然互斥）

② 采集侧 → 真实世界状态直读 → terrain.nbt 新增「信号缺失裁决」段
   候选集由记忆侧给定（采集侧**不自行枚举、不筛可见性**，§15.4 P2）；
   对每格（自上而下，次序承重）：
     双保险  if (terrain.keySet().contains(pos)) continue;   // 本帧已看见 ⇒ 不删（恒不应触发，见 §15.7）
     守卫    if (!level.isLoaded(pos)) continue;             // 区块未加载/越界 ⇒ 不裁决（P1）
     直读    state = level.getBlockState(pos);
       ├ state.is(VOID_AIR)  → 跳过（兜底 + 记账，见 P1；**本判必须在 isAir() 之前**）
       ├ !state.isAir()      → **不裁决**（真实世界在场，或已换成别的方块 ⇒ 一律保留）
       └ state.isAir()       → **裁决缺席** → 进本段

   **采集侧刻意不持信号缺失族名单**（实施时定案，见 §14.7 偏离 ②）：族由"记忆侧上报了哪些格"定义，
   而"该格现在是不是空气"这个判据**与方块种类无关**。故本侧第三步就写成 `!state.isAir()`——它同时
   覆盖"在场"与"已换成别的方块"两种情形，结论都是**不裁决**，与"逐族点名"的写法**逐格同结果**，
   却少了一份可能与记忆侧漂移的平行名单（两份名单一旦不一致，"上报了的格"与"可删的格"就会错配）。
   更实际的一条：`BlockStateUtil` 属于记忆侧那个 mod，采集侧**够不到**（不同 jar），
   想持名单也只能复制一份——复制正是漂移的来源。

③ 记忆侧 DeletionApplier → 执行（新增一条**并列**通道）
   执行顺序不变（先增量后减量）；仍保留 currentTerrain.contains(pos) 跳过（假阳性防护）；
   放行守卫换成并列的那把尺： isSignalLossBlock(mirror state.getBlock())
   **本节裁决绝不并入"已证空格集"**（provenEmpty，冻结实体清理用）——见 §15.5 第 4 条
```

**为什么裁决要另起一段，而不是塞进现有 `deletions` 列表**：现有 `deletions` 的放行守卫是
`isDeletableContent ∪ isShapedDeletableContent`——两者对绊线**都返回 false**（这正是 §2.2 的第三层
排除、也是"双保险"的落点）。若为这条通道把守卫放宽，就把"只删 cells 可报口径的内容"这条双保险
**整体打穿**：此后**任何来源**的 deletion 只要落在绊线格上都会被放行。故新增**并列段 + 并列守卫**：

| 通道 | 放行守卫 | 定义域 |
|---|---|---|
| `GEOMETRIC`（现段，**逐位不变**） | `isDeletableContent ∪ isShapedDeletableContent` | 实心不透明 ∪ 流体（水/岩浆）∪ 满格透明 ∪ 非满形状（无 BE、非信号缺失、几何非空） |
| `SIGNAL_LOSS`（本段，新） | `isSignalLossBlock(state.getBlock())` | 绊线 ∪ 绊线钩 |

两条守卫的定义域**不相交**（绊线既不是 `isDeletableContent`、也不是 `isShapedDeletableContent`；反之
本段只放行信号缺失族）⇒ 分段**不引入任何交叉放行**，两条通道各自的双保险都完整保留。这条"分段而非
放宽"的选择是本设计的核心结构决定：**能力按族开，双保险不拆**。

### 15.3 文件与接口落点

**文件格式**：信号缺失段**追加在 v4 几何段之后，并升版为 `version = 5`**（⚠ 与决策 S-A 的表述不同，
理由见下，已按 §14.7 偏离 ① 定案）：

```
[0..3]  magic "SCEL"
[4]     version = 5                                    ← v4 → v5（本次追加段落）
[..]    int  shapedCount ; shapedCount × {...}          ← §4.3.2 既有几何段（逐字不变）
[..]    int  signalLossCount                            ← 本段（新增，v5 的最后一段）
        signalLossCount 条： long BlockPos.asLong + ushort blockIdLen + UTF-8 blockId
```

> **为什么必须升版，而不能"并入 v4"**（实施时发现的偏离，S-A 的原始前提在写代码时被证伪）：
> S-A 的前提是"v4 尚未落地"，但**代码里 v4 已实现**（`MemoryCellReporter.VERSION = 4` 与
> `MemoryCellsReader` 的 v4 分支都在）。而 `MemoryCellsReader.parse` 末尾是**严格检查**
> `if (sp != bytes.length) return null`，其自带注释已写明 *"若将来再追加段落，须同时升版并按版本
> 分支，勿放宽此检查"*。于是：
>
> | 做法 | 旧版采集侧读到新文件 | 后果 |
> |---|---|---|
> | 不升版、尾后追加 | `sp != bytes.length` ⇒ **整份作废**（return null） | cells 全丢 ⇒ 各段都不判 ⇒ 恒不删（安全，但**连带废掉几何段**、且无版本号可查） |
> | **升版为 5** | 版本不认识 ⇒ 拒读 | 同为空集，但**行为可辨识**（日志有版本号），且不牵连任何既有段 |
>
> 故升版是唯一正确做法：**version 严格递进、读方按版本分支**，v4 的解析路径因此逐字不变（升版是纯
> 追加，不是改写）。§15.8 的 S-A 行已同步加注。

`terrain.nbt` 的维桶内新增**并列**键 `signalLossDeletions`（long 列表，恒写、空 = 本帧无裁决），
与既有 `deletions` 同层同型——旧读方不认识该键 → 读为空列表 → 行为等同本版之前（只欠删，安全）。

| 侧 | 文件 | 动作 |
|----|------|------|
| 记忆 | `MemoryCellReporter.java` | 改：`VERSION = 5`；`Segments` 增 `signalLoss` 段（`Map<Long,String>`，值 = blockId，供诊断与族扩展）；`computeCells` 第 ① 步并列分支；`writeAtomic` 追加段（`46 + …` 的定长部分 +4）；**并入内容指纹比较**（见下） |

> **指纹陷阱（实施时必查）**：`MemoryCellReporter` 的"内容未变则不重写"门控依赖 `Segments` 的相等
> 比较。若信号缺失段**未并入**该比较，则镜像里绊线增减**不会触发文件重写** ⇒ 本通道**整体空转**。
> 后果方向是安全的（只欠删：列表缺项 → 永不裁决；列表有陈旧项 → 记忆侧守卫 `isSignalLossBlock` 返
> false → no-op），所以它是"功能失效"而非"误删"，**但会静默失效**——列入 §15.7 第 8 条断言。

**改动量**：≈100~150 行（其中新增类 1 个、既有方法内并列分支 5 处）。**无新 MixIn、无新回读、
无新线程**——本通道完全不碰渲染帧。

### 15.4 四个必须处理的点

#### P1（唯一的"方向错"的坑）：读不到 ≠ 不存在

未加载的区块，`getBlockState` **不抛异常、也不返回空气**，而是返回 VOID_AIR。源码链（已核实）：

| 调用 | 行为 |
|---|---|
| [`Level.getBlockState`](decompiled_src_vf/client/net/minecraft/world/level/Level.java#L356) | `!isInValidBounds(pos)` → **`Blocks.VOID_AIR`**；否则 → `getChunkAt(pos).getBlockState(pos)` |
| [`Level.getChunkAt`](decompiled_src_vf/client/net/minecraft/world/level/Level.java#L188) | → `getChunk(x, z, FULL)`（`loadOrGenerate = true`） |
| [`ClientChunkCache.getChunk`](decompiled_src_vf/client/net/minecraft/client/multiplayer/ClientChunkCache.java#L39) | 不在范围内 / `isValidChunk` 失败 → 返回 **`emptyChunk`** |
| [`EmptyLevelChunk.getBlockState`](decompiled_src_vf/client/net/minecraft/world/level/chunk/EmptyLevelChunk.java#L26) | → **`Blocks.VOID_AIR`** |

也就是说：**玩家一走远、区块卸载，本通道读到的"空气"与"真的没有绊线"在字面上完全一样**。若按
"读到不是绊线就删"执行，会把镜像里**真实存在**的绊线批量删掉——这是唯一一条能把整套系统从
"永远安全欠删"一次翻成"批量误删"的路径。

守卫**不需要自己写**，vanilla 已给正是这一条的 API：

```java
// decompiled_src_vf/client/net/minecraft/world/level/Level.java:711-715
public boolean isLoaded(final BlockPos pos) {
   return !this.isInValidBounds(pos)
      ? false
      : this.getChunkSource().hasChunk(SectionPos.blockToSectionCoord(pos.getX()),
                                       SectionPos.blockToSectionCoord(pos.getZ()));
}
// decompiled_src_vf/client/net/minecraft/world/level/chunk/ChunkSource.java:25-27 —— hasChunk 的语义就是 FULL
public boolean hasChunk(final int x, final int z) {
   return this.getChunk(x, z, ChunkStatus.FULL, false) != null;
}
```

故守卫落成**一个既有调用**：`if (!level.isLoaded(pos)) continue;`——未加载 / 越界一律**不裁决**。
**P1 的默认方向写死：不可验证 ⇒ 保留。**

**仍然保留 `state.is(VOID_AIR)` 一处判断，但改作兜底 + 记账**：`isLoaded` 已覆盖"越界"（`isInValidBounds`）
与"未加载"两条主路径，VOID_AIR 在 `isLoaded == true` 时按构造不应出现；留着它是为了万一的环境差异
（服务端异常、维度高度边界）时不至于把 VOID_AIR 当成"缺席"——**它不是第二道防线，而是"读到意料之外
的东西就别动"的记账位**（日志计数，便于发现环境差异）。

#### P2：不得用"本次可见集里没有它"当证据

本通道的证据是**状态读**，与"是否看见"逻辑上无关。把可见集差集当证据会引进**假阴性**——"出画 /
被遮挡 / 背对 ≠ 不存在"，§14.4 与 §14.5 已经两次踩到这个坑的几何版本（红石粉"修复了"其实是出画、
睡莲的 4 格有 3 格是出画）。具体两条要求：

- **候选集由记忆侧给定**（它有镜像的权威列表），采集侧**不自行枚举、不做视锥/可见性筛选**；
- 采集侧的覆盖条件用**区块覆盖**（`isLoaded`）而不是"看得见"。这样整条通道**对渲染帧 0 依赖**：
  不读深度、不读 PBO、不需要 `snap`、与 Fabulous/Fancy/Fast 无关，因而也不可能因"这一帧没渲染到"
  而漏裁决。

> 注意这条与几何族**语义相反**：几何族**欠删于"看不见"**（证据来自像素），本通道**恰好在看不见时
> 也能删**（证据来自状态读）。所以 §15.7 有一条专门断言："真在场的绊线，即使背对/远处/被遮挡也必须
> 不删"——不是靠"看不见"保命，而是靠"读到了"保命。

#### P3：以状态为准，且只保留"删除"这半个动作

读到**第三种方块**（既非信号缺失族、也非空气）→ **不裁决**。理由：本通道只被授权"证明不在"，**没有被
授权"证明在"**；镜像里该格的内容由**常规观测通道**在下一帧覆盖（正向增量是内容的唯一权威）。若在这里
顺手改内容，就造出了"镜像里有一个从未被看见的方块"的**假记忆**，破坏"记忆 = 见过的世界"这条根本语义
（这正是 §2.2 把"方块被替换为另一仍存活对象"归给正向通道的同一条理由，见 `BE载体方块减量设计方案.md`
§2.2 末行）。

#### P4：时序 —— 只在"真实世界采集帧"成立

本通道读的是 `level.getBlockState`，**与整条采集链路同前提**：采集帧必须在真实世界。该前提**不是本通道
新增的**——v2.32 起 `terrain.nbt` 的整套语义（"活动维 = agent 当前维"，`世界类型区分与镜像复原设计方案.md`
§3）就建立于此；否则 `level.getBlockState` 读的全是镜像内容、整套系统自指。**运维结论：与现链路同一
约束，不新增部署前提。**

另有一条**与现有 deletions 同款的时序窗**：裁决在 t、执行在 t+Δt（一次文件往返）。期间真实世界新放了
绊线 ⇒ 镜像会删掉一格"其实在场"的绊线；下一轮采集由正向增量补回。与现段同款、同量级，**不新引入**。

### 15.5 与几何族的关系：四条硬边界（写死）

本通道**只对信号缺失族开放**，以下四条是规格的一部分，不是建议：

1. **不得外溢到几何族。** 几何族的判据（ε/δ 体系：§3.2 2b、决策 O/Q、`视觉api设计方案.md` §4.2.1 决策 R）
   是自洽的、且是"只相信看见的"这条防御的体现。一旦它们改走"状态直读"，**整套 ε/δ 体系立刻失去存在
   意义**，更根本的是——整条视觉链路会从"记忆由视觉产生"退化成"直接复制真实世界"，本末倒置。故
   边界是：**凡判据需要深度信号才能成立的，走几何段；凡判据的输入不存在的，才走本通道**。
2. **族由谓词定义，不由代码特例定义。** 唯一入口是 `BlockStateUtil.isSignalLossBlock`（表 `SIGNAL_LOSS_BLOCKS`
   单点维护，**且只在记忆侧**——采集侧的裁决写成 `!state.isAir()`，与方块种类无关，故不持名单，
   见 §15.2 ②末段与 §14.7 偏离 ②）。将来若有方块被确认"信号缺失"，**加表即纳入**，不动任何机制、
   不改文件格式（段已带 blockId）。
   **加表时的两条前置约束**（否则 §15.2 的"定义域不相交"会退化、双保险被拆）：
   - 新成员必须**满足 `!isDeletableContent && !isShapedDeletableContent`**——即**非满格、非流体、无 BE、
     非 `INVISIBLE`**。现行两位成员（`TRIPWIRE` / `TRIPWIRE_HOOK`）均满足（都是非满格、无流体、无 BE）。
     若将来纳入一个**满格**的信号缺失方块，它同时落进 `GEOMETRIC` 的定义域，两条通道会交叉放行——
     那时必须先拆 `GEOMETRIC` 的守卫而不能直接加表；
   - 新成员必须**同时**落进 §15.4 P1 的守卫域（即校正的前提是"区块已加载"）——本通道对**任何**族成员的
     安全性都只依赖这一条守卫，与方块种类无关。
3. **本版只开绊线族这一格。** "无深度信号的 BE 类"（`BE载体方块减量设计方案.md` §2.2 与绊线同列）在
   **判据侧**同样适用本通道（状态直读与是否有 BE 无关），但其**执行侧**需要 v2.38 的"唯一删除原语"
   （否则删了方块、留下 BE / 容器负载，正是 v2.38 §13 的失败模式）。故本版**只加 `TRIPWIRE` /
   `TRIPWIRE_HOOK`**，BE 类待 v2.38 原语就位后再加表——**通道通用、本版只开一格**。
4. **本通道的裁决不得并入"已证空格集"（`provenEmpty`）。**（实施时发现的一条真实误删路径，见 §14.7
   发现 ③）`DeletionApplier` 的冻结实体清理判据是"该实体全部 AABB 占用格 ∈ `deletions` ∪ {相机格}"
   即视为已消失 → `discard`。本通道的裁决**看似同型**（都是"采集侧证明该格空了"），但语义不同：
   `provenEmpty` 的含义是"该格已无任何占用物"，而本通道证明的只是"该格**现实里没有绊线了**"。
   绊线**不阻挡实体**（两者可同格共存，实体 AABB 的某一格完全可能正是绊线所在格）⇒"绊线没了"对
   实体占用**零信息量**。若并进去：站在原地的**活实体**，只要其 AABB 覆盖过某格曾被绊线占用的位置，
   就会被判"占用格全空"而遭 `discard`——**这是本通道唯一能造成"删活对象"的路径**，且与方块删除无关、
   不在原设计的视野内。故硬边界：**两条删除清单只在"删方块"这半个动作上并列，绝不汇入实体判据。**

`TripWireBlock.SHAPE_ATTACHED = Block.column(16.0, 1.0, 2.5)` 的**格局部坐标**（1/16 与 2.5/16），
而该格的 y 是 **65**。

#### 15.11.2 根因：`getShape(level, pos)` 返回**格局部坐标**，代码当成了世界坐标

证据链四环（任一环单独成立即可定案）：

1. **vanilla 语义**（`BlockBehaviour.java:668-673`）：`BlockState#getShape(level, pos[, ctx])` 直通
   `getBlock().getShape(state, level, pos, context)`。`pos` 只供**邻接依赖**的方块（栅栏/玻璃板连接）
   使用；**返回值不做 `move(pos)`**。
2. **绊线自身实现**（`TripWireBlock.java:69-70`）：直接返回局部常量 `SHAPE_ATTACHED` / `SHAPE_NOT_ATTACHED`。
3. **vanilla 自己的调用方负责平移**（`TripWireBlock.java:168`）：
   `level.getEntities(null, state.getShape(level, pos).bounds().move(pos))` —— **显式 `.move(pos)`**。
4. **运行时直证**：本帧诊断打印的 `shapeY=[0.0625,0.15625]`（该格 y=65；世界坐标应为 `[65.0625,65.15625]`）。

而 `ObjectResolver` 的四处形状调用点里，三处**都没平移**，且它们**紧邻的流体分支恰恰手动构造了世界坐标
AABB**（`new AABB(pos.getX(), pos.getY(), pos.getZ(), …+h, …)`）——同一方法里两种口径并存，说明作者的
意图是世界坐标，**形状分支是静默违反**。

后果：`minSlabEntry(cam, dir, shapes)` 拿**世界坐标的相机**去和**贴在世界原点的盒**求交。该盒在本帧屏幕上
有 19×17 像素的投影（`px≈688-706, py≈187-203`），其 `t_entry ≈ 73.6–74.1` 格，而该处场景深度只有
`1.79–1.81` 格 ⇒ 判据 `Z_opaque ≥ t_entry − δ`（要求 ≥ 73.52）**按构造不可能成立** ⇒ 每个候选都判"被挡"。

**§15.10.4 里"逐条闸门都该通过"的静态推理之所以与实测矛盾，是因为它默认了 `shapes` 已经在格上。真实的
失效点不在任何一条闸门里，而在闸门的输入上。**
