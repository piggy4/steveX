> 关联：`视觉api设计方案.md`（§5.2.1 L1 纯度、§7 纯累积外观冻结、§6.2 Tier-1/Tier-2）、

## 1. 问题

真人对物品的认知分三级：

| 级 | 真人动作 | 能知道什么 |
|---|---|---|
| **看到** | 看一眼图标 | id / 堆叠数 / 耐久条 / **附魔光效** / 皮革染色 / 旗帜纹样 / 药水颜色 |
| **查看** | 悬停该格（**一次一格**） | tooltip 全文：附魔 id+等级 / 自定义名 / 稀有度名色 / 药水效果 / 成书标题作者 / 属性修饰… |
| **取得** | 拿进背包、手持、或挂到鼠标上 | 之后可无限次"查看" ⇒ 等价于"已经知道" |

规则一句话：**仅"看到" ⇒ 只知道可见面；components 细节必须经过一次"查看"或"取得"。**

现状是**两条通道不一致**：可见面（`vision/snapshot` 的掉落物/展示实体、`f3` 的装备）已经薄化，
但 `container/get` 与 `vision/entity` 把"查看面"直接给了——开一次箱子/查一次实体，就等于把里面所有物品
悬停了一遍；`vision/entity` 更是把生物身上、盔甲架上、展示框里的物品连附魔一起整份给出。

## 2. 判据与证据（1.21.11 源码核实）

> 引用约定：本节与 §3 的 `ItemStack.java` / `Item.java` / `Items.java` / `CompassItem.java` 行号来自
> **vanilla 反编译源**（`MC_agent/decompiled_src_vf/client/...`，在本仓库之外）；其余 `*.java` 引用均为本仓库内文件。

### 2.1 "可见面"的权威判据是**光效**，不是真附魔

- `ItemStack.hasFoil()` = `glintOverride != null ? glintOverride : item.isFoil(this)`（`ItemStack.java:975-978`）；
  `Item.isFoil(stack)` = `stack.isEnchanted()` = `ENCHANTMENTS` 非空（`Item.java:342-344`、`ItemStack.java:1006-1008`）；
  `CompassItem.isFoil` 另加 `LODESTONE_TRACKER`（`CompassItem.java:29-30`）。
- vanilla 给这些物品硬设 `ENCHANTMENT_GLINT_OVERRIDE=true`（`Items.java`）：`experience_bottle`(1607)、
  `written_book`(1615)、**`enchanted_book`(1693-1694，且 `stored_enchantments=EMPTY`)**、`end_crystal`(1802)、
  `nether_star`(1888)、`enchanted_golden_apple`(1240)。
- ⇒ 现状 `DecorativeSummary.isEnchanted`（判 `minecraft:enchantments`，注释里**刻意**排除光效）
  与"所见"不符：**一本附魔书在展示框/陈列架/地上是可见发光的，API 却报 `enchanted:false`**。
  这是"漏报可见信息"。（其注释宣称的收益——不把附魔金苹果误报成附魔——是"报真相"而非"报所见"；
  两者可以并存，见 §5.1 的字段设计。）

### 2.2 "查看面"就是客户端已有的 tooltip，可原样取用

- `ItemStack.getTooltipLines(Item.TooltipContext, @Nullable Player, TooltipFlag)`（`ItemStack.java:859`）、
  `Item.TooltipContext.of(@Nullable Level)`（`Item.java:690,714`）—— 悬停时 GUI 走的就是这一条；
  附魔/药水/成书/属性行由各组件的 tooltip provider 生成。
- ⇒ "查看"不必自己拼字段，直接用 vanilla 的 tooltip 行，天然与真人所见一致
  （`F3+H` 的 advanced 档也可选）。

## 4. 设计原则

1. **可见面 / 查看面二分**：任何"仅看到"的读取面只给可见面字段；查看面字段必须经过一次显式"查看"动作。
2. **已取得例外**：物品在 agent 自己的背包 / 手持 / 鼠标携带（`carriedItem`）时直接给全量 components
   （等价真人可无限悬停）。判定按**来源指纹**而非当前位置 —— 物品挂到盔甲架、放进箱子后仍算"已知"，
   见 §14 补遗。
3. **一个"查看" = 一格**：与真人悬停的单位一致（不是一次看完整箱）。交易列表的特殊性见 §5.2。
4. **不漏报可见信息**：可见面判据用**光效**（§2.1）—— "你能看到的，API 一定告诉你"。
5. **与回读准则正交**：`semantic-vs-input-channel-rule` 决定"用语义包还是输入路径"；本方案决定"给多少信息"。
   查看动作**不改变任何状态**（纯观测），因此不涉及通道选择，也不受"无回读"限制。

## 5. 契约

### 5.1 可见面字段（统一薄化后的形状）

```jsonc
{"id":"minecraft:diamond_sword","count":1,
 "glint":true,                              // = hasFoil()：附魔光效（所见）。仅 true 时写
 "durability":1561,"maxDurability":1561}    // 可见耐久条（仅可损坏物品）
```

- **`glint` 取代 `enchanted`**：语义 = "看起来在发光"。`enchanted`（真附魔）只在**查看面**出现，
  以免把"发光但不是真附魔"（附魔金苹果/成书/末地水晶…）当成"知道了真相"。
  是否两个键并列（`glint=true, enchanted=false`，用于表达"发光但非附魔"）见 §13 决策点 2。

### 5.2 `container/inspect` —— 新增"查看"动作

**参数**：`slot`（int，必填，菜单槽号，与 `container/get` 的 `slots[].slot` 同一编号）

**返回**：

```jsonc
{"status":"ok","slot":0,
 "item":{"id":"minecraft:enchanted_book","count":1,"glint":true},   // 可见面（§5.1）
 "tooltip":["附魔书","锋利 V"],                                     // vanilla getTooltipLines(NORMAL) 的纯文本行
 "enchantments":{"minecraft:sharpness":5}}                          // 结构化抽取（可选，§13 决策点 3）
```

**错误/边界**：`no screen`；`slot out of range` + `size`；该格为空 →
`{"status":"ok","slot":N,"empty":true}`（**不是**错误：盯着一个空格子确实什么都看不到）。

**语义**：等价"把鼠标移到第 `slot` 格并读 tooltip"；**不改状态、不发包**。
实现 = 客户端已有的 `menu.getSlot(slot).getItem()` + `getTooltipLines(Item.TooltipContext.of(mc.level),
mc.player, TooltipFlag.NORMAL)`（§12 待核实 1）。

**与既有 API 的组合（村民交易）**：`container/select-trade {index}` → `container/inspect {slot:2}`
= "选中这笔交易 + 悬停结果格"，与真人一致；交易列表的 `inputA/inputB/result` 只给可见面。
（代价：不选中就无法查看某笔交易的具体附魔 —— 这正是真人语义：列表里只能看到图标与光效。）

### 5.3 `vision/entity` 门控

`{ok,uuid,nbt}` 的 `nbt` 里凡**仅可见/仅装备**的物品栈（`equipment.*`、`Item`、`Items`、`ArmorItems`…）
薄化为可见面；实体自身的非物品字段（位置/血量/属性/交易表…）不动（那是另一类"看不见的信息"，
见 §13 决策点 4）。实施位置建议：`serializeEntityFull` 之后、`nbtToJson` 之前裁 tag（一处收口）。
**指纹命中"经手过"集合的物品栈放行全量**（§14 补遗）—— 自己挂上去的盔甲、自己存进箱子的东西，
放行；别人的装备，薄化。

### 5.4 `minecraft:shelf` 移出 `PASS`

陈列架的陈列物品 = "看到的物品"（图标 + 光效），components 需悬停/取下方可知
⇒ 按"薄摘要"处理（`id/count/glint`），或移入 `ALLOW` 且白名单 = ∅（等价 `STRIP`）+ 由展示实体式摘要供可见面。
（同为 `PASS` 的 `campfire` 只接受食物，无附魔风险；其余 `PASS` 项的内容本身可见，不在本方案范围。）

### 5.5 记忆世界与复原：**不受影响**

镜像侧读的是 store 里的整份 payload/NBT（`containers.nbt` 的 `item` tag、`entities.nbt` 的 `nbt` 键），
与本次薄化的"agent 读取面"是两条路。**薄化只改 API 输出，不动落盘** ⇒ 无迁移、无存档影响。

## 6. 计费模型（诚实说明）

`container/inspect` 是**程序性边界，不是强制边界**：agent 完全可以循环 27 次，把它当"一次全知"用。
它换来的是：

- 结构性消除"一次 `container/get` 免费拿到全箱附魔"这类**零成本全知**；
- agent 的策略与日志里**留下"我查看过这一格"这一步**（可审计、可入训练数据）；
- 与真人动作单位（一格一次）对齐。

若要**强制**，需要额外机制（§8 档 3）：每格查看记一次客户端"已查看"集合（键 = 容器坐标 + 槽 + 物品指纹，
换物品即失效）、每次查看强制 ≥1 tick、或真走输入路径 `screen.mouseMoved` 把 hover 真的放到那一格
（视觉一致，但成本仍只是 1 次移动）。

## 14. 补遗：合法知识 vs 泄漏 —— "来源"维度（2026-09-19 追加）

**触发场景（用户提出）**：agent 把自己身上的盔甲脱下来挂到盔甲架上，之后还能否读到该盔甲的全量 NBT？

**现状（源码核实）**：**能，且只有 Tier-2 一条路**。

| 环节 | 事实 | 证据 |
|---|---|---|
| 服务端 → 客户端 | `LivingEntity`（含 `ArmorStand`）的非空装备位随 `ClientboundSetEquipmentPacket` 同步，`ItemStack.copy()` 走流编解码 ⇒ 带完整 components | `ServerEntity.java:288-300`（vanilla） |
| 客户端存档形态 | `ArmorStand.addAdditionalSaveData` → `super` → `LivingEntity.addAdditionalSaveData` 在装备非空时写 `equipment`；`EntityEquipment.CODEC = unboundedMap(EquipmentSlot.CODEC, **ItemStack.CODEC**)` ⇒ 每槽是完整 ItemStack | `ArmorStand.java:139`、`LivingEntity.java:754-756`、`EntityEquipment.java:11`（vanilla） |

**关键结论**：这个情形是**合法知识，不是泄漏** —— agent 刚把盔甲从自己身上取下（"已取得"），挂上去后仍应知道其附魔。问题不在"能读到"，而在**判定只用了"位置"这一个维度**：现状对"自己放上去的"和"别人的盔甲"一视同仁，两者都给；而本方案档 2 的薄化若同样只按位置判定，会把前者**误伤成只知道 `glint`**。

**修法（二选一，建议 A）**：

- **A（建议）来源指纹**：采集侧维护有界"经手过"集合，键 = 物品指纹（`id` + components 摘要，例如 `components` tag 的哈希）；
  凡是**进过 agent 主背包 / 护甲 / 副手 / 鼠标携带**的物品栈即入集。读任意位置的物品时——
  指纹命中 ⇒ 给全量；未命中 ⇒ 只给可见面。物品换位置（拿起→挂上→再取下）指纹不变 ⇒ 判定稳定，
  且"别人的盔甲"永不命中。代价：一个小 LRU 集合（建议上限 4096）+ 采集侧在 `inventory`/`container`
  读取路径顺带登记（无新增热路径成本）。
- **B（保守）**：API 一概不给，靠 agent 自己的上下文记住"我放上去的是什么"。零成本，但
  "放上去之后再由 API 读回"这条路断掉 —— 恰是本补遗的触发场景，故不推荐。

**对档 2 的影响**：§5.3 的 `vision/entity` 门控改为"**指纹命中则放行**"，而非"装备位一律薄化"；
`container/get` 同理（容器里若放着 agent 自己放进去的东西，指纹命中即可给全量——这也顺带修掉了
"自己存的箱子里的东西也要逐格查看"的不合理处）。
