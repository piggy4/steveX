# 记忆世界传送门冻结设计方案（v2.33）

> 状态：**已实施（v2.33，2026-09-06）**——用户定案「完全冻结」，记忆端 `PortalTravelMixin` 已实现、
> offline `compileJava` 通过；摘要并入 `视觉api设计方案.md` 与 `已实现内容.md`。代码未提交。
>
> 用户需求：记忆世界中探索时，若在主世界踏入一个（由视觉采集复现的）下界传送门，vanilla 会在虚空的
> 下界**自动新建一座传送门**（obsidian 框架 + 火），污染记忆世界；末地门同理。要求**关闭记忆世界里传送门
> 的传送功能，含下界传送门与末地传送门**（设计默认：门变为纯装饰，可自由穿过、不传送）。

## 1. 背景与问题

记忆世界各复原通道把 agent 看到的内容（含**已点燃的下界传送门方块**、末地传送门方块）1:1 复现进对应维。
但记忆世界下界/末地是**纯虚空画布**（v2.30 `voidNetherEnd`，无任何原生结构/方块）。此时若记忆玩家站进一个
复现的下界传送门：

- vanilla 等到传送门过渡时间到 → 计算目标维（虚空下界）出口 → `PortalForcer` 找不到现成出口门 →
  **`createPortal` 在下界虚空坐标就地新建一座 obsidian 传送门** → 记忆世界被写入非采集内容；
- 末地门同理：站进复现的末地传送门 → `EndPlatformFeature.createEndPlatform` 在虚空末地出生点铺 obsidian
  平台；若在记忆末地里站进末地门还会触发 End credits 结局动画。

且这类「非镜像驱动」的跨维移动本身与 v2.32「记忆玩家位置 = 镜像跟随权威」冲突——玩家应只被
`MemoryWorldManager` 按 agent 所在维摆放。

## 2. 触发机制（decompiled `server-1.21.11_unobfuscated` 已核）

1.21.11 传送门旅行**完全由实体驱动**（无方块排程 tick 参与）：

```
玩家身处传送门方块内
  → 方块 entityInside（NetherPortalBlock:110 / EndPortalBlock:61 / EndGatewayBlock:85）
     先查 entity.canUsePortal(false)               ← 闸门①：是否「允许用门」
     true 才 entity.setAsInsidePortal(portal, pos) → 登记 PortalProcessor，每 tick 累积 portalTime
  → 累积达 portalTransitionTime（玩家 4s / 创造延迟读 gamerule）
     Entity.handlePortal()（在 baseTick:503，仅 ServerLevel 分支）
       processPortalTeleportation(level, this, this.canUsePortal(false))   ← 闸门②：是否放行旅行
       true → this.portalProcess.getPortalDestination(level, this)
               · 下界门：NetherPortalBlock.getExitPortal →
                   已存在出口门 ? 用它 : newLevel.getPortalForcer().createPortal(...)   ← **新建污染源**
               · 末地门：EndPortalBlock.getPortalDestination →
                   非末地侧 EndPlatformFeature.createEndPlatform(...)（铺平台）/ 末地侧 ServerPlayer 走 credits
               · 折跃门：EndGatewayBlockEntity 定位外岛
       → this.teleport(teleportTransition)（跨维即 changeDimension）
```

**关键事实**：

- `Entity.canUsePortal(boolean)` 是传送门家族的**统一闸门**，出现在三处方块 `entityInside`（nether/end/gateway，
  决定是否「开始累积进内」）与 `handlePortal` 旅行判定（决定是否执行 `getPortalDestination` 与传送）两处——
  把它关成 `false`，上述整条链在第一步就短路：`setAsInsidePortal` 不被调 → `portalTime` 永不累积 →
  `handlePortal` 永不触发 → `getPortalDestination`（含 `createPortal` / 末地平台 / credits）永不执行。
- **覆写全部回落到基类**：`LivingEntity.canUsePortal = super.canUsePortal && !isSleeping`（LivingEntity:3629）、
  `Creaking` 同理 `&& super`（Creaking:351）——记忆玩家是 LivingEntity，在**基类** `Entity.canUsePortal` HEAD 强制
  `false`，经 super 链必使最终结果为 false。基类方法唯一其余调用是 `ThrownEnderpearl.isAllowedToTeleportOwner`
  的跨维分支（`owner.canUsePortal(true)`，Enderpearl:152）——跨维珍珠跳也一并关掉（记忆世界一致）。
- `canUsePortal` 只被传送门家族使用；记忆端**其它跨维传送不经它**——v2.32 镜像跟随走
  `player.teleportTo(level,…)` → `Entity.teleport(TeleportTransition)`（Entity:3232 起），不查 `canUsePortal` → 不受影响。

## 3. 为什么 v2.21「全局冻结」没覆盖

v2.21 在 ServerLevel **分发层**取消了排程方块/流体 tick 与冻结实体的 `tickNonPassenger`。而传送门使用
**既非排程 tick、也非冻结实体的 tick**：方块 `entityInside` 是实体每 tick 移动碰撞时由 ServerLevel 对**玩家**照常
驱动的（玩家 tick 未被取消），旅行判定在玩家自身的 `Entity.baseTick → handlePortal`。故 v2.21 的冻结对玩家
站进传送门无效——这是现存空洞，需本版补上。

## 4. 设计：单点关闭 `canUsePortal`

记忆端新增一个 Mixin `com.example.mixin.PortalTravelMixin`（`@Mixin(Entity.class)`），对基类方法
`boolean canUsePortal(boolean ignorePassenger)` **@HEAD cancellable**：当实体当前所在 level 是记忆世界
（`level() instanceof ServerLevel && MemoryWorldManager.isMemoryWorld(level)`）时 `cir.setReturnValue(false)`。

**效果**：
- 下界门 / 末地门 / 末地折跃门在记忆世界里全部不生效：不登记进内、不累积、不旅行、不创建目的地门、不铺
  末地平台、不弹 End credits——**门变成纯装饰**。
- 视觉与交互不损：客户端 `animateTick`（下界门紫粒子/声、末地门烟粒）是渲染层，本 Mixin 不碰 → 门照常
  「动」，玩家可自由穿过方块（传送门方块本无碰撞），只是不传送。
- 范围覆盖全传送门家族，一个注入点穷尽；记忆世界里活体只有本地玩家 + 冻结复原实体（后者 NoAI/NoGravity
  不移动且 `tickNonPassenger` 已停，永远走不进传送门），对记忆世界内任意实体一律置 false 安全且更简。

**为何不打在更靠后的点**：若只拦 `handlePortal`/`PortalForcer.createPortal`，实体仍会「登记进内 + 累积 +
触发 getPortalDestination」；`getPortalDestination`（下界门:130-180）内部**先查后建**，只有真正进到 createPortal
的分支才污染——但旅行被拦本身已无意义（用户要的就是「别传送」）。闸门①②合一打在 `canUsePortal` 语义最正、
副作用最小。

## 5. 代码改动（记忆端 `stevex-test-template-1.21.11`）

1. **新增** `src/main/java/com/example/mixin/PortalTravelMixin.java`（javadoc 风格同 `ServerLevelMixin`，
   引用本文档 §2/§3 + `MemoryWorldManager.isMemoryWorld`）：

   ```java
   package com.example.mixin;

   import com.example.memworld.MemoryWorldManager;
   import net.minecraft.server.level.ServerLevel;
   import net.minecraft.world.entity.Entity;
   import org.spongepowered.asm.mixin.Mixin;
   import org.spongepowered.asm.mixin.injection.At;
   import org.spongepowered.asm.mixin.injection.Inject;
   import org.spongepowered.asm.mixin.injection.callback.CallbackInfoReturnable;

   /**
    * v2.33（传送门冻结，见 docs/传送门冻结设计方案.md）：记忆世界传送门为纯装饰——禁止任何传送门旅行。
    * ...
    */
   @Mixin(Entity.class)
   public abstract class PortalTravelMixin {

       /** 打在基类 Entity.canUsePortal；LivingEntity/Creaking 覆写都调用 super → 强制 false 必然生效。 */
       @Inject(method = "canUsePortal", at = @At("HEAD"), cancellable = true)
       private void stevex$disablePortalTravel(final boolean ignorePassenger,
                                               final CallbackInfoReturnable<Boolean> cir) {
           if (((Entity) (Object) this).level() instanceof ServerLevel serverLevel
                   && MemoryWorldManager.isMemoryWorld(serverLevel)) {
               cir.setReturnValue(false);
           }
       }
   }
   ```

   Mixin 运行期按 mapped 名 `canUsePortal` 匹配（官方映射 `officialMojangMappings`，与现有 Mixin 同源）。
2. **改** `src/main/resources/stevex-test.mixins.json`：`mixins` 数组追加 `"PortalTravelMixin"`。
3. `StevexTest.java` / `MemoryWorldManager.java` / 采集端 **零改动**；无新配置项。
4. 编译验证 `./gradlew compileJava --offline`。

## 6. 正确性论证

- **单闸门穷尽全家族**：nether 门 / end 门 / 折跃门 / 跨维珍珠的「进入」与「旅行」都先过 `canUsePortal`
  （decompiled 行号见 §2）→ 关一处全关。
- **镜像跟随不受影响**：v2.32 跨维摆放走 `teleportTo`/`Entity.teleport(TeleportTransition)`，不经 `canUsePortal`。
- **不破坏冻结与减量**：只关「使用」，不涉及方块放置/删除、不涉 tick 分发、不涉渲染 → 与 v2.21 冻结、
  v2.23 减量、v2.32 分桶全正交。
- **污染源被掐在源头**：`PortalForcer.createPortal`（下界）与 `EndPlatformFeature.createEndPlatform`（末地）
  只在 `getPortalDestination` 内被调用，而后者只在 `handlePortal` 旅行放行后执行——旅行被禁即永不发生。
- **性能**：HEAD 早退、每实体每 tick 仅多一次 instanceof（且仅记忆世界实体触发），空闲成本≈0。
