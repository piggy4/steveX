# 生物群系复原设计方案（v2.31）

> 状态：**已实施（v2.31）**。设计经审阅批准后完成实现，两端 `compileJava --offline` 通过；
> 本文已更新为与代码一致的终稿（含实施偏差记录），摘要已并入 `视觉api设计方案.md` 与 `已实现内容.md`。

## 1. 背景与缺口

视觉链路已经能拿到"看到的所有对象"：terrain（方块 block+state）、方块实体（NBT）、实体、容器内容、反向通道 cells。**唯独没有任何群系字段**。代码级核查结论：

| 位置 | 现状 |
|------|------|
| 采集端 `F3Api.java:79` | 唯一的 biome 采样：`f3` 端点取**玩家脚下单点**（`environment.biome`），与视觉采集链路（`vision/snapshot` 及三个 store）无关 |
| 采集端视觉链路 | `ObjectResolver` / `VisionApi` / `VisionTerrainStore` 等**全链路 grep 不到 biome** |
| 复原端 `MemoryWorldManager.createVoidWorldDimensions` | 建档时给每维度**钉死单一群系**：主世界 `plains`、下界 `nether_wastes`、末地 `the_end`，且无第二个通道可改 |

群系虽不改变方块摆放，却决定客户端渲染外观：草/树叶/藤蔓的**色偏**、天空色/雾色、降水类型、环境粒子与氛围音效等。结果：在雪原/沼泽/丛林拍下的"冻结的瞬间"复原到记忆世界后，一律按平原的草色/天空/雾渲染——**方块都在，场景"肤色"错了**。这是目前唯一一类"看到了却还原不了"的环境信息。

## 2. 为什么需要一条新通道（群系不是方块数据）

- 群系存在**区块**里，不是方块属性：每 `LevelChunkSection` 一个 `PalettedContainerRO<Holder<Biome>> biomes`（4×4×4 quart cell 粒度），字段私有只读（解混淆源码第 21/148 行），`setBlock` 完全不触碰它。因此它搭不了地形通道的便车。
- 好消息：vanilla `/fillbiome` 命令提供了**完整公开写入口范式**（`FillBiomeCommand.java`），五步即可改写任意已加载 FULL 区块的群系并让客户端重着色：
  1. `level.getChunk(cx, cz, ChunkStatus.FULL, false)` 拿已加载块；
  2. `chunk.fillBiomesFromNoise(resolver, sampler)` —— `ChunkAccess` 公开方法，遍历全部 section，对每个 quart cell 用 resolver 返回值改写；
  3. resolver 对"不处理的 cell"返回 `chunk.getNoiseBiome(...)`（当前值）→ 其余格原样保留；
  4. `chunk.markUnsaved()` → 落盘；
  5. `level.getChunkSource().chunkMap.resendBiomesForChunks(List.of(chunk))`（`chunkMap` 是 `public final` 字段）→ 向跟踪玩家发 `ClientboundChunksBiomesPacket`，客户端重着色，无需整块重传。

> 已核实 API：`ChunkMap.resendBiomesForChunks(List<ChunkAccess>)`（ChunkMap.java:1272）、`ChunkAccess.fillBiomesFromNoise(BiomeResolver, Climate.Sampler)`（ChunkAccess.java:442）、`markUnsaved()`、`ServerChunkCache.chunkMap`（public final）。**全部公开，无需新增 Mixin / 新包。**

## 3. 总体设计

在既有"采集 NBT → 记忆端 mtime 轮询"架构上加一条姊妹通道：

```
采集端（渲染线程快照末尾）
  每帧 可见方块集 → 去重成 quart cell 集 + 相机 cell 锚点
  → VisionBiomeStore 累积 union → 整体覆盖写 biomes.nbt（stevex/vision/）
记忆端（服务器 tick / 服务器线程）
  BiomeRestorer 轮询 biomes.nbt（mtime 门控，同既有通道）
  → 新增/变化的 cell 归组到 chunk → 对「已加载」chunk 即时填（/fillbiome 五步）
  → 对「未加载」chunk 记 pending → 每 tick 扫 pending，一旦已加载即补填
    （tick-scan 补填，见 §5.3 —— 未用 CHUNK_LOAD 事件，实现偏差）
```

**核心取舍**：群系在"区块生成/加载"时就写对，让客户端第一次拿到 chunk 即正确；对已加载块的增量更新走 `resendBiomesForChunks` 即时纠正。不需要自定义 ChunkGenerator、不需要重建世界。

## 4. 采集端设计（stevex-template-1.21.11）

### 4.1 采样粒度：3D quart cell（每格 4×4×4 方块）

群系存储与复现的最小单位都是 quart cell。按 cell 记录比按"列"记录**同时正确**：
- 精确复现**地表与洞穴随高度的群系差异**（同列地面 jungle、深处 deep dark → 不同 `quartY` 的 cell 各记各的）；
- 不与 vanilla 的 cell 单值语义冲突（vanilla 一个 cell 本就只能有一个群系）。

cell 坐标 = `QuartPos.fromBlock(blockPos)`（`>>2`）。从**方块位置**采样 `level.getBiome(pos)` 得到的即该 cell 的群系（确定性）。

**采样粒度定案（用户确认）：逐 cell 写、绝不逐方块写。** 由于游戏本身以 cell 存群系，同一 cell 内所有方块的 `getBiome` 返回值**必然相同**（这是存储保证，不是比较判断）——因此即使对每个可见方块都调一次采样，按 cell 去重后天然收敛为一条 cell 记录，**永远不需要**、也**不可能**产生逐方块条目。实现时以 cell 为去重与写入单位即可，无需值比较、无需逐方块回退分支。

### 4.2 采样时机与来源（渲染线程，零额外扫描）

在 `ObjectResolver.resolve`（已在 `Minecraft.execute` 渲染线程 lambda 内）的**末尾**、三个 store `sync` 之前，此时 `terrain` 已含全部可见方块（含 §5.4 半透明/绊线补采）：

1. 遍历 `terrain.keySet()`，对每个方块坐标算 cell、以 cell 去重（一个 cell 保留任一采样坐标即可）——同 cell 多块只写一条；
2. **相机 cell 锚点**：额外加入 `BlockPos.containing(cameraPos)` 所在 cell（即使本帧零可见方块也要记——保证玩家所在位置的雾/天空色正确，模拟 `f3` 的脚下采样但提升到 3D cell）。

实现：`ObjectResolver` 收集 `List<BlockPos> biomeSamplePoints`（terrain 全部可见方块 + 相机 cell 锚点），交给 `VisionBiomeStore.sync`；cell 去重在 store 内部做，统计经 `ResolveResult.biomeStats` 一路带回 `VisionApi`。

### 4.3 VisionBiomeStore（新文件，`vision/VisionBiomeStore.java`）

仿 `VisionTerrainStore` 的最小通道：
- **union 语义**：启动时若 `biomes.nbt` 已存在则读入内存 union（记录历史），否则空。每帧只对"不在 union 中"的 cell 做 `level.getBiome` 解析（O(新增 cell)），新增并入 union。
- **写**：仅当本帧有新增 cell 时**整体覆盖写** union（单调增长；memory 端累积应用，无删除需求）。文件格式：

```
biomes.nbt = {
  "timestamp": <ms>,
  "cells": {
     "321,16,-84": "minecraft:plains",   // key = quart 坐标 qx,qy,qz
     ...
  }
}
```

- 与地形 store 的差异说明：terrain 写"本帧可见"由 memory 端累积；biome store 直接写"历史 union"，两种文件经 memory 端累积后到达同一终态，故直接写 union 更省 memory 端 diff。

### 4.4 对外 JSON（可选小尾巴）

`snapshot` 响应的 `storeStats` 增加 `"biomes": { "cells": <union 总数>, "added": <本帧新增> }`，便于 agent/日志确认通道工作。**不把逐 cell 表塞进 JSON**（量级与块表相当，走 NBT 文件更合适）。

## 5. 记忆端设计（stevex-test-template-1.21.11）

### 5.1 配置与路径

- `MemoryConfig` 增加 `biomeFile`（默认 ""）+ `resolveBiomeFile()`，候选路径与 `containerFile`/`terrainFile` 完全一致，只是文件名换成 `biomes.nbt`（缺省自动探测到采集侧同目录）。
- 沿用 `config/stevex-test/memory.json` 的解析/回退机制；**无新布尔开关**（文件缺失即通道静默停用，与 terrain 缺失行为一致）。

### 5.2 BiomeRestorer（新文件，`memworld/BiomeRestorer.java`）

镜像 `TerrainRestorer` 的轮询骨架：

- 状态：`cells: Map<String,Holder<Biome>>`（读到的 union、已解析为 holder；字符串 key 与文件一致，避免跨端二进制打包约定）、`prevIds: Map<String,String>`（最近一次文件快照，做 diff）、`pendingChunks: Set<Long>`（含未应用 cell 的 chunk，ChunkPos.asLong）、mtime 门控、缺失计数。
- `onServerStart()`：清空 `cells`/`prevIds`/`pendingChunks`/mtime → 首 tick 重读文件（支持 `resetOnLaunch` 重建后全量重填）。
- `tick(level)`（仅记忆世界，复用 `MemoryWorldManager` 过滤）：
  1. mtime 门控读 `biomes.nbt`（成功才推进 mtime；失败保留旧 mtime 下轮重试）；
  2. `changed = 本次文件 − prevIds`（key 缺席或 id 变化）；为空则跳到 4；
  3. 对每个变化 cell：`resolveBiome(id)` → 成功入 `cells`，失败 WARN（同 id 仅一次）跳过；再按 `qx>>2, qz>>2` 把所在 chunk 加入 `pendingChunks`；最后 `prevIds = 本次文件`；
  4. `drainPending`：遍历 `pendingChunks`，对**当前已加载**的块调 `applyChunk`（每 tick 限量 `MAX_APPLY_PER_TICK=64` 防卡顿）；未加载的留在集合等下次 tick；失败保留 pending 下轮重试。
- `applyChunk(level, cache, chunk)`（等价 `/fillbiome`，只在已加载块上调用）：
  1. resolver：`(qx,qy,qz,sampler) -> { h = cells.get(qx+","+qy+","+qz); return h != null ? h : chunk.getNoiseBiome(qx,qy,qz); }` —— 记录过的 cell 覆盖，其余**原样保留**；
  2. `chunk.fillBiomesFromNoise(resolver, cache.randomState().sampler())`；
  3. `chunk.markUnsaved()` → 落盘持久化（未加载块从磁盘重读也是对的，无需跨 unload 记 applied）；
  4. `cache.chunkMap.resendBiomesForChunks(List.of(chunk))`，并从 `pendingChunks` 移除该块。

> **差异说明（相对初稿 §5.1 §5.3）**：① 不做 `appliedCells` 精确集合——`markUnsaved` 已把群系写盘，块 unload→reload 自然从盘上带出正确值，故 pending 移除即足够，状态更简；② `prevIds` 存整份 id 快照 diff，天然只处理新增/变化 cell（文件是单调 union，绝大多数轮无变化、零开销）。

### 5.3 生命周期与挂点

- `MemoryWorldManager`：静态持有 `BIOME = new BiomeRestorer()`；`onServerStart()` 链 + `onServerTick` 驱动；tick 顺序定在 **TERRAIN → ENTITY → RESTORER → CONTAINER → BIOME → DELETION → CELLS**（实际插在 `CONTAINER.tick` 之后、`DELETION.apply` 之前：BIOME 不改变方块，与 DELETION/CELLS 无耦合，故插在既有链中部即可；`forceRestore` 命令一并触发 `BIOME.forceRefresh()`）。

> **实施偏差（tick-scan 取代 CHUNK_LOAD）**：初稿设想注册 `ServerChunkEvents.CHUNK_LOAD` 在块加载瞬间补填；实施改为 **`drainPending` 每 tick 扫 pendingChunks**（含非轮询 tick，`getChunkNow` 判加载）。理由：记忆玩家按采集姿态整区传送，内容区块本就随传送逐个加载，补填窗口至多一个 tick，tick-scan 即可覆盖；无需新增事件监听/主入口改动（`StevexTest.java` 零改动），也规避事件注册与单 tick 块加载时序的偶发竞态。代价：每 tick 对 pending 未加载块各做一次 `getChunkNow` 查表（O(pending)，哈希查 map，可忽略）。

### 5.4 正确性论证

- **首次发送即正确**：多数块的群系数据在其所在 chunk 生成前就已就绪（采集先于复原），块一被服务端加载，`drainPending` 在 ≤1 tick 内把群系写进该块——早于或紧随该块首次向客户端发送；`resendBiomesForChunks` 在块已跟踪（已加载）时才发 biome 包，无空块副作用。
- **竞态自愈**：若 biome-only 包偶发先于完整 chunk 包到达（客户端尚无该 chunk），会被后续正常 chunk 发送覆盖——而我们已 `markUnsaved` 落盘，落盘值即正确值 → 自愈。若需更稳可把 resend 延迟到下一 tick，实施时定。
- **非侵入**：resolver 对未记录 cell 返回当前值 → 未访问区域（默认平原虚空缓冲）不受影响；记录单调累积、幂等重放无副作用。
- **3D 忠实**：cell 带 `quartY` → 洞穴/地表差异被精确保存，非"整列一个值"的近似。

## 6. 边界与限制（明确不做）

1. **仅主世界**：与现有 terrain/entity/container 各通道一致（记忆端只对 OVERWORLD 复原）；下界/末地本就无内容。若将来采集支持跨维度，给 biomes.nbt 加 dimension 键即可扩展。
2. **只覆盖"有可见方块或相机所在"的 cell**：4 格粒度与 vanilla 存储一致；两群系边界若恰好落在无可见内容的空白处则保留默认值（视觉上无着色对象，可接受）。
3. **自定义/数据包群系**：要求采集端与记忆端共享同一注册表（同 MC 版本 + 相同 mod/数据包）。解析失败（`registryAccess` 查不到）→ 跳过该 cell 并记 WARN，不崩溃。
4. **零新依赖**：补填走每 tick 的 `getChunkNow` 探测（tick-scan），不注册 `CHUNK_LOAD`；本通道只依赖既有的 `ServerTickEvents` 与全部已用公开 API，**无新依赖、无主入口改动**。

## 7. 验证步骤

1. 两端 `./gradlew compileJava --offline` 通过（沿用解混淆源码核对方法名：`ChunkAccess`/`ChunkMap`/`QuartPos`/`ServerChunkCache`）。
2. 采集端手工：在平原→森林/沼泽/雪原交界的真实世界走动，确认 `run/stevex/vision/biomes.nbt` 生成、cells 只增不减、`storeStats.biomes.added` 首帧>0 后归零。
3. 记忆端手工：删档重建记忆世界，观察复原场景中草/树叶色偏、天空/雾与采集场景一致（如平原绿地旁出现雪原白草、沼泽灰褐水）。对比 `/fillbiome` 手动把同区改成 plains 再改回，验证 resend 生效、颜色即时刷新。
4. 边界：进入未访问虚空区仍为默认平原色；控制台无新 WARN。
5. 关掉采集端删掉 biomes.nbt → 记忆端安静 no-op，通道自动停用。
