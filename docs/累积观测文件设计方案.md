## 1. 背景与缺口

### 1.1 agent 读不到累积记忆

记忆世界（记忆端 `com.example.memworld`，真实 `ServerLevel` + `.mca` 存档）里**累积着** agent 走过、
看过的全部方块与实体。但这份累积对 agent 不可达：

| 路径 | 为什么不行 |
|------|-----------|
| 直接读记忆端的 `.mca` | 记忆端**正在运行**，存档文件被游戏进程持有；且 `.mca` 是 Anvil 格式，读它需要 chunk 定位 + `block_states.palette` + 位解包，与本项目"只读 NBT"的既定边界冲突 |
| 读 `terrain.nbt` / `entities.nbt` | 这两个是**瞬时语义**——每次采集整体覆写当前维的桶，只保留"最近一帧看见了什么" |
| 读 `block_entities.nbt` / `biomes.nbt` / `containers.nbt` | 这三个**确实是累积的**，但只覆盖方块实体 / 群系 cell / 容器——不含普通方块，不含实体 |

所以 agent 能回忆的上限 = 最后一次 `vision/snapshot` 的视野。走开、转身、视野外，全丢。

### 1.2 现有 7 个文件的语义分类（已核实）

| 文件 | 内容语义 | 内存结构 | 写盘条件 | 给谁读 |
|------|---------|---------|---------|--------|
| `terrain.nbt` | **瞬时**（本帧可见方块） | `worlds: Map<dim, CompoundTag>`，当前维桶整体替换（`VisionTerrainStore.java:202`） | 每次采集无条件 | 记忆端 |
| `entities.nbt` | **瞬时**（本帧渲染到的实体） | 同上（`VisionEntityStore.java:182`） | 每次采集无条件 | 记忆端 + `vision/entity` |
| `block_entities.nbt` | **累积 union** + **F1 即时修剪** | `byDim: Map<dim, Map<posKey, StoredEntry>>`（`VisionBlockEntityStore.java:18`） | 有新增/变化，**或有修剪** | 记忆端 |
| `biomes.nbt` | **累积 union**（跨会话单调） | `byDim` 单调 union（`VisionBiomeStore.java:20,43`） | 有新增 cell | 记忆端 |
| `containers.nbt` | **累积 union** + **F1 延迟修剪** | `byDim`，启动 load、提交 upsert（`ContainerMemoryStore.java:74`） | 有提交或判删 | 记忆端 |
| `memory_cells.bin` | 记忆**镜像的几何格清单** | 记忆端写 | 每 10 tick | 采集端（判删输入） |
| `memory_sprites.bin` | sprite alpha 表缓存 | 记忆端写 | epoch 变化 | 采集端（几何判据输入） |

**两个瞬时、三个累积，无例外。** 且三个累积文件共享同一实现模式（§4.1 直接照抄）。

**⚠ 修正（2026-10-07）**：上表初版把 ③ `block_entities.nbt` 记作"只增不删"。**这与代码不符**——
v2.38（§4.1 F1 / 决策 G·H·I）已在采集端引入**唯一删除原语**，把"判据证明已消失"落到两份持久负载上
（`ObjectResolver.java:409-412`）：

| 文件 | 修剪时机 | 为什么不对称 |
|---|---|---|
| ③ `block_entities.nbt` | **即时**（`applyDeletions`） | NBT 载荷每帧可观测、可重建；误剪代价 = 一轮闪烁且自愈 |
| ⑤ `containers.nbt` | **延迟 K 代际** + 观测到活体即**撤销** | Items 是交互事件产物，观测层面拿不回来 ⇒ 必须给可撤销窗口 |

这一条对"agent 读哪些文件"有直接影响（见 §1.2.1）。

### 1.2.1 哪些文件是给 agent 的（承 §1.1）

**"累积"与"给 agent"在方案里是两件不同的事**，不要混为一谈：

| 文件 | 给谁读（本表原列） | agent 读它能得到什么 | 限制 |
|---|---|---|---|
| ① `terrain.nbt` | 记忆端 | 本帧可见方块 + 三份删除清单 | **瞬时**，无累积语义 |
| ② `entities.nbt` | 记忆端 + `vision/entity` | 本帧可见实体 | **瞬时** |
| ③ `block_entities.nbt` | 记忆端 | 方块实体的完整 NBT 负载，累积 | **只含方块实体**，没有普通方块 |
| ④ `biomes.nbt` | 记忆端 | 各处群系 id，单调累积 | 粒度 = **4×4×4 quart cell** |
| ⑤ `containers.nbt` | 记忆端 | 容器槽位内容 | **滞后**（K 代际延迟 + 撤销窗口）；末影箱段无坐标 |
| ⑧ `terrain_union.nbt` | **agent**（本方案新增） | 累积方块 | — |
| ⑨ `entities_union.nbt` | **agent**（本方案新增） | 累积实体 + 占用格 | — |

为什么只给 ①② 造了并集副本、却让 agent 直读 ③④⑤：**记忆端需要的那两份恰好是瞬时的那两份**。
方块实体 / 群系 / 容器天生就是累积的，agent 直接读原文件即可，没有"被覆写掉"的风险。
⑧⑨ 的存在理由就是这两点的交集——**唯二两份"记忆端需要、却又每帧整体覆写"的内容**，
必须另存一份给 agent 才留得住。

⑦ `memory_sprites.bin` 是二进制查找表且零坐标——**不是** agent 的读物；⑥ `memory_cells.bin` 描述的是
**记忆镜像的候选格**（"记忆端有什么"），不是"现实里有什么"，给 agent 读只会造成误读。

### 1.3 为什么不能把 `terrain.nbt` / `entities.nbt` 改成累积

**理由 A —— 记忆端的删除守卫会当场瘫痪（决定性）**

`DeletionApplier.apply` 的删除主循环（`DeletionApplier.java:107,125-129`）：

```java
final Set<BlockPos> currentTerrain = terrain.blocks().keySet();
...
for (BlockPos pos : deletions) {
    if (currentTerrain.contains(pos)) {   // ← 守卫
        deletionVisibleSkipped++;
        continue;                          // 本帧还看得见 → 拒绝删
    }
    ...
}
```

守卫的语义是「**采集端说这格消失了，但它又出现在本帧的可见方块里 → 矛盾 → 以可见为准**」。

`blocks` 一旦成为历史全集，任何被删的格历史上必然出现过 → 必然命中守卫 →
**`deletions` 全部被跳过** → 减量通道整体失效，记忆世界只增不减。

注意这里的关键区分：`blocks` 在删除流程里**不是判据**（判据在 `memory_cells.bin` → `DeletionJudge`），
它是**守卫**。所以改语义的后果不是"多删"，是**漏删**。方向相反，结论相同。

**理由 B —— 记忆端每次更新都要解析整个文件（决定性）**

`MemoryRestorer.tick` 有 mtime 门控（`MemoryRestorer.java:161-173`：文件 mtime 未变 → 不读不解压），
但门控只省掉**空闲**成本。只要采集端写一次盘，记忆端就要走 `readFile`（`MemoryRestorer.java:340`）
**解析全文件各维桶**——包括它根本不用的累积部分。union 长到几 MB 后，这份解析成本随每次采集发生。

**理由 C —— 语义混装**

`blocks` 同时服务两个语义相反的需求：记忆端要"这一帧看到了什么"（否则无法判删、无法指纹 diff），
agent 要"我见过什么"。塞进同一字段是双写一致性的来源。

### 1.4 现有删除链路的完整事实（2026-10-07 复核）

union 的生成逻辑直接复用现有删除算法，故先把链路钉死。以下**逐条经代码复核**：

```
┌─────────── 判据侧（全在采集端） ──────────────────┐
│  memory_cells.bin  ──→ 候选清单（哪些格要检查）    │
│  memory_sprites.bin ─→ 形状判据的 sprite alpha 掩码│
│          ↓                                       │
│  四条判据路径 → 产出三条清单                       │
│    ① 深度判据（opaque / translucent）→ deletions  │
│    ② 形状判据（shaped）              → deletions  │
│    ③ 状态直读（signalLoss 族）        → signalLossDeletions │
│    ④ 实体占用直读（entity 段）        → entityDeletions     │
└──────────────────┬───────────────────────────────┘
                   │
┌─────────── 通道 + 守卫（跨进程） ─────────────────┐
│  terrain.nbt   = 三条清单的载体（VisionTerrainStore.java:170-198）│
│                + blocks 作方块可见集守卫（DeletionApplier.java:107,126）│
│  entities.nbt  = entities 的 uuid 集作实体可见集守卫（EntityRestorer.java:336）│
└──────────────────┬───────────────────────────────┘
                   ↓ 记忆端
  DeletionApplier.apply(level, terrain, ENTITY.currentUuids(dim))   // MemoryWorldManager.java:394
```

三条要点：

1. **两个 `.bin` 只被采集端读**（`VisionApi.java:76` / `ObjectResolver.java:241`），从不跨进程。
   它们是**判据的输入数据**，不是通道。注意 `memory_sprites.bin` 只服务四条路径中的第 ② 条
   （`ObjectResolver.java:959` 的 `sprites.maskForIndex`），另三条用不上它。
2. **两个瞬时 `.nbt` 是同一种角色——"可见集守卫"**，语义完全对称：`terrain.blocks` 挡方块误删
   （`if (currentTerrain.contains(pos)) continue;`），`entities` 的 uuid 集挡实体误删
   （`EntityRestorer.java:251`：「当前可见实体绝不可删」）。
3. **`deletions` 变量在 `ObjectResolver.resolve` 内当场就存在**（`DeletionJudge` 的直接返回值），
   所以 union 的维护**不需要读任何文件，完全在采集端内部闭环**。

## 2. 方案总览

### 2.1 文件布局

> **本节已按 §11（region 分片）改写。** 分片定案于 2026-10-07，完整规格见 §11。

```
<gameDir>/stevex/vision/
  terrain.nbt                      ← 不动（瞬时）
  entities.nbt                     ← 不动（瞬时）
  memory_cells.bin                 ← 不动（记忆端写、采集端读）
  memory_sprites.bin               ← 不动（记忆端写、采集端读）

  terrain_union/                   ← ⑧【新】累积，给 agent 读（原 terrain_union.nbt）
    minecraft_overworld/r.0.0.nbt
    minecraft_the_nether/r.0.0.nbt
  entities_union.nbt               ← ⑨【新】累积，给 agent 读（不切片，§11.7）

  block_entities/                  ← ③ 原 block_entities.nbt，按 region 切分
    minecraft_overworld/r.0.0.nbt
  biomes/                          ← ④ 原 biomes.nbt，按 region 切分
    minecraft_overworld/r.0.0.nbt
  containers/                      ← ⑤ 原 containers.nbt，按 region 切分
    minecraft_overworld/r.0.0.nbt
    ender.nbt                      ← 末影箱段（无坐标，不能分片，§11.6）
```

- **切分范围：③④⑤⑧ 四个累积文件**；⑨ 因键是 UUID 不切（§11.7），①② 是瞬时文件、本就不长。
- ⑧⑨ 是新增文件，**记忆端完全不感知**；③④⑤ 的格式变了，**记忆端必须跟着改**（§11.9）。

### 2.2 数据流

```
             采集端（agent 游戏进程）                        记忆端（MemoryWorld 进程）
  ┌──────────────────────────────────────────────┐   ┌────────────────────────────────┐
  │  vision/snapshot 触发（人工，唯一触发点）      │   │                                │
  │        ↓                                     │   │                                │
  │  深度采集 → 反投影 → ObjectResolver.resolve   │   │                                │
  │        ├─ 本帧可见方块 ────────┬──────────────┼──→│ terrain.nbt → 守卫 + toPlace    │
  │        │                       │              │   │        ↓                       │
  │        │                       └──→ terrain_union.nbt ──→ 【agent 读】             │
  │        ├─ 本帧可见实体 ────────┬──────────────┼──→│ entities.nbt → 复原             │
  │        │                       └──→ entities_union.nbt ─→ 【agent 读】             │
  │        └─ deletions ←──────────┼──────────────┼───│← memory_cells.bin（几何镜像）   │
  │             │                  │              │   │                                │
  │             └──────────────────┘              │   │  deletions 应用 + 守卫          │
  │             （同时用于从 union 中移除）        │   │                                │
  └──────────────────────────────────────────────┘   └────────────────────────────────┘
```

**关键性质**（依据见 §1.4）：`deletions` 本来就是采集端自己算出来的（`DeletionJudge` 用
`memory_cells.bin` + 本帧深度图），所以"从 union 中移除被判删的格"**完全在采集端内部完成，
不引入任何新的跨进程耦合**。union **不在删除链路上**——它只是搭同一班车（§4.2）。

### 2.3 为什么是两个新文件，而不是在同文件加并列键

并列键（在 `terrain.nbt` 桶里加一个 `blocksUnion`）是更小的改动，但**在理由 B 上输掉**：

`MemoryRestorer.readFile` 用的是 `NbtIo.readCompressed`，**整个文件一次性解析**。
并列键方案下，记忆端每次收到更新都要反序列化整个 union（哪怕只用其中 841 字节的 `blocks`）。
新文件方案下，记忆端的解析成本**永远钉在当前规模**，与 union 长多大无关。

代价只是多两个文件（7 → 9），以及两次写盘（可接受，见 §7.2）。

## 3. 文件格式

### 3.1 通用契约

> **⚠ 本节描述的是分片前的单文件契约。** §11 定案后，③④⑤⑧ 四者改为**目录 + 区文件**：
> `worlds` 外层与顶层 `currentDimension` 被**目录层级**取代，桶内键名与条目形态不变。
> 分片后的契约见 **§11.5**；本节保留用于描述 ⑨（不切片）与过渡期的旧格式。

沿用现有 5 个文件共同的 `WorldsFile` 分桶契约（`WorldsFile.java:17-19`）：

```
顶层 { "currentDimension": "<dimId>", "worlds": { "<dimId>": <桶内容> } }
```

复用 `WorldsFile` 工具类（采集端已有同名实现），agent 侧只需一套解析逻辑即可读全部 7 个 NBT 文件。

### 3.2 `terrain_union.nbt`

```jsonc
{
  "currentDimension": "minecraft:overworld",
  "worlds": {
    "minecraft:overworld": {
      "updatedAt": 1720000000000,        // 本桶最后一次写盘的墙钟毫秒（桶级快照）
      "gameDay": 12,                      // 本桶最后一次更新时的游戏日（= dayTime / 24000）
      "blocks": {
        "-41,62,31": { "block": "minecraft:stone",   "state": {},                  "lastSeenDay": 8  },
        "-37,64,28": { "block": "minecraft:chest",   "state": { "facing": "north" }, "lastSeenDay": 12 },
        "-42,62,37": { "block": "minecraft:water",   "state": { "level": "0" },    "lastSeenDay": 12 }
      }
    },
    "minecraft:the_nether": { /* 同构，独立 union */ }
  }
}
```

- `blocks` 的键与值形态**逐字沿用** `terrain.nbt`（`"x,y,z"` → `{block, state}`），
  agent 侧可以用同一套解析代码。
- `lastSeenDay` / `gameDay` 为**暂缓字段**（理由见 §3.4），实施时省略。
- 桶级 `updatedAt` 冗余一份，供"一眼判断整桶多旧"用，免去遍历。

### 3.3 `entities_union.nbt`

```jsonc
{
  "currentDimension": "minecraft:overworld",
  "worlds": {
    "minecraft:overworld": {
      "updatedAt": 1720000000000,
      "gameDay": 12,
      "entities": {
        "069a79f4-44e9-4726-a5be-fca90e38aaf5": {
          "id": 42, "type": "minecraft:zombie",
          "pos": [-38.5, 64.0, 31.5],
          "motion": [0.0, -0.078, 0.0],
          "rotation": [180.0, 0.0],
          "onGround": 1,
          "health": 20.0,
          "firstSeenDay": 10,               // 【新】首次见到（暂缓，§3.4）
          "lastSeenDay": 12,                // 【新】最后见到（暂缓，§3.4）
          "cells": ["-39,64,31", "-39,65,31"],   // 【新】本帧观测时的 AABB 占用格，见下
          // 以下特例载荷键与 entities.nbt 逐字同形（v2.34/v2.35/v2.41）
          "item":  { /* 掉落物整份物品栈 */ },
          "nbt":   { /* 展示实体整份 payload */ },
          "living":{ /* 活体全量属性 */ }
        }
      }
    }
  }
}
```

- 键 = 实体 **UUID**（与 `entities.nbt` 一致），不是坐标——实体在移动。
- `cells` 是 union 侧**独有**字段（`entities.nbt` 没有）：记录该实体最后被观测到时的
  **AABB 占用格**，用于 §4.3 的移除判据。形态用 `"x,y,z"` 字符串数组，与 `blocks` 的键同风格，
  agent 侧无需解码 `BlockPos.asLong`。
  **口径必须与记忆端一致**——`floor(minX)..floor(maxX)` 三轴闭区间枚举，即 `ObjectResolver.
  visibleEntityCells`（`ObjectResolver.java:492-510`）已在算的那一套；每次观测到该实体时**整体重写**
  （实体在移动，旧格作废），这是"更新"而非"并入"。格集为空（AABB 退化/被过滤）时按空处理，
  永不触发移除（保守）。
- 载荷键（`item` / `nbt` / `living`）**逐字沿用** `entities.nbt` 的既有形态与白名单策略
  （`VisionEntityStore` 的序列化直接复用）。
- `firstSeenDay` / `lastSeenDay` 为**暂缓字段**（§3.4）。原设计中实体比方块多一个
  `firstSeenDay`：实体的"持续存在"是可观测的连续现象（跟踪同一只僵尸），方块没有这个价值。

### 3.4 暂缓项：每格时间戳（`lastSeenDay` / `firstSeenDay`）

> **用户 2026-10-07 表示先不考虑时间戳**，故本节内容**暂缓**——实施时 §3.2 / §3.3
> 两个格式中的 `lastSeenDay`（及桶级 `gameDay`）**省略**，§5.2 的实体幽灵对策随之不适用。
>
> ⚠ **§5.3 决策 C 已定案，本节不再连带它**：`updatedAt`（墙钟，诊断用）与每格时间戳
> **无关**，独立保留——切片后为区级（§11.5）。本节只影响 `lastSeenDay` / `firstSeenDay` / `gameDay`。
> 本节保留完整设计备查，将来需要时可直接启用。

**去掉时间戳不影响条件写（§4.5）**。条件写由三重触发保证：① 有新增格；② 有格的内容变化；
③ 有格被移除。同一批方块重复看到（内容不变、且不在删除清单里）不会置 dirty，因而不会触发写盘
——这正是原设计想要的效果，**不依赖时间戳**。

（以下为原设计备查）**粒度选择**：

- **不用墙钟毫秒**：同一游戏日内的重复观测会让每格毫秒值都不同 → 每次采集整个 union 都 dirty
  → 条件写彻底失效。
- **不用游戏 tick**：同上，粒度太细。
- **选游戏日（`dayTime / 24000`，20 分钟）**：同一游戏日内重复看到同一批方块 → 值不变 → 不写盘；
  跨日 → 一次全量写。每天最多一次全量重写，可接受。

游戏时间优于墙钟还因为：记忆世界是冻结的（不 tick），墙钟会持续走；而 agent 的"时间感"来自游戏时间，
且 agent 能从 `f3` / `snapshot` 拿到当前 `dayTime` 做比较。

## 4. 采集端维护逻辑

### 4.1 镜像结构——照抄 `VisionBlockEntityStore`

三个现有累积 store 用的是同一个模式，直接复用：

```
byDim: Map<dim, Map<posKey, Entry>>     // 内存镜像，Entry 用 record（不可变）
构造时 load() 读入既有文件              // 跨会话累积
sync() 里移除 + put 新增/变化的条目      // 旧的原地保留
dirty 标志 + 条件写                     // 没变化不落盘
save() 全量写回整个 byDim               // 内容是累积的，物理动作是全量写
```

### 4.2 `terrain_union` 的更新规则：先删后并 + 可见守卫

```java
Map<String, Entry> union = byDim.computeIfAbsent(dim, k -> new LinkedHashMap<>());

// ① 先移除：被判删的格——带可见守卫（与记忆端 DeletionApplier.java:126 同规则）
for (BlockPos p : deletions)            if (!frameBlocks.contains(p)) union.remove(posKey(p));
for (BlockPos p : signalLossDeletions)  if (!frameBlocks.contains(p)) union.remove(posKey(p));

// ② 后并入：本帧可见方块
for (var e : frameBlocks.entrySet()) {
    String key = posKey(e.getKey());
    Entry  old = union.get(key);
    Entry  now = new Entry(e.getValue().blockId(), e.getValue().stateProps(), gameDay);
    if (old == null)                        { union.put(key, now);                       dirty = true; }
    else if (!old.sameContent(now))         { union.put(key, now);                       dirty = true; }  // 现实中换了方块
    else if (old.lastSeenDay != gameDay)    { union.put(key, now.withDay(gameDay));      dirty = true; }  // 跨日刷新
    // 其余情况（内容相同、同一游戏日）→ 跳过，不置 dirty
}

// ③ 条件写
if (dirty) { dirty = false; scheduleSave(); }
```

**顺序是承重的（先删后并，不是先并后删）**：

- 采集端必须复现记忆端的可见集守卫——**本帧还看得见的格，不许删**。
- 实践中 `deletions` 与 `frameBlocks` 互斥（`DeletionJudge` 用本帧深度图判定，本帧可见者
  不可能被判"消失"），故两种顺序在正常路径上结果相同；但"先删后并"让*本帧可见永远赢*成为
  **结构性保证**而非巧合，且与记忆端语义对齐（两端规则一致，将来排查问题可对齐）。
  反向顺序的失效方向是坏的：判据边界抖动时会抹掉刚看见的方块。

**②的第二个分支同样是承重的**：玩家把一个石头换成木板时，union 必须跟着变——它记录的是
"**这个格现在是什么**"，不是"这个格曾经是什么"。这是"增+删"语义（§5.1）的自然推论。

**union 不驱动记忆世界的删除**。删除记忆世界走的是 §1.4 的既有链路；union 只是**搭同一班车**：

```
deletions ──┬──→ terrain.nbt       ──→ 记忆端删记忆世界   （已有，不动）
            └──→ terrain_union.nbt → 删自己的副本        （新增，纯本地）
```

### 4.3 `entities_union` 的移除：复用已有判据（与记忆端逐位一致）

实体的移除**直接复用记忆端已经实现的判据**，不引入新算法。

**判据本体**（`EntityRestorer.java:227-244`，v2.22 §7.11「指定维冻结实体**全部 AABB 占用格**
是否都在 `provenEmpty` 中」）：

```java
public boolean allCellsEmpty(String dimension, UUID uuid, Set<BlockPos> provenEmpty) {
    Entity e = applied.get(uuid);
    final AABB box = e.getBoundingBox();
    for (x, y, z 遍历 box 覆盖的所有格)
        if (!provenEmpty.contains(new BlockPos(x, y, z))) return false;
    return true;
}
```

`provenEmpty` = `entityDeletions ∪ {相机格}`；记忆端的应用循环在 `DeletionApplier.java:197-208`：

```java
for (UUID uuid : entities.uuids(dimension)) {
    if (currentEntityUuids.contains(uuid)) continue;        // 本帧可见 → 不删
    if (entities.allCellsEmpty(dimension, uuid, provenEmpty)) entities.discard(dimension, uuid);
}
```

**「AABB → 覆盖格」的枚举口径在代码里已经统一为 `floor(min)..floor(max)`**，三处同口径：

| 处 | 位置 | 用途 |
|---|---|---|
| 记忆端写候选 | `MemoryCellReporter.java:360-377` | 枚举冻结实体占用格 → cells 实体段 |
| 采集端双保险 | `ObjectResolver.java:492-510` | 本帧可见实体覆盖格 → `visibleEntityCells` |
| 记忆端判全空 | `EntityRestorer.java:233-243` | `allCellsEmpty` |

`ObjectResolver.java:488-489` 的注释明确要求三者一致：「格枚举与记忆侧 `MemoryCellReporter`
的实体段同口径（`floor(min)..floor(max)`），否则两边对同一实体的格集不一致，双保险会假触发」。

**为什么复用是"逐位一致"而不是"接近"**：两边取的 AABB 来自**同一帧**。记忆世界的冻结实体由
`entities.nbt` 重建，而 `entities.nbt` 每次采集整体覆写当前维——所以记忆端 `allCellsEmpty` 里的
`e.getBoundingBox()` 就是"该实体最后一次被看见时"的 box；union 的 `cells` 记的也是同一帧、同一
枚举口径的格集。两者不是"近似相等"，是同一个集合的两次计算。

**采集端因此需要的**：每个实体的占用格按 uuid 分组。`ObjectResolver.visibleEntityCells`
（第 492 行）已在做同一件事——遍历 `snap.entities()` 的 `e.box()` 枚举覆盖格——只是它把结果
合并成一个 `Set<BlockPos>` 供 `EntityPresenceCorrector` 当双保险用；**按 uuid 分组是同一个循环体**。

```java
// ① 并入：本帧可见实体（连同其占用格）
for (var e : snap.entities())
    union.put(e.uuid(), new Entry(..., cellsOf(e.box())));      // 与 visibleEntityCells 同循环体

// ② 移除：逐位复现 allCellsEmpty 判据
for (UUID uuid : union.keySet()) {
    if (frameEntityUuids.contains(uuid)) continue;                        // 本帧可见 → 不删
    if (union.cells(uuid) 全部 ∈ entityDeletions) union.remove(uuid);     // = allCellsEmpty
}
```

**一条仍存在的覆盖边界**（与判据无关）：`MemoryCellReporter` 写候选时有 `entityGate`
（整实体粒度的追踪门限）与 96 格距离两道过滤（`MemoryCellReporter.java:360-377`），
**超出范围的实体其占用格根本不进候选**，永远不会出现在 `entityDeletions` 里。这部分实体的
幽灵由 §5.2 / §6.1 说明。

### 4.4 挂载点

`ObjectResolver.resolve` 内，在各 store 的 `sync()` 之后（`ObjectResolver.java:377-430` 那一段）。
此时 `blocks` / `entities` / `deletions` / `signalLossDeletions` / `entityDeletions` 全部就位，
无需改动上游任何环节。

### 4.5 写盘策略（已定案 D：两者叠加）

`save()` 在渲染线程执行（`ObjectResolver.resolve` 经 `Minecraft.execute` 派发），
对 10 万格规模要几百 ms。采用两级：

1. **渲染线程**：`new LinkedHashMap<>(union)` 做一次**浅拷贝**（10 万条约几 ms；条目 tag 自放入起
   不再被修改，每次更新是整体替换，故浅拷贝之后无竞态），连同桶级元数据一起丢给后台 executor；
2. **后台线程**：NBT 编码 + gzip + 原子写。

外加**限频**（最短 5 秒间隔，超时才调度）。两者叠加：限频压掉高频采集的写盘次数，
浅拷贝 + 后台写消除渲染线程的停顿。

**关于原子写**：`writeAtomic`（`.tmp` + `ATOMIC_MOVE`，回退 `REPLACE_EXISTING`）的写法来自记忆端
`MemoryCellReporter.java:433-533`，但要明确这是**跨 mod 照抄写法，不是调用**——记忆端
`com.example.memworld` 与采集端 `name.modid.vision` 是两个独立的 mod / jar，`MemoryCellReporter`
不在采集端的 classpath 上。同理，**采集端此前没有任何后台线程**（vision 包内零 `ExecutorService`／
原子移动），本方案是**首次**在采集端引入异步写盘，须自行承担线程生命周期与退出前 flush
（实现见 §10）。

**限频是后沿触发**：排定的任务在**运行时**才取快照，届时拿到的是最新那一份——窗口内到达的多次变更
被合并，而不是被丢弃。这同时要求各 store 的浅拷贝由**渲染线程**做（union 的 map 只在渲染线程变更）。

## 5. 决策项与结论

### 5.1 决策 A：union 是"只增"还是"增+删"？——**已定案：增+删（用户 2026-10-07）**

| | 语义 | agent 看到的世界 |
|---|---|---|
| 只增 | 历史全集，永不遗忘 | **考古层**：一堆已经不存在的方块。agent 以为箱子还在，跑过去发现没有 |
| **增+删** | 跟随 `deletions` 移除判删格 | **当前状态的投影**：会漏（覆盖不全），但不会骗 |

**采纳"增+删"**。承接需求原话"让 agent 读到累积记忆"——agent 要的是**离开后还记得**，
不是**记得一切曾经存在的**。

反驳"只增更安全"的说法：删除判据（`DeletionJudge`）本身就是有守卫、有假阳性防护的成熟通道
（`memory_cells.bin` → 深度判据 / 状态直读两条通道），不是随手删；而只增的代价是 agent 被迫
自己维护"哪些还在"的推理，那是把问题推给了不该承担它的一方。

### 5.2 决策 B：**超出判据覆盖范围**的实体幽灵怎么处理——**暂缓（用户 2026-10-07：先不考虑时间戳）**

实体删除判据**有覆盖范围**：`memory_cells.bin` 的实体段只含**记忆镜像里、且在 96 格球内**的格
（`removalMaxRayDist`），故 §4.3 的移除（无论多精确）只能作用于 `entityDeletions` 给出的格。
**走出这个范围的实体永远不会被移除**——一只僵尸跑掉了，它会永远留在 `entities_union.nbt` 里，
带着消失那一刻的 `pos` / `health` / `living` 载荷。

两个方向（**当前按"接受"实施**）：

- **接受**：agent 能问"这一带以前有过什么"，但要自己判断可信度；
- ~~**加时间戳**：`firstSeenDay` / `lastSeenDay` 让 agent 能区分"刚看到的"和"三天前的"~~
  ——用户 2026-10-07 表示先不考虑，暂缓（设计保留在 §3.4）。

### 5.3 决策 C：桶级的 `updatedAt` / `gameDay` 要不要——**已定案：保留 `updatedAt`、去掉 `gameDay`（用户 2026-10-07）**

原理由：每格已带 `lastSeenDay`，桶级两个字段是冗余的；保留是为了免遍历即可判断"整桶多旧"。

随 §3.4 的时间戳一并调整：`gameDay` **去掉**；`updatedAt`（墙钟，本桶最后一次写盘时间）
**与每格时间戳无关，独立保留**——它只用于诊断"这个文件多久没更新了"，成本几个字节。

> **⚠ 粒度被 §11 改动（2026-10-07）**：③④⑤⑧ 切片后 `updatedAt` 由**桶级降为区级**（§11.5）
> ——语义反而更准（能看出**哪个区**多久没更新）。**⑨ 不切片，仍是桶级**（§3.3）。
> "保留 `updatedAt`"这条决策本身不变，变的只是它挂在哪一层。

### 5.4 决策 D：写盘策略（§4.5）——**已定案：两者叠加（用户 2026-10-07）**

选项：(a) 同步写 + 限频；(b) 后台写 + 浅拷贝；(c) 两者叠加。
**采纳 (c)**——浅拷贝 + 后台 executor，外加最短 5 秒限频。

### 5.5 决策 E：文件命名——**已定案：`terrain_union` / `entities_union`（用户 2026-10-07）**

候选：`terrain_union.nbt` / `entities_union.nbt` 或 `terrain_memory.nbt` / `entities_memory.nbt`。
后者易与"记忆世界"（memworld）混淆，**采纳前者**。

> **⑧ 的形态被 §11 改为目录（2026-10-07）**：`terrain_union/<维>/r.<X>.<Z>.nbt`（§11.3）。
> **目录名沿用 `terrain_union`**，故"与 memworld 区分"的取舍不变；
> ⑨ 保持单文件 `entities_union.nbt`，命名结论完全不变。

## 6. 已知偏差与定位

### 6.1 与记忆世界必然漂移

两个方向都会漂：

| 方向 | 成因 |
|------|------|
| union 说"删了"，记忆世界还在 | `DeletionApplier` 有守卫，会 `refused` 一部分删除（`DeletionApplier.java:137` 有专门的失配告警，注释明说有两种相反成因） |
| union 里有的格永远删不掉 | 采集端 union 有、记忆端镜像没有的格，不进 `memory_cells.bin`，永不被判删 |

注意两端用的是**同一份 `deletions`**（§1.4），所以漂移不来自判据本身，只来自两端的**应用阶段**
——记忆端的可见集守卫与 `refused`（`DeletionApplier.java:125-129`），union 侧的可见集守卫
（§4.2 / §4.3）。两边**同规则、各自独立执行**，故结果可能不同。这是**结构性的，不是缺陷**：
任何"两个独立维护的累积"都必然漂移。

### 6.2 定位声明（承重）——**已定案：接受（用户 2026-10-07）**

**这两个文件是 agent 的世界模型，不是记忆世界的精确镜像。**

- 用途：**背景知识**——规划时的先验、路径上的已知障碍、"上次见过的箱子在哪"
- 非用途：**事实来源**——agent 真正要操作某个方块/容器时，必须用 `vision/snapshot` 当场确认
- 接受：它可能比记忆世界多几块或少几块

写进文档是为了防止将来有人拿它当权威源做破坏性决策。

## 11. region 分片（2026-10-07 定案并实施；实施状态见 §11.13）

### 11.1 动机与本节的定位

**问题**：NBT 没有索引——读一个文件必须**整体解压 + 建树**，无法"只读 x 附近"。① `terrain.nbt`
今天 841 字节，但 ⑧ `terrain_union` 长到 MB 级后，agent 每次读都要把整个世界的方块建进内存。

**§7.1 漏掉的那个轴**：§7.1 只算了**压缩后的磁盘体积**，并据此写了"文件体积不是主要矛盾"
（§7.1 末句）。那句话**对写盘耗时成立**（zlib 压缩率高，I/O 不贵），**对解析后的内存不成立**：
1–2 MB 的压缩文件解出来是 26 万个 `CompoundTag`（Java 侧上百 MB 对象图，Python 侧更甚）。
**分片解决的正是这个轴。**

**记录**：本次提出的动机是"这些文件都太大了、读取会导致内存爆炸"。核对现状后确认这是**预判
而非实测**——2026-10-07 实测全部 5 个文件合计仅 43 KB（④ `biomes` 39 KB 为最大，① 841 B，
② 215 B；⑧⑨ 尚未落盘）。但预判的**方向与量级都有据**：NBT 无索引这一条是结构性的，不随观测变化。

**第二个动机（2026-10-07 追加）**：切片同样加快**记忆端的更新**——今天只要一个区变了，
记忆端就要全量解析整个文件。这笔收益是真的，但它带来一个必须对冲的新成本
（"发现哪个区变了"从免费变成 O(目录)），**详见 §11.9**。

### 11.2 定案内容

| # | 项 | 结论 |
|---|---|---|
| 1 | 区的划分 | **照抄 MC**：`region = 32×32 chunk = 512×512 方块`，**全高度**（Y 不入键） |
| 2 | 区坐标 | `regionX = blockX >> 9`，`regionZ = blockZ >> 9`（512 = 2⁹） |
| 3 | 文件名 | `r.<regionX>.<regionZ>.nbt` —— 二维 X.Z，与 MC 的 `r.X.Z.mca` 同构 |
| 4 | 切分范围 | **③ `block_entities` / ④ `biomes` / ⑤ `containers` / ⑧ `terrain_union`** 四个 |
| 5 | 不切 | **⑨ `entities_union`**（键是 UUID，无坐标映射，§11.7） |
| 6 | 变更发现 | 每个目录根加 `_index.nbt`（区 → `updatedAt`），记忆端**仍只 stat 一个文件** | §11.9.3 |

> 选这四个的理由与 §1.2.1 同一逻辑：**"累积"是会长大的前提，而"键是坐标"是能切片的前提**。
> 四个文件同时满足；⑨ 满足前一条、不满足后一条。

### 11.3 目录布局

```

  entities.nbt                     ← 不动
  memory_cells.bin                 ← 不动
  memory_sprites.bin               ← 不动
  entities_union.nbt               ← ⑨ 不切片，保持单文件

  terrain_union/                   ← ⑧ 原 terrain_union.nbt
    _index.nbt                     ← 【新】维 → {区坐标 → updatedAt}，见 §11.9
    minecraft_overworld/
      r.0.0.nbt
      r.0.1.nbt
      r.-1.0.nbt
    minecraft_the_nether/
      r.0.0.nbt
  block_entities/                  ← ③ 原 block_entities.nbt
    _index.nbt
    _pose.nbt                      ← agent 姿态 + dayTime 单独落盘（§11.6.1，实施期补）
    minecraft_overworld/r.0.0.nbt
  biomes/                          ← ④ 原 biomes.nbt
    _index.nbt
    minecraft_overworld/r.0.0.nbt
  containers/                      ← ⑤ 原 containers.nbt
    _index.nbt
    minecraft_overworld/r.0.0.nbt
    ender.nbt                      ← 末影箱段单独落盘（§11.6）
```

> ③ 与 ⑤ 各多出一个**根级标量文件**（`_pose.nbt` / `ender.nbt`）：它们承载**没有坐标**的那部分
> （③ 的 agent 姿态与世界时间、⑤ 的末影箱玩家态），既进不了区文件，也不能进 `_index.nbt`
> ——后者会把索引 mtime 按"变了最快的那一个"的节奏刷新，门控当场失效。两者是同一判据
> （§11.6 / §11.6.1）：**变化频率与作用域都不同的东西，分属不同文件**。
> 前导下划线使其与 `r.<X>.<Z>.nbt` 天然区分，`listRegionFiles` 的解析器不会误收。

- **维目录名 = `dimId.replace(':', '_')`**（`minecraft:overworld` → `minecraft_overworld`）。
  冒号在 Windows 文件名中非法，必须替换；保留 namespace 以免与自定义维同名冲突。
- ③④⑤⑧ 统一为"**一文件一目录**"，agent 侧一套目录遍历代码读全部四个。
- `_index.nbt` 放在**目录根**（不分维），使记忆端**每类文件仍只需 1 次 stat**——与今天完全一致（§11.9）。

### 11.4 桶键 → 区坐标（★ ④ 与其余三个不同）

| 文件 | 桶内键 | 条目键 | 区坐标算法 |
|---|---|---|---|
| ⑧ `terrain_union` | `blocks` | `"x,y,z"`（方块坐标） | `x >> 9`, `z >> 9` |
| ③ `block_entities` | `blockEntities` | `"x,y,z"` | `x >> 9`, `z >> 9` |
| ⑤ `containers` | `containers` | `"x,y,z"` | `x >> 9`, `z >> 9` |
| ④ `biomes` | `cells` | `"qx,qy,qz"`（**quart**，`QuartPos.fromBlock` = `x >> 2`） | **`qx >> 7`, `qz >> 7`** |

> **★ ④ 是 `>>7` 不是 `>>9`。** 一个区 = 512 方块 = 512/4 = **128** 个 quart cell = 2⁷。
> 用 `>>9` 不会报错，但会让 ④ 的"区"实际缩水成 128×128 方块——**与其余三个文件同名不同义**，
> agent 就得为 ④ 单独维护一套区算法。此处必须钉死。
> （`VisionBiomeStore.java:135-136` 的 `cellKey` 用 `QuartPos.fromBlock` 生成键。）

### 11.5 区文件内部格式

区文件天然单维、天然单区，故去掉 `worlds` 外层与顶层 `currentDimension`：

```jsonc
// terrain_union/minecraft_overworld/r.0.0.nbt
{
  "dimension": "minecraft:overworld",  // 【新，实施期补】自校验：★ 权威源是目录名，本字段只用于发现"文件被搬了"
  "regionX": 0,                    // 【新】自校验：与文件名不一致即为错配
  "regionZ": 0,
  "updatedAt": 1720000000000,      // 本区最后一次写盘的墙钟毫秒（§5.3：区级）
  "blocks": {                      // ← 桶内键名与条目形态【一字不改】
    "-41,62,31": { "block": "minecraft:stone", "state": {} }
  }
}
```

- **桶内键名（`blocks` / `blockEntities` / `cells` / `containers`）与条目形态完全不变**——
  agent 的**条目解析器零改动**，变的只是"文件在哪、叫什么"。
- `regionX` / `regionZ` 是冗余自校验字段：将来若改区大小（§11.10），一眼就能发现旧文件未重分片。
- `updatedAt` 由**桶级降为区级**——语义反而更准（能看出哪个区多久没更新）。
- ③④⑤ 原有的 `version` 等文件级元数据，**冗余进每个区文件**（简单，且单区可独立解析）。
- 顶层 `currentDimension` 去掉：**采集端**的 `currentDimension()` 仍由 ③ 的 `_pose.nbt` 提供（记忆端原有
  读取方读的也一直是 `terrain.nbt`，不是 ③），**记忆端** ⑤ 的 `currentDimension` 根本没有读取方。
  何况分片后"文件最近写入维"这个说法本身已无意义——一次 `commit` 可以横跨多个维。

**★ `dimension` 为什么必须自报，而不能从目录名反推**（实施期发现的硬约束）：

目录名是 `dimId.replace(':', '_')`——**不可逆**。命名空间本身可以含 `_`：`my_mod:foo` → `my_mod_foo`
→ 反推成 `my:mod_foo`。而**采集端启动时必须扫全部区文件重建内存 union**（§11.8），它事先**不知道**
有哪些维 id 存在，只能拿着目录名去猜维 id——猜错就把记录搬了家（条目按绝对坐标键控，放进错误的维
不是格式错误，是静默错位）。

区文件自报 `dimension` 后，这条约束解开：采集端从文件内容读到真维 id，目录名退化为**纯定位**。
记忆端同理——它按 `_index.nbt` 里的真维 id 走，只在 `readRegion` 里做 `dimDirName(自报维) == 目录名`
的一致性检查，两边同用这个（有损但一致的）规则，故 `_` 的不可逆性不会造成误判。

副产品：**整棵树在 `_index.nbt` 丢失时可精确重建**——扫目录、读每个区文件的自报维与区坐标，即可
还原出完整的索引（§11.8 的 `loadExisting` 正是这么做的），无需任何外部信息。

### 11.6.1 ③ 的 agent 姿态：同一类问题，第二份独立文件（实施期补）

本方案落笔时（§11.5）只考虑了"桶内的键"，漏看了 ③ 的桶里还混着**维级标量**：`agentPos` /
`agentYaw` / `agentPitch` / `agentFov` / `dayTime`（`VisionBlockEntityStore`）。它们：

- **没有坐标** ⇒ 进不了区文件（"按坐标分桶"对它们不存在，同 §11.6 的末影箱）；
- **每帧都在变**（`dayTime` 在世界时间推进时逐 tick 变）⇒ **不能进 `_index.nbt`**。这一条比"进不了区
  文件"更硬：

> 索引被重写 ⇒ 索引 mtime 变 ⇒ 记忆端的门控放行 ⇒ **每帧一轮全量 diff**。
> 于是 §11.9.2 那句"索引未变则 `stat` 成本≈零"当场失效，而 `pollIntervalTicks = 1`
> （`MemoryConfig.java:23`）的成本论证正是建立在那句话上的。

于是 ③ 也裂出一个独立文件：

```jsonc
// block_entities/_pose.nbt   （store 根，与维目录平级）
{
  "currentDimension": "minecraft:overworld",
  "worlds": {                        // ← 结构一字不改，与 §11.5 之前 ③ 的顶层完全相同
    "minecraft:overworld": {
      "agentPos": "12.5,64.0,-31.2", "agentYaw": 90.0, "agentPitch": 0.0,
      "agentFov": 70, "dayTime": 6000
    },
    "minecraft:the_nether": { … }
  }
}
```

**判据（两条问题共用的那一条）**：*两个变量的变化频率不同，就该分属不同文件*。
末影箱 ↔ 容器、姿态 ↔ 方块实体，各自落在频率谱的两端——把它们合进同一个 mtime 门控，
门控就只能按"变得最快的那一个"的节奏放行。

记忆端随之有**两个独立门控**（`MemoryRestorer` / `ContainerMemoryApplier` 各两个）：
一个 stat 索引、一个 stat 标量文件，任一放行即"这一轮有新内容"。**门的形状没变**（仍是每 tick
每个文件一次 stat），只是从"一个文件一个门"变成"两个文件两个门"——代价仍是 `O(1)`。

> 遗留项：`_pose.nbt` 目前每次写**全部维**的姿态。若日后维数多到在意这点开销，可改为按维分文件
> （`_pose.<维目录名>.nbt`）；现在不做——维度数是个位数，且这份文件本来就是"整体替换"语义。

### 11.7 ⑨ 为什么不切

⑨ 的键是**实体 UUID**，坐标在值里（`pos`）——**"坐标 → 文件"这个映射在 ⑨ 上不存在**。
要切就得先发明一个（按"最后观测位置的区"入桶），随之而来三件事：

1. 实体跨区要"从 A 删、往 B 写"——**两个文件、无跨文件原子性**；
2. `cells` 可能跨区边界（与 `pos` 不同区）；
3. "uuid X 在哪个文件"没有索引就得**扫全目录**。

而 ⑨ 恰是体量最小的之一（实体的数量级是"见过几千个"，不是"几十万格"）。
**收益与复杂度不成比例，不切。** 将来若要切：入桶用条目里已有的 `pos`，`cells` 保留原样、
不参与桶分配（它是移除判据的输入，不是位置标识）。

### 11.8 采集端改动（内存模型：2 层 → 3 层）

**这是切分能真正省下写盘开销的前提**——只把文件切碎、内存里仍是平铺的全量表，`flush` 就得
每次重建全部内容，等于白切。

```
现状：byDim : Map<dim, LinkedHashMap<posKey, Tag>>
改后：byDim : Map<dim, LinkedHashMap<regionKey, RegionBucket>>
      RegionBucket = { LinkedHashMap<posKey, Tag> entries; boolean dirty; long updatedAt; }
```

- `sync` 的规则**一条不变**（键仍是 `posKey`），只是先定位到区桶再写入；
  **某区真有变更才置该区 `dirty`**。
- `publish()` 只浅拷贝 **dirty 区**（消掉现状里的一个 O(总量)）。
- `flush()` 只 `buildRoot` + 写 **dirty 区**对应的文件（消掉另一个 O(总量)，
  即 §7.2 说的"每次 dirty 的写盘是几百 ms 级"）。
- `loadExisting()` 改为**扫目录 + 逐区读**，仍然全量载入内存——**不做驱逐**（§11.12）。

**③④⑤ 不需要调度器**：它们本来就是**条件写**（③④ 有变更才写、⑤ 低频事件驱动），
分区后单次写盘**只会更小**，同步写可接受。⑤ 的"单写者、无竞态"结构理由
（`ContainerMemoryStore` 类 javadoc）不变。

### 11.9 记忆端改动（**§8 的修正在此**；同时是一次提速）

**这是本方案最大的一处代价，必须显式记账；但它同时带来一笔此前没算到的收益。**

#### 11.9.1 收益：切片同样加快记忆端的更新

这与 §2.3 当初"为什么另存独立文件"的论证**是同一条，只是下沉一级**：
§2.3 的原话是"记忆端每次收到更新都要反序列化整个 union（哪怕只用其中 841 字节的 `blocks`）"。
现在把 ③ 切片，等于说："记忆端每次收到更新都要反序列化**整个 ③**，哪怕只有一个区变了。"

- 今天：③ 一变 → `MemoryRestorer.readFile` **全量解析**（`MemoryRestorer.java:170-176`）
- 切片后：只解析**真变了的那几个区**

按 §7.1 的 MB 级规模估算，单次更新从"整文件解析"降到"单区解析"，约一个数量级。
**关键是这笔成本落在记忆端的服务端 tick 内**（`MemoryWorldManager.java:375-395` 逐个 restorer `tick`），
所以省下的不只是 CPU，是**记忆世界本身的卡顿**。

#### 11.9.2 代价：发现"哪个区变了"不是免费的，而它今天是免费的

```
MemoryConfig.java:23
  "pollIntervalTicks": 1,   // 每隔多少 tick 做一次源文件 mtime 检查（1 = 每 tick；
                            //   mtime 未变不读文件，stat 成本≈零，见 §7.4）
```

默认 1 = **每 tick 都 stat**，而这个默认值之所以成立，是因为每个 restorer 只对
**一个已知路径**做一次 `getLastModifiedTime`（`MemoryRestorer.java:163-170`；
`BiomeRestorer` / `ContainerMemoryApplier` 同款）。**"stat 成本≈零"是一条写进配置注释的设计前提。**

**切成目录后这条前提当即失效**：变成 `list 目录 + 逐个 stat`。按 §7.1 的规模
（10 个 MC region ≈ 100 个区文件/类型 × ③④⑤ 三类），即**每 tick 几百次 stat、20 Hz 下约 10–20 ms/tick**。
而且它是**每 tick 都付、永久付**——比它想省的那笔（只在文件真变时才付）出现得频繁得多。
**不处理这一条，净效果可能是变慢。**

#### 11.9.3 解法：保留"单点 mtime 门"，让它只指向索引

采集端在每个目录根维护一个小索引 `_index.nbt`：

```jsonc
// block_entities/_index.nbt
{ "dimensions": {
    "minecraft:overworld": { "0,0": 1720000000000, "-1,0": 1720000000123 },
    "minecraft:the_nether": { "0,0": 1720000000456 }
} }
```

- **数据源不是新的**：每个区文件里已有 `updatedAt`（§11.5），`updatedAtByDim` 也已经是这个结构，
  只是粒度停在"维"。索引是它的**一层投影**，不引入第二个真相来源。
- **记忆端的门控形状完全不变**：每 tick 仍只 **stat 一个文件**（`_index.nbt`）→ 空闲成本仍是"≈零"，
  与今天逐字节等价。
- 索引 mtime 变了 → **读索引**（小）→ 与本地缓存的 `{维 → {区 → updatedAt}}` **diff** →
  **只读那几个真变了的区文件**。
- 于是**两头都不亏**：发现成本 O(1) 不变，读取成本从 O(全量) 降到 O(变化的区)。

**写入顺序必须钉死：先写区文件，最后写索引（原子写）。** 记忆端是"看到索引变了才去读区文件"，
索引先写会让它读到还没更新的区。区文件本身的读一致性由 `writeAtomic` 保证（§11.5）；
注意 ③④⑤ **今天用的是裸 `NbtIo.writeCompressed`**（`VisionBlockEntityStore.java:335` /
`VisionBiomeStore.java:151` / `ContainerMemoryStore.java:151`），
即"写入半截"是**今天就有**的状态，靠记忆端的重试兜底（`MemoryRestorer.java:172`「写入半截等 → 保留旧 mtime，下轮重试」）。
切片时**顺带把这三处也换成 `UnionSaveScheduler.writeAtomic`**，这条重试逻辑的语义保持不变
（读区失败 → 不推进该区的本地 `updatedAt` → 下轮重试）。

#### 11.9.4 读取点清单

现有读取点全部是"**一个路径 → 一次全量 `readCompressed`**"：

| 文件 | 记忆端读取点 | 现状 |
|---|---|---|
| ③ | `MemoryConfig.java:195-198`（路径探测）+ `MemoryRestorer.java:146,340-342`（`resolveSourceFile()` → `readFile`） | 单路径 + 全量解析 |
| ④ | `BiomeRestorer.java:160` | 同上 |
| ⑤ | `ContainerMemoryApplier.java:372` | 同上 |

改动内容：`resolveSourceFile()` 这类"单路径"抽象换成"**目录 + `_index.nbt`**"，
读取改成 **读索引 → diff → 逐区读变化的区 → 合并**。

**⑧ 是例外，零外部代价**：它只给 agent 读，记忆端不知道它存在（这正是 §2.3 选"独立文件"的红利）。
故 ⑧ 的 `_index.nbt` 只服务 agent（可选，见 §11.13）。

### 11.10 区大小：照抄 MC 的理由与风险（记录）

**定案理由（用户 2026-10-07）**：§7.1 的"26 万格/区"是**理论上限**（= 512×512 × 1 格/列，
即整区每一列都被观测到），实际观测远达不到。

**留档的风险**（不推翻定案，仅备忘）：两个方向都会让它增长——
① 长期在同一区活动会向该值**逼近**（并集是跨会话累积的，不清空）；
② 地形起伏与洞穴暴露会让**单列格数 > 1**，可能**超过** 26 万。

**缓解（这是本方案敢照抄 MC 的依据）**：区键是**纯函数**（`x >> 9`），
**改区大小 = 改一个常量 + 一次性重分片，完全不触及内容格式**；
区文件内的 `regionX` / `regionZ` 自校验字段（§11.5）能在重分片时立刻发现错配。
**故"先照抄 MC、不够再调"是可逆的**——这是本次决策成立的关键前提，若区大小不可逆则应另议。

### 11.11 迁移

- **⑧ 零迁移**：`terrain_union.nbt` **从未落盘**（文件不存在；§10.6 记录尚未跑过 `runClient`）。
- **③④⑤ 需一次性迁移**：现存单文件（实测 998 B / 39 KB / 1.8 KB）→ 读旧文件 → 按区拆写 →
  旧文件删除或改名 `.bak`。数据量小，一次性。
- **无版本协商**：两个 mod 在同一台机器上、同时构建、同时启动，不存在新旧版混跑。

### 11.12 不做

- **不做驱逐 / LRU**：内存镜像仍是**全量常驻**，只是按区组织。真正的内存下界要等确认
  "采集端 mod 内存是瓶颈"后再做——届时数据已按区组织，是顺势的一步。
- **不做 GC**：④ `biomes` 是四个文件里**唯一没有删除通道**的（③ 有 `applyDeletions` 即时修剪、
  ⑤ 有 `applyDeletions` 延迟 K 代际 + 撤销），**只增不减**。它与分片**正交**，
  先加 GC 还是先分片需单独权衡——注意 ④ 今天就是最大的文件（39 KB）。
- **不做自适应区大小**。
- **不切 ⑨**（§11.7）。

### 11.14 首次实机崩溃与其修法（v2.48.1，2026-10-07）

#### 11.14.1 现象

21:52:10 记忆端集成服务器崩在 `TerrainRestorer.tick` → `readFile`，崩溃报告写
`Description: Loading NBT data`。日志里的抛出物是
`net.minecraft.nbt.ReportedNbtException: Loading NBT data`，`Caused by:
java.io.EOFException: Unexpected end of ZLIB input stream`。

#### 11.14.2 原因：① 的**非原子写** × 读取点的**catch 写窄了**

两个独立缺陷叠在一起才致命：

1. **① `terrain.nbt` / ② `entities.nbt` 仍在非原子写**（§11 只切了 ⑧③④⑤，① ② 原样保留）。
   采集端 21:52:10.761 正在整体覆盖写 `terrain.nbt`，记忆端同一秒按 mtime 门读到的是"gzip 头在、
   尾不在"的半截文件。**这次爆炸的直接诱因是文件变大**：① 从 841 B（10-02）涨到 458972 B（10-07），
   覆盖写的耗时从微秒级变成百毫秒级，"读方每 tick 轮询"撞上写入窗口的概率不再是零。
2. **读取点的 `catch (IOException e)` 拦不住它**。`NbtIo.readCompressed` 对截断文件抛的是
   **非受检**的 `ReportedNbtException`（它把 `EOFException` 包在里面），`IOException` 分支根本不进
   ⇒ 异常直接冒到 `onServerTick` ⇒ 集成服务器崩。**两端全部读取点都犯了这个错**，不止崩的这一处。

   > 这条与 §11.9.3 的"读失败不推进门控、下轮重试"是同一件事的两半：那段代码**写对了**降级逻辑，
   > 但降级分支挂在了一个永远不会进的 catch 上——等于没有。

#### 11.14.3 顺带发现：迁移路径本次没有被走到

- 21:40:39 的一次 `ls` 显示三个旧单文件俱在（`biomes.nbt` 38969 B / `block_entities.nbt` 998 B /
  `containers.nbt` 1826 B）；21:48:05 采集端启动时它们已不在。
- 但 21:49:01 的首次保存里 ④ 是 `total=5592, added=5592`（**全部为本会话新增**）⇒ 启动瞬间
  `loadExisting()` 读到的区目录是空的，`migrateLegacyIfPresent()` 因"旧文件不是普通文件"直接返回。
- 两端代码里**没有任何会静默移除旧文件的路径**：采集端唯一的移除手段 `retireLegacyFile` 是无条件
  INFO 日志 + 改名 `.migrated`；`deleteRecursively` 只被 ③ 的 `clear()` 调用；记忆端一处删除都没有。
- ⇒ 那三个文件是**在 mod 之外**（21:40:39–21:48:05 之间）消失的。**待确认是否人为清理**；
  若是，则 §11.13 第 4 项（迁移）至今**一次都没跑过**，属于未验证代码。

#### 11.14.4 修法（两条都要，缺一不可）

1. **写方原子**：① `VisionTerrainStore.writeFile` / ② `VisionEntityStore.writeFile` 的裸
   `NbtIo.writeCompressed` 换成 `UnionSaveScheduler.writeAtomic`（`.tmp` + `ATOMIC_MOVE` 回退
   `REPLACE_EXISTING`）。至此**采集端每一个被读方轮询的文件都是原子写**——与 §11.9.3 已经确立的
   "文件存在 ⇒ 文件完整"同一条不变量。
2. **读方容错**：两端所有 `NbtIo.readCompressed` 读取点的 catch 从 `IOException` 加宽为
   `IOException | RuntimeException`。**这不是第 1 条的冗余**：第 1 条只保证"今后不再产生半截文件"，
   而"进程被杀 / 断电 / 两个 mod 版本混跑"留下的半截文件会**永久留在地雷状态**——每次轮询都崩。
   降级行为沿用各自既有语义（索引/区 → 返回 null/空表 ⇒ 不推进 mtime ⇒ 下轮重试；
   ① ② 的 `loadExisting` / ③ 的姿态 / ⑤ 的末影箱 → 返回 null ⇒ 保留旧内存镜像）。

   > **不变量（新增）**：凡"写方原子 + 读方按 mtime 轮询"的文件，读方还必须能容忍"文件坏"并降级为
   > 下轮重试。理由是 MC 的 NBT 读取把坏文件错误设计成了**非受检**异常——`catch (IOException)` 是
   > 一条静默失效的防线。
