## 1. 返回码

### 1.1 三个返回码

| 返回码 | 含义 | 由谁产生 |
|---|---|---|
| `SUCCESS` | 做成了 | 条件为真；动作完成 |
| `FAILURE` | **没成** | 条件为假；动作报告失败 |
| `RUNNING` | 还没做完，下一个 tick 继续 | 跨 tick 的动作 |

**【已定，2026-10-05】只有三个。** 曾经设计过第四个 `UNCOVERED`（"没有一条规则适用于当前局面"），**已否决**，理由见 §1.2.1。

### 1.2 传播规则（教科书语义）

**Selector**（按子节点顺序求值，遇 `SUCCESS` 或 `RUNNING` 停止）：

| 情形 | 返回 |
|---|---|
| 任一子节点 `SUCCESS` | `SUCCESS`（立即短路） |
| 任一子节点 `RUNNING` | `RUNNING`（立即短路） |
| 全部 `FAILURE` | `FAILURE` |

**Sequence**（按子节点顺序求值，遇 `FAILURE` 或 `RUNNING` 停止）：

| 情形 | 返回 |
|---|---|
| 任一子节点 `FAILURE` | `FAILURE`（立即短路） |
| 任一子节点 `RUNNING` | `RUNNING`（立即短路） |
| 全部 `SUCCESS` | `SUCCESS` |

**`Match`（§3.3）不做聚合**：它的返回值**直接取命中分支的返回值**。

**推论（需在实现与校验中守住）**：条件节点必须集中在 Sequence 前部。中置条件一旦为假就立即短路，会造成"**已经产生了副作用，却报告本分支失败**"——那是个静默的谎言。校验器应对此告警。

#### 1.2.1 为什么没有 `UNCOVERED`（原方案已否决）

**【已定，2026-10-05】**

原设计要求第四个返回码：条件为假不返回 `FAILURE` 而返回 `UNCOVERED`，并让它**穿过 Sequence 向上传播**，使"我压根没有对应规则"能在树根可见，作为升级给慢树的信号（D3）。

否决它的不是"大模型能不能自己判断"，而是**快树的结构从一开始就错了**。

原推理是：升级信号必须在树根可见，而分支几乎都是"以条件守卫开头的 Sequence"，经典语义下守卫失败会让整条分支返回 `FAILURE`，树根就分不出两种情况。推一遍快树：

```
Selector (reactive) "反射根"
  ├─ Sequence "溺水自保"      ← 触发条件：在水下且氧气低
  ├─ Sequence "着火自保"      ← 触发条件：正在燃烧
  └─ Sequence "近战自保"      ← 触发条件：5格内有敌对生物
```

| 情形 | 过程 | 根返回 |
|---|---|---|
| 无威胁 | 三个触发条件全假 | `FAILURE` |
| **有怪，但既没退路也没武器** | 触发条件为真，"手段"层全失败 | `FAILURE` |

**Selector 的语义就是"一个不行试下一个"，它天生不保留"哪个不行"。** `UNCOVERED` 被发明出来，只是为了把这条被 Selector 丢掉的信息捞回来。

正确的做法是**换节点类型**：快树要回答的是"现在到底是哪种局势"，这是**互斥分类**，不是优先级选择。改用 `Match`（§3.3）之后，这个问题在结构层面就消失了——"触发条件为真但没解决"由**命中分支 + `FAILURE`** 唯一确定（见 §7.2），不需要任何全局返回码。

**连带收益**：所有节点的语义回到教科书。写树的人、读树的人、以及任何参考第三方行为树资料的地方，都不需要再做语义转换。

**已否决的备选方案**（记录以免重复论证）：保留 `UNCOVERED`，但降级成"只作用于快树的结构约定"——快树每个分支必须以 `Condition` 开头，触发条件为真而分支返回 `FAILURE` 即记一次"未处理局面"。它确实能跑，但那是在**给一个错误的结构打补丁**：既然每个分支都要检查触发条件，那它本来就该是 `Match`。

## 3. 控制节点

### 3.1 求值模式：`memory` 与 `reactive`

每个 `Sequence` / `Selector` 必须声明 `mode`（`Match` 没有——它的 `when` 天然每 tick 重评，见 §3.3）：

- **`memory`**：记住游标。子节点返回 `SUCCESS` 后，下一个 tick 从它的**下一个**孩子继续。已完成的步骤不重跑。
- **`reactive`**：每个 tick 都从**第一个**孩子重新求值。优先级/守卫每 tick 重新确认。

**这不是一个可有可无的开关，它决定"恢复"能不能成立。** `reactive` 模式下每个 tick 都重跑所有前置步骤，动作节点必须幂等或自带"我已经做过了"的判断——对任务树是灾难。

**结论（重要）：两棵树的求值模式不同。**

- **任务树用 `memory`** —— 不重跑已完成的步骤。
- **全局反射树用 `reactive`** —— 每 tick 重评优先级，这正是它存在的意义。

D1 的"两棵树"划分刚好和"两种求值模式"重合。安全相关的持续守卫由反应树负责，任务树可以放心用 `memory`。

**【审阅点 2】** 会不会出现任务树里某个守卫需要在动作执行期间持续确认？例如"挖矿中，如果工具耐久归零则中止"。按当前设计，这类检查属于全局反射树（它对所有任务生效），任务树不必自己管。但如果确实需要任务**特有**的持续守卫，`memory` 模式就漏掉了它，得单独设计。

### 3.2 `Sequence` / `Selector`

```json
{ "id": "1.2", "type": "Sequence", "name": "金矿采集主链", "mode": "memory", "children": [ ... ] }
```

`name` 是给人和大模型读的，不参与执行。

### 3.3 `Match`（互斥分类）

**这是快树的根节点类型**，也是全设计里唯一"非教科书"的部分——但它是**新增一个节点**，不是改写已有节点的语义，所以不影响任何别的地方。

```json
{
  "id": "r",
  "type": "Match",
  "name": "当前局势",
  "arms": [
    { "when": { "type": "Condition", "cmd": "player.is_underwater", "params": { "oxygen_below": 5 } },
      "then": { "type": "Sequence", "name": "溺水自保", "mode": "memory", "children": [ ... ] } },
    { "when": { "type": "Condition", "cmd": "player.is_burning" },
      "then": { "type": "Sequence", "name": "着火自保", "mode": "memory", "children": [ ... ] } },
    { "when": { "type": "Condition", "cmd": "entity.nearest_hostile", "params": { "range": 5 } },
      "then": { "type": "Selector", "name": "手段", "mode": "reactive", "children": [ ... ] } }
  ],
  "otherwise": { "type": "Sequence", "name": "正常", "mode": "memory", "children": [] }
}
```

**规则**：

1. `arms` 从左往右求值 `when`，**第一个为真者胜出**
2. tick 命中 arm 的 `then`；**它的返回值就是 `Match` 的返回值**，不做聚合，**不试后面的 arm**
3. 全部 `when` 为假 → tick `otherwise`，同上
4. **`otherwise` 必填**（缺失则校验失败）

**与 `Selector` 的差别**（这三行决定了什么时候用哪个）：

| | `Selector` | `Match` |
|---|---|---|
| 语义 | 优先级 / 备选方案 | **互斥分类** |
| 谁判断"适用" | 分支内部自己判断 | **`when` 显式给出** |
| 分支失败后 | 试下一个 | **不试，直接上抛** |
| 穷尽性 | 无要求 | **`otherwise` 必填** |
| 典型场景 | "有现成铁镐就用，没有就现做一把" | "现在到底是哪种局势" |

**为什么快树必须是 `Match` 而不是 `Selector`**：见 §1.2.1。一句话——`Selector` 会把"触发条件为真但没解决"和"触发条件为假"压成同一个 `FAILURE`，而快树**运行时**没有大模型可用，压掉了就分不出来。

**`when` 强制为 `Condition` 叶子。** 两个理由：求值必然便宜（§4.1 对 `Condition` 的要求），以及可静态校验。

**`Match` 本身每 tick 重评 `when`**（这是它的意义），所以它没有 `mode` 字段。各 arm 的 `then` 子树各自声明自己的 `mode`。

**两条与快树自动迭代相关的约束**（快树由大模型离线生成并迭代优化，见 §7.1 / [目标Agent画像.md](目标Agent画像.md) §2.5 T9）：

- **`when` 只能用命令注册表（§9）里的现成条件**，不能自由发明。理由同上——规则 1 的"求值必然便宜"是靠原语白名单守住的，不是靠"作者会自觉"。**已定。**
- **新增 arm 插在哪一位、按什么排序，规则未定。** 规则 1 的"第一个为真者胜出"意味着插入位置会直接改变已有 arm 的命中结果：插在前面会抢走后面的命中，插在后面可能永远轮不到。手写时靠人的直觉排序；大模型迭代写树时必须有显式规则（紧迫度？特异性？）。**待定，记在 T9。**

### 3.4 `Parallel`

**建议第一版不做。** 真正的并行动作在 Minecraft 里很少（"边走边看"是寻路的内部实现，不是两个并行动作），而 `Parallel` 的失败/成功策略组合（`require_all` / `require_one`）会成倍增加语义复杂度。等到确实出现"必须同时做两件事"的场景再加。

**【审阅点 3】** 如果你已经预见到需要并行（例如"逃跑的同时吃东西"），现在就说，它会改变 `RUNNING` 的传播规则。

### 3.5 `Repeat`（循环）

**【已定，2026-10-05，D11】** 从装饰器**升为独立类别**——它多了一个终止条件，不再是"单孩子装饰器"。

**两种终止条件，二选一，必居其一：**

```json
{ "type": "Repeat", "n": 64, "child": { "…": "…" } }
```

```json
{
  "type": "Repeat",
  "until": { "type": "Condition", "cmd": "inventory/count-at-least",
             "params": { "item": "cobblestone", "count": 64 } },
  "maxIterations": 128,
  "child": { "type": "Sequence", "mode": "memory", "children": [ "…" ] }
}
```

**五条规则：**

1. **`n` 与 `until` 必居其一。** 都没有 = 无限循环，schema 直接拒绝。
2. **`until` 先检查后执行**（`while` 语义，不是 `do-while`）。背包里已经有 64 个就一次都不挖。
3. **每轮迭代开始，`child` 的游标归零**（见 §6.5.1）。`child` 若是 `reactive`，本规则无效果——它本来就每 tick 重评。`Repeat` 自己**没有 `mode`**，语义是固定的。
   **归零的只有执行状态（游标），不重建胶囊实例帧**（§5.1）——帧是任务状态，与迭代无关。`child` 是 `SubTree` 时，帧只在**进入调用点**时创建一次。
4. **`child` 返回 `FAILURE` → 整个 `Repeat` 立即 `FAILURE`**，不跳过这一轮继续；向上走 §7.5。全部迭代 `SUCCESS` 才 `SUCCESS`。
5. **`until` 模式必须给 `maxIterations`。**

#### 为什么条件循环不能用 `n` 代替

「挖 64 个圆石」里，**"挖了 64 次"和"拿到 64 个"是两个不同的命题**：

- 某次迭代空手而归（方块被水冲了 / 半路被抢占打断）→ 挥了 64 次，只拿到 63 个
- 背包满时挖出来的东西**直接消失且不报错** → 数量对不上还查不出原因
- 连锁挖矿类的 mod 一次挖一串 → 早就够了还在挖

`n` 把"什么时候算完成"焊死在写树的时候；`until` 每轮重读一次世界。

**顺带一个反例**：想在现有节点里用 `Repeat(-1) { Sequence[ Inverter(until), 循环体 ] }` 凑出条件循环**是坏的**——迭代 1 里 `Inverter` 成功了，`Sequence` 的游标就移过去了，迭代 2 直接跳过它，条件**再也不会被检查**。这正是规则 3 存在的原因，也是为什么 `until` 必须是节点级字段，而不能写成循环体的第一个孩子。

#### 规则 3 是循环成立的核心

行为树里没有 `for` 计数器——**"重新做一遍"的唯一表现形式就是"游标归零"**。少这一条：

```
Repeat(until: 圆石 >= 64)
└─ Sequence (memory) "挖一个圆石"
    ├─ Condition "附近有圆石"
    ├─ Action    "走过去"
    └─ Action    "挖掉"
```

- **迭代 1**：找到 → 走过去 → 挖掉 → `SUCCESS`，游标走到**末尾**
- **迭代 2**：再 tick 这个 `Sequence` → 游标已在末尾 → **直接返回 `SUCCESS`，一条命令都没跑**
- `Repeat` 认为这轮成功了，数量没变，条件仍不成立 → 继续下一轮……**空转 64 次，然后报告"挖完了"**

而且游标归零在这里**恰好就是"重新观察世界"**：循环体第一个节点是 `Condition "附近有圆石"`，重建游标 = 重读一次。上一轮那个坐标早没了，不归零等于拿着过期坐标去挖一个不存在的方块。

#### 规则 5 为什么是必须的

`until` 可能永远不成立——周围没有圆石，或者圆石在岩浆对面走不到。`Timeout` 也能兜底，但**迭代次数上限更好用**：不受 tick 卡顿影响，语义也更贴（"我试了 128 次都不行" > "我花了 40 秒"）。

用尽后返回 `FAILURE`，正好接上 §7.5 的三步廉价试探 → 升级慢树。

#### 循环是惰性展开的放大器

这条比上面几条都更贴本项目的处境。

按 D7，树是大模型惰性展开的。**没有循环节点**，"挖 64 个圆石"只有两条路：

- 展开 64 棵几乎一样的子树 → 64 次大模型往返，而且每棵会长得略有不同（LLM 不是确定性的）。第 37 棵忘了检查背包满不满，就出错
- 展开 1 棵 → 但没有任何节点能表达"重复它"

**有循环节点，LLM 只需展开一次循环体。** 往返次数从 66 降到 2（一次展开循环骨架，一次展开循环体），出错面从 64 处收敛到 1 处。

#### 暂缓：`ForEach`

遍历黑板上的一个列表（"把这箱子里的东西挨个搬过去"）是**另一类**循环——终止条件既不是计数也不是世界谓词，而是"列表走完了"。第一版用不上，等真有需求再议。

### 3.6 装饰器明细

| 装饰器 | 语义 | 备注 |
|---|---|---|
| `Inverter` | `SUCCESS`↔`FAILURE` | 一个孩子 |
| `Retry(n, delay)` | 子节点 `FAILURE` 时重试至多 n 次 | 超过 n 返回 `FAILURE` |
| `Timeout(ms)` | 超过时限则中止子节点并返回 `FAILURE` | 触发子节点的 abort |

## 4. 叶子节点

### 4.1 `Condition`

```json
{ "id": "1.1.1", "type": "Condition", "name": "威胁检测", "cmd": "player.is_attacked", "params": { "range": 5 } }
```

- **必须无副作用**，只读世界状态。
- **必须便宜**，会以快树的 tick 频率被调用。只能读本地缓存快照，不得发起服务端往返（见 [目标Agent画像.md](目标Agent画像.md) §2.5 T7）。
- 返回 `SUCCESS`（真）或 `FAILURE`（假），永不返回 `RUNNING`。

### 4.2 `Action`

```json
{
  "id": "1.2.4",
  "type": "Action",
  "name": "采集金矿",
  "cmd": "macro_collect_resource",
  "params": { "type": "gold_ore", "count": 1, "tool": "iron_pickaxe" },
  "writes": ["mine.count"]
}
```

- 返回 `SUCCESS` / `FAILURE` / `RUNNING` 三者之一——动作不会"不适用"，所以它不可能返回 `Match` 里 `when` 假那种情况的任何变体。
- `cmd` 必须在命令注册表中存在（见 §9）。
- `params` 必须匹配注册表声明的参数 schema。
- `writes` 声明它写哪些黑板键（见 §5），由注册表提供默认值；显式声明可覆盖。

### 4.3 `PendingExpansion`（待展开占位）

这是 `Study/bt_output.json` 里 `expand_logic` 的正式形态。它**不是 Action**——它不在世界里做事，它是"这里需要一棵子树，但我还不知道长什么样"。

```json
{
  "id": "1.2.1.2",
  "type": "PendingExpansion",
  "name": "逻辑展开：合成铁镐",
  "goal": "获取石镐、煤炭并熔炼成铁锭，随后合成铁镐",
  "inputs": ["iron_ingot", "stick"],
  "outputs": ["iron_pickaxe"],
  "hint": "初始状态：背包无铁镐"
}
```

- `inputs` / `outputs` 是**可检查的契约**：展开出来的子树必须能声明它消费 `inputs`、产出 `outputs`。这让"大模型展开了一个不干活的子树"变成一个可检测的错误。
- `hint` 是给大模型的额外上下文，不参与校验。

**展开时机（关键设计）：展开不发生在 tick 内。**

执行器到达 `PendingExpansion` 时，返回一个**独立的控制信号** `NEEDS_EXPANSION`（不是四个返回码之一），挂起任务树，把控制权交回慢树的规划阶段；展开完成后用新子树替换该节点，再从该位置继续 tick。

**理由**：如果允许在 tick 中同步展开，tick 循环就会阻塞在一次大模型调用上——而这正是双树架构要避免的失败模式。快树抢占的时刻也无法预测，两件事撞在一起会很难调试。

**【审阅点 4】** `NEEDS_EXPANSION` 期间任务树是挂起状态，这段时间里 agent 只受全局反射树保护。如果展开很慢（几秒），agent 会"发呆"几秒——除非让慢树在展开期间保持上一个动作继续跑。要不要这个"继续跑"，是个独立的选择。

## 5. 黑板

### 5.1 作用域

**每个任务树实例一个黑板**（"任务" = 一棵慢树的作用域，见 [目标Agent画像.md](目标Agent画像.md) §2.2 D12；**任务之间黑板清空，世界状态靠命令重查**）。全局反射树**不读写黑板**（保持无状态，否则共享状态会成为两棵树之间的隐式耦合）。

任务树被替换（重规划）时清空。树被中止（D4 重置）时**不清空**——重置的是树的执行状态，不是任务状态；慢树需要靠黑板里的内容判断三档判据（D3）。

#### 5.1.1 两级作用域（2026-10-07 新增）

**一个黑板，两级作用域链**：任务帧 + 胶囊实例帧。

```
任务帧     ← 树主体读写；胶囊的 outputs 拷贝到这里
  └─ 胶囊实例帧   ← 每次 SubTree 调用创建一个；形参拷入，裸名默认写这里
```

**为什么需要**：§5.3 原本只要求"胶囊用命名空间前缀"来避免不同胶囊互相踩，但那条规则管不住**同一个胶囊被调用两次**——两处调用写的是同一个 `nav.current`，顺序执行时是覆盖，嵌套或并发时是互相破坏。

| 规则 | 内容 |
|---|---|
| **解析** | 裸名（`current`）→ 实例帧。`$name` → 先查实例帧，未命中再查任务帧。任务树主体只有任务帧 |
| **写入** | 裸名**只能写实例帧**。胶囊无法直接写任务帧 |
| **跨边界** | 只能经胶囊的 `outputs` 声明：退出时自动把实例帧的值拷回任务帧，键名用 `outputs` 里写死的那个 |
| **禁止遮蔽** | 实例帧的裸名不得与任务帧已有键重名，校验器直接报错 |
| **禁止递归** | 运行时深度上限（如 8 层），超了返回 `FAILURE`。静态查环抓不到经 `PendingExpansion` 的间接递归 |

**生命周期**

| 事件 | 实例帧 |
|---|---|
| 进入胶囊（装载时实例化） | 创建，形参拷入 |
| 退出（`SUCCESS` / `FAILURE`） | 按 `outputs` 拷回任务帧，然后**丢弃**。失败时**也拷**——部分结果正是 D9 恢复要的证据 |
| 被中止（D4 重置） | **冻结保留**，与任务帧"中止不清空"同一个理由。D9 恢复时"这个胶囊走到哪了"是判据之一 |
| 树被重规划 | 丢弃 |
| `Repeat` 进入下一轮迭代 | **不动**（帧是任务状态，不是执行状态，见 §3.5 规则 3） |

**实例 id**：胶囊体在**装载时**实例化进运行树，胶囊内的节点获得实例 `id` = `<调用点 id>/<胶囊内 id>`（如 §8.2 例子里 `n1.5` 调用点内的是 `n1.5/g1`）。树**文件**里不展开——存储层仍只有 `{ ref, params }`（§8.1）。这是 D9 证据链能跨重规划使用的前提：§8.4 的"路径是运行时派生的"在实例化之后依然成立。

**存储层不展开的理由**：展开写进文件会让树体积随调用点数量线性增长，而每次调用点的节点 `id` 都是新的——改一处调用，diff 上就多出一整棵展开的子树，§8.4 的"未受影响的节点保持原 `id`"随之失效。

### 5.2 什么进黑板，什么不进

- **进**：任务执行状态。这次挖了几根、上次失败的原因、还剩几个目标。这些**没有服务端回读通道**。
- **不进**：世界状态。背包里有什么、血量、坐标——这些通过命令直接查，冗余存储会引入不一致。

这条边界要守住，否则黑板会变成一个什么都塞、然后没人知道哪个值是新鲜的垃圾抽屉。

### 5.3 类型与命名

- 类型保持小集合：`number` / `boolean` / `string` / `vec3` / `itemStack` / `list`。
  **`list`（2026-10-07 补）** 是必需的：处理视觉返回值之后最常见的结果就是列表（可见方块、掉落物、路点），胶囊的 `inputs` 也常常是一个列表。元素类型由胶囊的 `signature` 声明（如 `{ "type": "list", "item": "vec3" }`）；列表**整体覆盖**，不支持部分更新。
- **跨胶囊边界的名字必须带命名空间前缀**（`chop.count`、`nav.lastReached`），指的是两类键：**任务帧的键**，和胶囊 `outputs` 声明的键。
  **胶囊内部的名字自由起**（`current`、`remaining`）——两个胶囊内部的同名键活在**不同的实例帧**里，本来就不碰（§5.1.1）。
  > 这条比 2026-10-06 版**更弱**：原版要求"胶囊必须用前缀"，现在是"跨边界必须用前缀"。约束放松了，因为它要解决的问题（两个胶囊互相踩）已经被实例帧解决；剩下的只有回传时的碰撞。
- 校验器检查四件事：**未声明的写**（动作写了它没声明要写的键）、**写冲突**（同一节点内两个**可能并发或顺序不定**的兄弟子树声明写同一个键——`Sequence` 里两个有序的写同一个键是合法的覆盖）、**未声明的读**（`$x` 没有来源）、**遮蔽**（实例帧裸名与任务帧已有键重名，§5.1.1）。

### 5.4 读写接口

走命令注册表，不新增节点类型。大模型只需学一套机制（`cmd` + `params`）：

```json
{ "type": "Condition", "cmd": "blackboard.compare", "params": { "key": "mine.count", "op": ">=", "value": 8 } }
```

**【审阅点 5】** 递增由谁做？两个选择：(a) 动作在注册表里声明 `writes`，执行器自动递增；(b) 大模型显式写一个 `blackboard.increment` 节点。我倾向前者——少一类大模型会犯的错（忘了写递增，导致条件永不满足、无限循环）。代价是灵活性下降，比如"每次加 2"就要另想办法。

## 6. 中止（abort）

### 6.1 触发

只有一个触发源：**全局反射树抢占**。任务树没有"自愿中止"的概念——那是 `FAILURE`。

### 6.2 传播

`abort()` 从任务树根递归向下，只有当前处于 `RUNNING` 的那条路径上的节点会收到：

- **控制节点**：把 `abort()` 转发给当前活跃的孩子。**自己的游标保留**——归零的只有被中断的那个最小任务，见 §6.5.1。
- **叶子节点**：执行自己的清理。

### 6.3 默认中止流程

大多数叶子使用默认实现，内容是固定的四步：

1. 停止当前移动 / 寻路
2. 松开所有按下的按键
3. 若开着容器界面 → `container/close`（D5）。**不要求它回报 carried 的去向**——那个信息客户端读不到，改由 §6.5 的自动判断从世界里读出来
4. 取消未完成的批量时序

**不触碰黑板。**

### 6.4 特例中止（少数）

D4 撤掉了"每个节点声明 halt 语义"的字段，代价是特例变成隐式知识。**这个代价由命令注册表补回来**（§9）：命令声明 `consumes`（消耗资源）或 `irreversible`（不可撤销）时，**注册时强制要求提供自定义中止实现**，否则命令注册失败。

这满足 D4 的残留要求——"新加了一个用消耗品的动作但忘了写中止"会在**注册期**响亮地失败，而不是运行时静默烧物品。

### 6.5 中止之后：恢复步骤

**树重置，不冻结（D4）。** 记住"我在哪"不等于冻结"我当时的状态"。

**只记录一样东西（D9，2026-10-06 简化）**：

**被中断的最小任务的位置**——从根到它的 `id` 链。

**不记**段内已执行到哪条命令。**也不记**前置 / 后置边界 `Condition`：前置就是 M 在父序列里的前一个兄弟，树里可查；后置不记的理由见 §6.5.2。

**判断与恢复是同一段（D6）。** 执行器另外自动读**中断前后世界的差异**——位置、背包、容器是否还开着、附近有没有新出现的掉落物 / 实体。这一项是关键：它让"携带中的物品掉在地上"这类**客户端没有回执**的状态变化变得可判定——掉地上就是附近多了一个掉落物实体。

#### 6.5.1 游标归零

**游标（`memory` 模式的进度）只在两种场合回到起点**：

| 场合 | 归零范围 | 见 |
|---|---|---|
| **循环开始新一轮迭代** | `Repeat` 的 `child` 整棵子树 | §3.5 |
| **抢占恢复** | **只有**被中断的那个最小任务，祖先全部保留 | 本节 |

除这两者外，游标**永不归零**——节点首次被 tick 时它本来就停在起点。

下面说的是**抢占恢复**这一种。

怎么识别最小任务：按 [目标Agent画像.md](目标Agent画像.md) §2.2 D8，最小任务内部没有读取。所以**执行器结构化判断即可，不需要额外字段**——沿活跃路径**从上往下**找，第一个**子树内不含 `Condition` 节点**的控制节点，就是被中断的最小任务。

```
Sequence (memory) "容器交互"
  ├─ Condition "界面已开"           ← 前置边界
  ├─ Sequence (memory) "搬两组"      ← 子树内无 Condition → 游标归零
  │    ├─ Action slot 2
  │    ├─ Action slot 0
  │    └─ …
  ├─ Condition "get: 已搬完"         ← 下一个段的入场券，不是"搬两组"的毕业证（§6.5.2）
  └─ …
```

被打断在 `slot 0` 上 → 内层 Sequence 游标归零（整段重跑），**外层游标不动**。

**为什么祖先必须保留**：清空游标 = 从根重跑整条路径。若任务树是 `[装备铁镐, 下到 y=16, 容器交互, 采集金矿]`，在"容器交互"被苦力怕打断，清空游标意味着恢复时"下到 y=16"要**重新寻路**。位置没变、镐还拿着，没有理由重跑。

#### 6.5.2 恢复判定：回溯到前置边界，交大模型（D9）

**【2026-10-06 改】** 原设计是本地三步判定（① 求值后置 → ② 求值前置 → ③ 重跑，上限 1）。**第①步已废弃**，理由见下；整个本地判定随之塌缩成一次大模型调用。

```
被打断在最小任务 M 的中途
   ↓
回溯到 M 的入口（游标归零到 M，§6.5.1）
   ↓
交大模型，附三样证据：
   · M 的定义（goal / inputs / outputs / 段内命令）
   · 前置 Condition 的求值结果
   · 中断前后世界的差异
   ↓
继续跑 M ／ 修补 M 或其后的计划 ／ 重规划
```

**为什么废弃①**：① 是"求值 M 的后置 Condition，`SUCCESS` 说明段其实已做完"。这一步不成立——**`Condition` 的求值永远是对的，问题在于它描述的对象与 M 无关。**

| | 前置 Condition | 后置 Condition |
|---|---|---|
| 与 M 的关系 | M 的**必要条件**：不成立则 M 一定跑不动 | **既非必要也非充分** |
| 对"M 做完了吗"的信息量 | 能**否定** M | **零信息** |

**根因：写 `Condition` 的人是为它后面的东西写的。** 它是下一个兄弟的入场券，不是前一个兄弟的毕业证。它读起来像 M 的验收条件，只是好树的巧合——[目标Agent画像.md](目标Agent画像.md) D8 原来那句"末尾那次观察同时充当后置断言"说的正是这件事，那句已一并修正。

```
Sequence "夜间作业"
  ├─ Condition "是白天"
  ├─ Sequence "露天挖矿"          ← M
  ├─ Condition "天还亮着"         ← 为下一步"继续露天作业"写的
  └─ …
```

中断后求值「天还亮着」→ `SUCCESS` → 旧① 判「露天挖矿已完成」→ **静默跳过**。天是否还亮，跟挖了几个矿毫无关系。

还有三条构造上的理由，让①连猜都猜不准：

- **M 是父序列的最后一个孩子** → 后置根本不存在，① 直接落空
- **M 的父是 `Match` 的 arm 或 `Repeat` 的 body** → "兄弟"不是序列步骤，语义完全不同
- **M 的左兄弟是另一个最小任务而非 `Condition`** → 前置也不存在；此时没有便宜预筛，直接交大模型（方向保守，无害）

**砍掉①的代价很小**：① 的收益是"省掉一次没用的重跑"——纯优化，不是正确性检查。做完了还重跑一遍，最坏是浪费几条本地命令。真正的代价只在含 `consumes` / `irreversible` 的段上（重跑一次 = 多消耗一次），这类段的恢复靠大模型看着世界差异判断。

**前置也不当门控，当证据**：前置不成立时答案未必是"重规划整棵树"，可能是"容器被中止流程关了，重开一下"。硬门控会把小补丁升级成整树重规划。反正这次大模型一定要被叫，把前置的求值结果作为输入交出去，成本一样，信息更多。

**重试上限消失**：原来的"上限 1"是防「重跑 → 后置不成立 → 再重跑」的环。没有后置就没有环——重跑挂在树自己的返回码上，`FAILURE` 上传，正好接 §7.5。

**成本与它成立的前提**：每次抢占恢复一次大模型往返，慢树停顿秒级。这不违反 D3——D3 的前提是"这个判断本地做得对"，而"被中断的段做到哪了"本地做不对，从来不在 D3 的适用范围内。代价可接受的前提是**"情节结束"是低频事件**（§7.4：只发生在命中真实 arm 且返回 `SUCCESS` 时），**这个频率需要实测确认**。其间快树照常每 tick 跑。

**「前置成立」不等于「重跑安全」**（这条与本次改动无关，仍然成立）：前置只说明**进入时**的假设成立，不说明段内每条命令的假设成立——段内没有读取（D8），那些假设**从未被验证过**。举例：M = `[slot2 拿起, slot0 放下]`，中断在中间，中止流程 close 时服务端把 carried 还给背包或掉在地上（[目标Agent画像.md](目标Agent画像.md) §2.3①），slot 2 于是从「有铁锭」变成「空」。**若前置写的是「界面已开」，它会通过**，然后重跑去点空槽。

**已知的洞（待定，与本次改动无关）**：**重跑可能返回 `SUCCESS` 而什么也没做成。** 上例重跑时，点空槽被 `AbstractContainerMenu.doClick` 的 `!carried.isEmpty()` 守卫拦下（空操作），点 slot 0 同样为空操作——**M 返回 `SUCCESS`，一个铁锭都没搬**。原"段内幂等"防线（标记沿用 §6.4 的 `consumes` / `irreversible`，不新增概念）只保证**重跑不会把事情搞坏**，不保证**重跑能把事情做成**；容器点击大多幂等，恰恰因此看不出这个洞。旧①本来也堵不住它——它只在后置恰好相关时撞上。

**待定**：

- 交给大模型的世界证据里，"中断前后差异"的窗口**从中断那一刻才开始**，看不见 M 已经做到哪。要让它判断"M 是否已达成"，需另给一份**进入 M 之前的快照**（至少覆盖 M 的 `inputs` / `outputs` 涉及的部分）。加不加，等价于"接不接受偶尔白跑一次 M"。
- 恢复请求在飞行中时又被抢占：丢弃旧请求还是排队。

### 6.6 中止的耗时上限

中止本身可能比威胁还慢（§D5 讨论过的延迟问题）。因此：

**【审阅点 6】** 是否需要一条紧急旁路——威胁距离小于阈值时跳过默认中止流程的第 3 步（关容器），接受界面残留？我倾向于**需要**，但阈值需要实测确定。

## 7. 执行模型

### 7.1 两棵树的共存

| | 全局反射树 | 任务树 |
|---|---|---|
| 数量 | 1，常驻 | 0 或 1（**「0」待设计**，见下） |
| 求值模式 | `reactive` | `memory` |
| 树的来源 | 大模型**离线**生成 + 迭代优化，**运行时无大模型** | 大模型**在线**惰性展开（D7） |
| 读黑板 | 否 | 是 |
| tick 频率 | 高（抢占检查） | 与任务节奏一致 |
| 条件代价 | 必须极低 | 可以是前提重检 |
| 改动门槛 | **新增 arm 自动；修改 / 删除已有 arm 需审阅 + 可回滚**（T9） | 自动（每次展开即是改动） |

**两棵树的"大模型介入时机"是反的**，这是关键区别：快树的树在**运行时之外**就定好了，tick 里一行大模型都不跑；任务树的子树是**运行到那里才生成**的。所以 §7.3 那条"tick 中不允许任何大模型调用"对快树而言是设计前提，对任务树而言是流程约束（靠挂起实现，见 §4.3）。

**快树的改动门槛更高，因为代价不对称**：慢树规划错了顶多挖不到东西，快树改错了是 agent 被烧死、淹死、炸死。详见 [目标Agent画像.md](目标Agent画像.md) §2.5 T9。

**「0 或 1」里的「0」是一个尚未设计过的状态。** 任务树只有两种时刻存在：正在跑一个任务，或者没有任务。后者的行为、以及**下一个任务从哪来**（D2 明确说了快树不产生新任务），见 [目标Agent画像.md](目标Agent画像.md) §2.2 **D12**——那里定了"一棵慢树 = 一个任务，不是一次对话"，并给出任务来源的配套。

**「0 或 1」还有一个更硬的推论：任务必须串行。** 任务粒度按**目标状态**切（D12），于是"等待"被吸进任务内部（`Repeat` 的 `until` + `waitMs`，§3.5 / §9.3），而同时只允许一棵树 ⇒ 同一时刻只有一件事在被推进。想并行就得允许同时存在多棵树，那要改的就是本表这一行本身。见 D12「任务粒度 ⇒ 任务必须串行」。

### 7.2 tick 顺序

每个 tick：

1. tick 全局反射树，读**两个**结果：**命中的是哪个 arm** + **返回码**
2. 按下表决定动作
3. 若未抢占 → tick 任务树
4. 任务树返回 `NEEDS_EXPANSION` → 挂起，转入规划阶段

**快树的四种情况**（快树根是 `Match`，见 §3.3）。全部由"命中哪个 arm + 返回码"唯一确定：

| 命中 | 返回 | 含义 | 动作 |
|---|---|---|---|
| `otherwise` | `SUCCESS` | 无反射适用 | 什么都不做，tick 任务树 |
| 真实 arm | `RUNNING` | 情节进行中 | **抢占** |
| 真实 arm | `SUCCESS` | 情节结束 | 恢复流程（§6.5） |
| **真实 arm** | **`FAILURE`** | **识别了局面，但解决不了** | **升级慢树**（D2） |

两点要注意：

- **"命中哪个 arm"是可读的**，不是靠返回码反推。"无反射适用"（命中 `otherwise`）和"有反射但处理不了"（命中真实 arm + `FAILURE`）在结构上就分得开——**这正是 §1.2.1 否决 `UNCOVERED` 的原因**。
- **`otherwise` 每 tick 都会命中**（空闲是常态）。所以恢复流程（§6.5）**不能锚在"根返回 `SUCCESS`"上**，必须锚在"命中的是真实 arm"上，否则每个空闲 tick 都会跑一遍恢复。

**反射树的情节是边缘触发的**：一旦进入（命中真实 arm 且返回 `RUNNING`），跑完整个情节才重新检查条件。检查可以高频，但**进入**不能。否则"吃掉食物的 1.6 秒里条件持续为真"会反复重入（见 [目标Agent画像.md](目标Agent画像.md) §2.5 T3）。

### 7.3 tick 中不允许出现的操作

这条是硬约束，校验器和 code review 都要守：

- **任何大模型调用**
- **任何阻塞式等待**
- **条件节点里的世界写操作**
- **任何可能发起服务端往返的操作**（除 `Action` 明确声明的）

### 7.4 快树抢占的返回约定

**命中真实 arm 时**：`RUNNING` 表示"我还在处理"；`SUCCESS` 表示情节结束——此时进入恢复流程（§6.5）。命中 `otherwise` 则什么都不是，直接 tick 任务树。

**恢复流程不做本地判定，直接交大模型（§6.5.2，2026-10-06 改）。** 每次情节结束一次大模型往返，慢树停顿秒级。挂起期间快树照常每 tick 跑，agent 不受保护缺失。

代价可接受的前提是**"情节结束"是低频事件**：它只发生在命中真实 arm 且返回 `SUCCESS` 时（命中 `otherwise` 每 tick 都有，不算），与 §7.5 那个秒级的 `FAILURE` 不是一个量级。**这个频率需要实测确认**——若实际与失败同频，须回来补本地门控。

> 原【审阅点 7】（情节结束后先廉价重检还是直接交还慢树）已由 D9 定案，见 §6.5.2。

### 7.5 任务树根返回 `FAILURE` 之后

**【已定，2026-10-05】** 不无条件交慢树，**先做一次廉价试探**——与 D3「先廉价重检、失败才升级」同一条原则。

```
任务树根 FAILURE
   ↓
① 重试该节点一次（覆盖瞬态失败：寻路被挡、目标刚要挖到）
     SUCCESS → 继续
     否则 ↓
② 换目标重试（若该节点声明了多个候选目标，如"金矿"有多个矿点）
     SUCCESS → 继续
     否则 ↓
③ 交慢树：由大模型判断重规划整棵树，还是换个方式重试
```

①② 都不消耗大模型往返。

**为什么需要它**：`FAILURE` 是最高频的返回码（挖不到、走不过去、背包满了）。如果每次都要一次秒级的大模型往返，慢树会被日常失败淹没。真正需要大模型的只是"我这条路走不通了"。

**待定**：② 的"候选目标"从哪来——由命令注册表声明（§9），还是从失败节点的 `params` 推。若走注册表，那是对 §9 的新要求。

## 8. JSON 表示

### 8.1 完整字段表

| 字段 | 适用类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | 全部 | 是 | 稳定标识，生成时分配。用于引用被打断的节点 |
| `type` | 全部 | 是 | 见 §2 |
| `name` | 全部 | 否 | 人类/大模型可读，不参与执行 |
| `children` | `Sequence`/`Selector` | 是 | |
| `arms` | `Match` | 是 | 每项 `{ when, then }`；`when` 必须是 `Condition` 叶子（§3.3） |
| `otherwise` | `Match` | 是 | 必须存在，保证穷尽 |
| `mode` | `Sequence`/`Selector` | 是 | `memory` \| `reactive` |
| `cmd` | `Condition`/`Action` | 是 | 命令注册表中的名字 |
| `params` | `Condition`/`Action`/`SubTree`/`Compute` | 否 | 值可以是**字面量**，或 `"$键名"` **读引用**（先实例帧后任务帧，§5.1.1）。`Condition`/`Action` 按命令注册表 schema 校验；`SubTree`/`Compute` 按胶囊 `signature.inputs` 校验（§8.3） |
| `writes` | `Action` | 否 | **映射**，不是键名列表：左 = 黑板键，右 = 值来源。值来源可以是 `returns` 的字段路径、三个路径拼成的 `vec3`、`"+1"` 递增。默认取自注册表。**裸键名写实例帧，带前缀的键名写任务帧**（§5.1.1） |
| `child` | `Repeat` / 装饰器 | 是 | 单个孩子 |
| `n` / `ms` | `Retry` / `Timeout` | 是 | |
| `n` / `until` | `Repeat` | **二选一，必居其一** | 计数循环 / 条件循环（§3.5） |
| `maxIterations` | `Repeat` | `until` 模式下必填 | 硬上限，防止 `until` 永不成立（§3.5） |
| `ref` | `SubTree` / `Compute` | 是 | `名字@内容哈希`，指向胶囊库条目（§8.3） |
| `goal` / `inputs` / `outputs` / `hint` | `PendingExpansion` | `goal` 必填 | 见 §4.3 |

**这张表只覆盖树文件。** 胶囊文件是另一种制品（字段：`name` / `kind` / `hash` / `origin` / `signature` / `preconditions` / `body`），格式见 [算法层与执行层设计方案.md](算法层与执行层设计方案.md) §8.2。本文档与胶囊库的接触面只有两处：`ref` / `params`（语法）与实例化时机（§8.3）。


注意几处变化：原 `bt_output.json` 的根节点把"紧急自卫层"写进了任务树——按 D1 它应该属于**全局反射树**，任务树里不该有。示例中已移除。

**`n1.4` 也可以不塞进宏动作，由树自己表达循环**（§3.5）：

```json
{
  "id": "n1.4",
  "type": "Repeat",
  "name": "采集 8 个金矿",
  "until": { "type": "Condition", "cmd": "inventory.count-at-least",
             "params": { "item": "raw_gold", "count": 8 } },
  "maxIterations": 24,
  "child": {
    "id": "n1.4.1", "type": "Sequence", "name": "挖一个金矿", "mode": "memory",
    "children": [
      { "id": "n1.4.1.1", "type": "PendingExpansion", "goal": "找到最近的金矿并挖掉它",
        "outputs": ["raw_gold"] }
    ]
  }
}
```

两种写法的取舍不在"哪个对"，而在**循环边界露不露在树里**：宏动作版执行器看不见循环，出错时面板上没东西可看；显式循环版每次迭代重读一次背包，且 LLM 只需展开一次循环体（§3.5 末节）。

**`SubTree` 调用（全文档第一个例子）**：

```json
{
  "id": "n1.5", "type": "SubTree", "name": "走到矿区",
  "ref": "nav.goto@a3f9c1",
  "params": { "route": "$nav.waypoints" }
}
```

三件事：

- `ref` = `名字@内容哈希`，指向**胶囊库**条目，不是内联的子树（§8.3）。
- `params` 的键必须与胶囊 `signature.inputs` 声明的形参**一一对应**；值可以是字面量（`[248, 71, -64]`），也可以是 `"$键名"` 读引用（这里取任务帧的 `nav.waypoints`）。
- **调用点必须给全**。胶囊里没有"默认去读某个全局键"这条路——这正是 `params` 要消灭的东西。

胶囊库里对应的条目（人写的，`origin: "human"`）：

```json
{
  "name": "nav.goto",
  "kind": "tree",
  "hash": "a3f9c1",
  "origin": "human",
  "signature": {
    "inputs":  { "route": { "type": "list", "item": "vec3", "required": true } },
    "outputs": { "nav.lastReached": { "type": "vec3" } }
  },
  "body": {
    "type": "Sequence", "mode": "memory",
    "children": [
      { "id": "g1", "type": "Repeat", "name": "逐个路点走完", "maxIterations": 200,
        "until": { "type": "Condition", "cmd": "blackboard.compare",
                   "params": { "key": "$remaining", "op": "==", "value": 0 } },
        "child": { "…": "…" } }
    ]
  }
}
```

注意 `body` 里的名字：`$route` 是**形参**（进实例帧），`$remaining` 是**胶囊内部**的键（也活在同一帧里）。两者都不带命名空间前缀——因为调用点看不见它们。**回传的任务帧键才要前缀**，就是 `outputs` 里的 `nav.lastReached`（§5.3）。

### 8.3 胶囊引用与实例化

**存储层不展开，装载时才实例化。** 树文件里永远只有 `{ ref, params }`。

| 层 | 看见什么 |
|---|---|
| 树文件（存储） | `{ "ref": "nav.goto@a3f9c1", "params": {...} }`——diff 干净，胶囊体改版不会让树文件变化 |
| 运行树（装载后） | 胶囊体被复制进来，内部节点获得**实例 id** = `<调用点 id>/<胶囊内 id>`（如 `n1.5/g1`） |
| 内省接口（G1） | 按实例 id 索引的扁平表。胶囊内部节点的执行状态（返回码、游标、重试计数）照常出现在表里，不需要特殊处理 |
| 黑板 | 每个调用点一个**实例帧**（§5.1.1） |

**为什么不在存储层展开**：展开会让树体积随调用点数线性增长，而且每个调用点的节点 `id` 都是新的——改一处调用，diff 上就多出一整棵子树，§8.4 的"未受影响的节点保持原 `id`"随之失效。

**版本引用用内容哈希（`name@hash`）的理由**：树是大模型生成和修改的产物。它不需要"人可读的版本号"，它需要**引用不会在背后变化**——胶囊库更新后，已保存的树必须仍然指向当初那一版。哈希覆盖 `signature` + `preconditions` + `body`（不含 `name`），内容相同即同一条目。库保留所有**被某棵已保存的树引用过**的版本，其余可回收（细节见 [算法层与执行层设计方案.md](算法层与执行层设计方案.md) §8.4 / §8.6）。

**【审阅点 11】** 哈希的粒度：改一行注释也会换哈希，所有引用它的树都"过期"。备选是把注释排除在哈希外，代价是哈希不再完全覆盖语义。

### 8.4 ID 与路径

- `id` **稳定**：树被编辑（替换一个子树）时，未受影响的节点保持原 `id`。
- **路径**（从根到叶的 `id` 链）是运行时派生的，只在**当前树版本内**有效。慢树用路径定位被打断的节点，跨版本无效——这是可以接受的，因为重规划后路径本来就失去了意义。

**跨版本稳定（2026-10-05 补充，T4 的要求）**

上面第一条原本说的只是"同一棵树的运行期内"。版本保存系统（[目标Agent画像.md](目标Agent画像.md) §2.5 T4）要能算 diff，要求更强的一条：

> **反思 / 重规划修改树时，未受影响的节点必须沿用原 `id`，不得重新生成。**

否则整棵树会被重写一遍（哪怕语义完全没变），diff 上全部显示为"删除 N 个 + 新增 N 个"，历史不可读、回滚不可信。

**这不是引擎能自动保证的——它约束的是生成树的大模型**，必须在展开 / 反思的提示词里明确告知："改动树时，保留未受影响节点的 `id`。"

## 9. 命令注册表接口

49 条命令散在 14 个 API 文件里，目前**没有任何自描述**。这是实打实的现状缺口，也是本节存在的原因。

### 9.1 每条命令必须声明

| 字段 | 用途 |
|---|---|
| `name` | 命令 ID，如 `container/drag` |
| `params` | 参数 schema（供校验，也是给大模型看的文档） |
| `returns` | 返回结构 |
| `preconditions` | **同时是候选 Condition 节点库** |
| `postconditions` | 用于展开契约的 `inputs`/`outputs` 校验 |
| `abort` | 默认 or 自定义；见 §6.4 |
| `consumes` | 消耗的资源；非空则强制要求自定义 abort |
| `irreversible` | 是否不可撤销；为真则强制要求自定义 abort |
| `cost` | **代价档位**，决定它能否出现在 Condition 里、能否进快树（见下） |

**`cost` 需要三档，不是布尔**：

| 档 | 含义 | 能出现在哪 |
|---|---|---|
| `local_cached` | 读本地缓存快照，O(1) | **快树 Condition** + 任务树 Condition |
| `local_scan` | 本地但要扫描（如遍历附近实体） | 仅任务树 Condition |
| `server` | 发起服务端往返 | 仅 `Action`，**不能做 Condition** |

快树每 tick 都要重评它的全部 `when`（§3.3），所以**只有 `local_cached` 能进 `when`**——这就是 §3.3 说的"原语白名单"的具体形式。

`local_cached` 那一档现在还没有实现基础：[目标Agent画像.md](目标Agent画像.md) §2.5 T7 要求 steveX 现有的视觉 / 实体 / 容器几套 API 先提供廉价的"当前帧"读取口。**在它落地之前，快树的 `when` 没有可用的原语。**

### 9.2 为什么这份表是提示词

**树的质量上限 = 命令文档的质量。** 大模型写不出它不知道的动作，也写不对它不知道的前提。`preconditions` 一栏尤其关键——它同时产出两个东西：

1. 执行时的动作准入检查
2. 行为树里 Condition 节点的候选来源

这两件事**不该分家**。所以在 API 层把前置条件写清楚，收益是双份的。

### 9.3 时序由 `waitMs` 承担

**【已定，2026-10-04】** 命令段内部的时序由树里**显式的 `waitMs`** 表达。树里可以直接出现 `{"waitMs": 200}` 这样的步骤。

**`waitMs` 的语义**：在**无法同时进行**的两个行为之间强制断开。

| | 例子 | 写法 |
|---|---|---|
| **互斥** | 打开背包 / 攻击 | 两者之间必须有 `waitMs` |
| **不互斥** | 前进 / 横移（不同输入轴） | 省略 `waitMs` |

**已否决的方案：命令层完成语义。**

方案内容是：让每条命令声明自己属于"我完成了"还是"我排队了"，属于后者的再声明一个可观察条件，由执行器自动插入等待。这样树里就不需要 `waitMs`。

否决理由：

1. 49 条命令逐条声明观察条件，工程量与出错面都太大。
2. **即使条件立刻成立，仍然需要 `waitMs`。** Minecraft 不允许同一时刻执行大量操作，两个操作之间必须有间隔——这是底层机制，不是保守估计。因此该方案省不掉 `waitMs`，只是叠加了一层复杂度。

**已核对的事实**（说明为什么这个间隔是必须的，以及为什么读不出来）：

现有命令层有两种调用形态，混在一起用。

- `container/get` 走 `AgentWebSocketServer.runOnClient(2_000, ...)`（`AgentWebSocketServer.java:180`）—— **阻塞**。它把 lambda 投到客户端线程队列，用 `CountDownLatch` 等结果，最多 2 秒。
- `container/slot` 走 `Minecraft.getInstance().execute(...)`，然后立刻 `return Map.of("status","ok")`（`ContainerApi.java:417`）—— **不阻塞**。点击在之后的某个 tick 才真正发生。

所以点击之后必须等一段，等多久取决于客户端队列排空到哪一 tick。**这个长度无法从命令的返回值里读出来**——这正是 `waitMs` 必须存在的原因。

#### 9.3.1 赌输时的后果（已核对，接受此风险）

**客户端点击是乐观执行的。** `MultiPlayerGameMode.handleInventoryMouseClick`（`decompiled_src_vf/client/net/minecraft/client/multiplayer/MultiPlayerGameMode.java:444`）先在本地 `containerMenu.clicked(...)`（`:457`），**然后**才把 diff 发给服务端：

```java
containerMenu.clicked(slotNum, buttonNum, clickType, player);
// …算出 changedSlots，再 send(ServerboundContainerClickPacket)
```

所以连续点击**在客户端本来就自洽**——`waitMs` 不是为了保证客户端状态正确。

**服务端收到后**（`decompiled_src_vf/server-1.21.11_unobfuscated/net/minecraft/server/network/ServerGamePacketListenerImpl.java:1853`）：

```java
boolean fullResyncNeeded = packet.stateId() != this.player.containerMenu.getStateId();
this.player.containerMenu.clicked(slotIndex, packet.buttonNum(), packet.clickType(), this.player);   // ← 照样执行
// …
if (fullResyncNeeded) {
    this.player.containerMenu.broadcastFullState();   // ← 用服务端状态覆盖客户端
} else {
    this.player.containerMenu.broadcastChanges();
}
```

**点击不会被丢弃，它会在服务端的真实状态上执行。** 如果客户端那条乐观链已经和服务端分叉，这一步就做了一个**和意图不同的操作**，随后 `broadcastFullState()` 把客户端整个覆盖回去。

**这条路径没有日志**——`fullResyncNeeded` 分支里一行 LOGGER 都没有。失败是静默的。

所以 `waitMs` 不是同步，**是赌往返在给定时间内完成**。赌输时后面每一步都基于错的前提，而日志上每一步都是 `ok`。

**为什么仍然可以接受（不引入新机制）**：按 [目标Agent画像.md](目标Agent画像.md) §2.2 D8，最小任务的末尾本来就有一次读取。段内的错位会在**段末那次读取**被发现——代价是丢掉一段的命令，而不是一直错到底。

**推论（约束）**：命令段不宜写得太长。这正是 D8 里"读得太疏"那条的等价说法。另外，段末那次读取必须**真的被当作条件用**（D8 的分支点），而不是走个过场。
