## 存储布局

```
src/bt/
├── README.md
└── trees/
    ├── fast/   快树：版本链（v1 → v2 → v3）
    └── slow/   慢树：① 任务内演化链  ② 跨任务实例集
```

两棵树**共用一套版本机制，但是两个独立存储区**（[目标Agent画像.md](../../docs/目标Agent画像.md) §2.5 T4 第 4 条）。分开的实质理由不是内容不同，而是：

| | 快树 | 慢树 |
|---|---|---|
| 生命周期 | 长期资产（周 / 月迭代） | 任务工件（分钟级） |
| 增长 | 几版到几十版 | **每个任务一棵 → 无限** |
| 保留策略 | 全留（要能回滚） | 必须清理 |
| 写入模式 | **事件驱动**（一批可审阅的改动 = 一版） | **流式**（每次展开 / 重规划写一条） |

## 一棵慢树 = 一个任务（D12）

树的创建单位是**任务**，不是对话。判据：**根 goal 达成后，可以停下来做别的事而不损失**。

由此产生一个尚未设计的配套：**任务来源**。§7.1 说任务树数量是「0 或 1」——"0"（空闲态）的行为、以及下一个任务由谁派发，目前只有方向（当前：人下指令；后续：任务选择器），形态未定。见 [目标Agent画像.md](../../docs/目标Agent画像.md) §2.2 D12。

**推论：任务必须串行。** 粒度按目标状态切（不是按动作），等待因此被吸进任务内部（`Repeat` 的 `until` + `waitMs`）；加上任务树数量「0 或 1」，同一时刻只有一件事在被推进。**要并行就得允许同时存在多棵树——那要动的是 §7.1 本身，不是给记忆加一类。** 见 D12「任务粒度 ⇒ 任务必须串行」。

## 实现时第一个会撞到的问题

`src/agent/agent.js` 目前**每 3 秒轮询一次** mod 状态（`player` / `f3` / `status`），而 [行为树节点设计方案.md](../../docs/行为树节点设计方案.md) §7.2 要求**每个 tick** tick 一次全局反射树（游戏 tick = 20Hz）。

60 倍的差距。快树要能抢占，就必须有 mod 侧的 tick 推送（或 tick 事件回调），不能靠轮询——这也正是 §2.5 T7「抢占检查的读取代价」要求"读本地缓存快照，不得每次问服务端"的原因。
